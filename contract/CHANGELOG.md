# contract — change log

## 2026-10-27 — Whether a node's updates are available, and each update run of a node; capabilities-contract 0.31.0

`capabilities-contract` 0.31.0 adds ledger step `0032-node-updates` (store tables 1.17). `capabilities_node_states` gains `update_available` (boolean), `update_offer` (jsonb, the producer's account of what is newer and what it brings) and `update_checked_at`, null until the node's manager has checked; `node_state_put`, the node's regular state write, leaves them as they are. `capabilities_node_updates` holds one row per update run of a node: a uuid `id`, `node` with a foreign key to `capabilities_nodes` that follows its id and goes with it, and no `project_id`, since the run is the machine's. `state` is one of `requested`, `running`, `updated`, `current`, `rolled_back` and `failed`, beside `requested_at`, `requested_by`, `started_at`, `finished_at`, `reason` in words, and jsonb `versions_before`, `versions_after` and `doctors`. The store refuses a second requested or running row for a node (a partial unique index), a start time on a requested row or none on any other, a finish time on an open row or none on an ended one, and a `rolled_back` or `failed` row without a reason. Every insert or update of a row raises the version of channel `capabilities_node_update` for its node in `schema_channel`, so the node's manager, following it, takes a request up at once. The store tier's `node_update_offer_put` writes the availability onto a node's state row, `node_update_request` inserts a requested row and refuses `update_pending` while one is open, `node_update_claim` closes a row left running as `failed` with an interrupted reason and marks the requested row running or makes the node's own, `node_update_finish` ends a running row, `node_updates` reads each node's latest run, and `node_states` reads the three new columns. No capability script changes: the range `>=0.12,<1` admits 0.31.0.

## 2026-10-27 — What a node is expected to have, and the owner's word on it; capabilities-contract 0.29.0

`capabilities-contract` 0.29.0 adds ledger step `0031-node-expectations` (store tables 1.16). `capabilities_node_logins` gains `claude_needed`, `codex_needed` and `gh_needed`, booleans defaulting to false: whether a service the agent places on that node needs that tool signed in there. Two tables keep the owner's word over that, per agent and node. `capabilities_node_login_expectations` is keyed by `project_id`, `node` and `tool` (`claude`, `codex` or `gh`). `capabilities_node_session_expectations` is keyed by `project_id`, `node`, `capability` and `connection`. Each row carries `expected`, `updated_at` and `updated_by`, and the `node` foreign key to `capabilities_nodes` follows its id and goes with it. No manager write replaces a row; it goes only with its node or when the owner takes it back. In the store tier, `node_logins_put` takes `needed`, the tools the placed services need; `None` leaves what the row says of that as it is. `node_logins` reads the three columns. `node_expectation_set` sets a word to true, false or none and answers `{before, after, changed}`, and `node_expectations` reads them. No capability script changes: the range `>=0.12,<1` admits 0.29.0.

## 2026-10-27 — Each node's state and its agents' device-bound sessions; capabilities-contract 0.28.0

`capabilities-contract` 0.28.0 adds ledger step `0030-node-states` (store tables 1.15). `capabilities_node_states` holds one row per node, keyed by `node` with a foreign key to `capabilities_nodes` that follows its id and goes with it, and no `project_id`: the row is the machine's, shared by every agent on it. It carries `load_1`, `load_5`, `load_15`, `cpu_count`, `memory_used_bytes`, `memory_limit_bytes`, `disk_used_bytes`, `disk_total_bytes`, `booted_at`, `boot_line`, `image_version`; `reported_at` is the store's time of the write and `fresh_until` that and the stated interval (`NODE_STATE_FRESH_SECONDS`, 90), after which the node reads unreachable. `capabilities_node_logins`, keyed by `project_id` and `node` with the same foreign key, holds for each of `claude`, `codex` and `gh` a `<tool>_login` - `signed_in`, `signed_out`, `absent` or `unknown` - with the `<tool>_account` it states, kept only while signed in, and `checked_at`: a sign-in is per agent, since a tool keeps it in the home of the OS user it runs as. `capabilities_node_sessions`, keyed by `project_id`, `node`, `capability` and `connection`, holds `live`, `account` and `checked_at`, with the same foreign key. The store tier's `node_state_put` writes a node's whole row and answers its `reported_at` and `fresh_until`, `node_logins_put` writes a project's sign-ins on a node, `node_sessions_put` replaces a project's sessions of one capability on a node, `node_agents_prune` drops the sessions of the asked projects' other capabilities and the sessions and sign-ins of projects no longer linked to the node, never another linked project's, and `node_states`, `node_logins` and `node_sessions` read them, `node_states` with `reachable` and `uptime_seconds` by the store's now.

## 2026-10-26 — Any node an agent lets write changes its shared records and settings, not only the master; capabilities-contract 0.26.0

`capabilities-contract` 0.26.0's store tier lets a node whose link to a migrated agent carries `may_write` write what the master writes: the rows every node shares (node null) - settings, identifiers, connections, grants, the default pointer and policy - and the rows naming itself. Before, every write such a node made was moved onto rows naming it, so it never changed what the other nodes read. Where such a node already holds a row naming itself for what it writes - a setting path in its own settings document, an identifier, a grant, its default pointer or its policy row, as it wrote them before - it reads that key from that row, so its write lands there: it changes or removes its own value, and only once it holds none does it write the shared one. A settings write splits the same way, path by path, so an edit never copies a node's own values into the shared document. A row naming another node is still the master's alone (`node_read_only`), a node whose link does not carry `may_write` still writes nothing (`node_read_only`), and while `migrating_since` is set only the migration on the master writes (`agent_migrating`). A settings write made from a document read earlier is refused rather than written over another node's change: `settings_write` takes `base`, the generation the change was made from as `setting_generations` gives it, and refuses `stale_edit` where the scope's generation is another by the time it holds the document's lock; `<name> settings edit` passes the generation it read before the editor opened, so an edit another node wrote under exits 6 `stale_edit` and changes nothing, and run again it reads the new document. `settings set` and `unset` were already applied to the document as it stands under that lock, and `put` replaces the document whole, as before. No ledger step and no capability script change: the range `>=0.12,<1` admits 0.26.0. The manager moves to `>=0.26.0,<1`.

## 2026-10-25 — Each node's row of what it runs, and whether it works; capabilities-contract 0.23.0

`capabilities-contract` 0.23.0 adds ledger step `0028-service-instances` (store tables 1.13): `capabilities_service_instances`, one row per service a node supervises, keyed by `project_id`, `capability` and `node`, deleted when the node stops supervising it. `state` is one of `starting`, `ready`, `unusable`, `degraded`, `failing`, `held`, `waiting` and `stopping`, and `ready` is computed from it (`ready` or `degraded`). The store tier's `service_instance_put` writes a whole row and `service_instance_drop` deletes it. deployment moves to `>=0.23,<1`; every other capability script keeps its range.
