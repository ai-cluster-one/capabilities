# contract — change log

## 2026-10-17 — `migrate files plan` creates and upgrades no table

The plan a capability gives `capabilities migrate` changes nothing in the store, its own tables and every other owner's included: every connection the capability opens through the shared database layer during `migrate files plan` is one connection per database inside a transaction that is never committed, a migration on it runs the steps it would apply inside that transaction and records them, and the transaction is rolled back when the plan ends, so the capability reads its tables as an upgrade would leave them whether they are missing or behind. The steps are named by owner under the report's `tables_to_upgrade`. Every capability carries the change through `sync-contract`.

## 2026-10-16 — Helpers for a moved agent: whether its records are rows, and retired overrides

The preamble gains `_records_in_store()` (whether this project is an agent whose records and settings moved into the store) and `_env_override(*keys)`, which returns an override naming a record or settings file and, for a moved agent, ignores it with a one-line notice on stderr. Every capability carries the change through `sync-contract`.

## 2026-10-16 — `migrate files` moves a capability's own files of a project into the store

Every capability answers `<name> migrate files plan|write|verify [--answers FILE]` with JSON, for the manager's `capabilities migrate`: it reads no policy row (the machine ceiling answers it, and `write` the read-only switch), opens the project's records as the migration (`migrate@<node>`, through the new `_RECORDS_ACTOR`), and calls the capability's optional `_migrate_files_mover(action, answers, all_answers)`, defined outside the fences, which returns its `items`, `questions`, `files`, `verified` and whatever else it names; without one it moves nothing. The manifest carries `migrate_files`, true where the capability defines a mover. Every capability carries the change through `sync-contract`.

## 2026-10-16 — An agent whose records moved into the store reads and writes everything there, settings included

`record_table_steps()` gains `0014`-`0018` and `STORE_TABLES_VERSION` moves to `(1, 3)`: grants take a form for every agent (`agent_id` null) with a default pointer of their own, keyed so that two such rows never stand for one grant; identifiers take an optional `node`, keyed with it; and settings become rows in `capabilities_settings` (one per leaf path, a value a scalar, an array or `{}`, guarded by a trigger that refuses an object with keys and a path overlapping another of its document), `capabilities_settings_documents` (the documents that exist, with their generation) and `capabilities_settings_changes` (the append-only trail). `open_records()` asks the agent registry first wherever a database resolves: an agent with `migrated_at` gets the new `AgentRecords`, which reads every record and its settings documents from rows - its own over every agent's, this node's over every node's - and writes them under the node authority (the master writes shared rows, a node with `may_write` rows of its own, nothing else) and the `migrating_since` freeze (only `migrate` on the master). It refuses an agent that moved on a process without `AGENT_NODE_NAME` (`node_unnamed`) or on a node not registered (`node_unregistered`), naming the master. Every other project opens as before; a store that does not answer within two seconds leaves a files-mode project on its files, and a store-mode project's settings then refuse rather than read files. File writes of a project ask the registry too and refuse during an open migration (`agent_migrating`) or after one (`agent_migrated`). `open_records()` takes `actor`; the tier adds `Records.settings_kept()`, `guard_write()`, `setting_document()`, `AgentRecords.settings_write()`, `setting_generations()`, `settings_tree()` and `settings_leaves()`. `_settings_check(scope, document)` loses its `path` and is run on the document itself before anything is written; the `settings` verb writes rows for such an agent, names `generations` and each write's `generation`, takes a JSON array of keys as a path, and gains `export` and `edit [--yes]`. A store that cannot be reached when the adapter opens is exit 5. Every capability carries the change through `sync-contract`.

## 2026-10-16 — A capability reads the project id from project.json alone, and the record tables carry the kernel's

`_project_id_state()` reads the id from the envelope's `project.json` and no longer asks the manager for ContextKit's answer or reads the identity record. A handed-down `CAPABILITIES_PROJECT_ID` for the root is used as given unless project.json declares another, which is the state `mismatch` and refuses a write naming both ids. Where project.json declares no id and the project has `.contextkit/config.toml`, the capability asks the manager, which copies an id that binding holds into project.json once; a manager that cannot answer leaves the state `unresolved`, refusing writes. The states are `declared`, `undeclared`, `handed`, `mismatch` and `unresolved`; `bound` and `contextkit_id` are gone, `_context_identity()` and `_identity_verdict()` are removed and `_manager_declared_id()` is added. `record_table_steps()` gains the steps `0009`-`0013` that create `capabilities_agents`, `capabilities_agent_nodes` and `capabilities_global` and copy ContextKit's `contextkit_agents` rows once, and `STORE_TABLES_VERSION` moves to `(1, 2)`; the tier adds `STORE_AGENTS_TABLE`, `STORE_AGENT_NODES_TABLE` and `STORE_GLOBAL_TABLE`. Every capability carries the change through `sync-contract`.

## 2026-10-14 — Bare `help` says where the project it runs in keeps connections

For a capability with the connections tier, bare `help` now prints a section, `Where connections live`, after the CLI's own help body and before the declared verbs, rendered by the new `_connections_home_section()` from the project's `connections_mode()`: in files mode the project's own `connections.json` and the machine's beneath it, in store mode the store's `capabilities_connections` and `capabilities_connection_grants` tables and that no `connections.json` is read for the project, and outside any project the machine's `connections.json`. It reads `project.json` only. A capability's help body no longer states that home itself and points at the section. Every capability carries the change through `sync-contract`.

## 2026-10-14 — Machine administration answers to the machine ceiling, and `connection add|remove` guard what they would overwrite or take away

Breaking for a caller that updated a connection by adding it again: `connection add` now refuses an id that already exists at its scope with exit 6 `connection_exists`, and writes over it only with `--replace`, which keeps every field not given as an update did. `connection remove` refuses with exit 6 `connection_granted`, naming each project, while a project is granted the connection and would lose it. For a connection kept in the store, that is every project the store holds a grant enabling it for, on any node; the store tier adds `Records.grantees(capability, connection)`. For a connection of the machine, it is the project the call runs in, when that project grants it and declares no connection of its own under that id.

Machine administration reads no policy row: it answers to the machine ceiling, and its writes to the read-only switch. Outside any project, that is a verb declared in `MACHINE_READS`, a verb a `LINK_METHODS` ceremony runs, and `setup` reporting; a capability allowed on the machine but enabled at neither scope now serves them there, where they exited 4 `not_enabled`. Wherever it runs, it is `setup set|unset --machine` and `connection add|remove --machine`, which writes the machine's scope as `--global` does and refuses beside `--project`. Without `--machine`, `setup set|unset` and `connection add|remove --global` pass the policy gate as before. Inside a project every read answers to policy as before. `_gate()` decides it once, in `_machine_administration()`. Every capability carries the change through `sync-contract`.

## 2026-10-13 — What a person is asked for is declared, and written through the contract: `connection add|remove`, `setup`, `settings` and linking events

A capability may declare, above the fences, `CONN_FIELDS` (a connection entry's fields: `key`, `label`, `help`, `type`, `required`, `secret`, and for a secret the `env` template its key is written under), `SETUP_FIELDS` (the machine's prerequisites, env keys kept in its `credentials.env`), `LINK_METHODS` (the interactive ceremonies that link a connection, each an argv carrying `--events`) and `SETTINGS` (its settings homes, one per `project`, `global` or `machine` scope, in JSON or TOML, and the keys it declares, each with its `scope` and whether it applies on the next call, a `service reload` or a restart). `manifest` carries them as `connections {fields, setup, link}` and `settings {homes, keys}`, both `null` where nothing applies, built by the new `_manifest_core()` a capability that adds to its manifest starts from. Each declaration turns on a verb: `connection add <id> [--project|--global] [--default] [--field KEY=VALUE ...] [--stdin]` and `connection remove <id>`, with a secret taken only from the JSON object on stdin and written to the scope's `.env.local` or `credentials.env`, the entry written through the records adapter; `setup [show|set|unset]`; and `settings [show|get|set|unset|put] [--scope S]`, which reads every home whole and writes one key or one document, checked against the declaration and then by the capability's own `_settings_check(scope, document, path)` before the file is replaced. A capability that declares nothing answers none of them, so a domain verb of the same name stays the capability's own. All three pass the policy gate and refuse under the read-only switch. `_events_begin()`, `_event()` and `_event_answer()` carry the linking event stream: once begun, `_emit` writes `{"event": "done", "result": ...}` and `_die` writes `{"event": "error", ...}` before its envelope on stderr. Bare `help` ends with a section rendered from the declarations. Every capability carries the change through `sync-contract`.

## 2026-10-13 — A policy record says which node its row names, and a policy row can be written for one node

A resolved policy record now carries `node`: the node the row that answered names in store mode, and null for the row for every node and for every record read from files, which carry no node. `Records.set` and `Records.delete` take `node`, so a store-mode project writes or removes its row, or the global row, for one node; in files mode a `node` is refused as `node_requires_store`, a node that is not a name as `bad_node`, and a `node` for any collection but `policy` as `bad_node`. The resolution order is unchanged: the project's row for this node, its row for every node, the global row for this node, the global row for every node. Every capability carries the change through `sync-contract`.


## 2026-10-13 — A project's identifiers and gate live in its store with its connections, under one records switch

A project whose `project.json` says `"records": "store"` resolves its connections, grants, default pointer, identifiers and policy from its store, and its files are not read for them. Identifiers come from `capabilities_identifiers`, the project's row (`agent_id` its id) over the global row (`agent_id` null, shared by every project reading that store), label by label. The gate comes from `capabilities_policy`, from the first of: the project's row for this node, its row for every node, the global row for this node, the global row for every node; with none it denies by default. The scope that answered is the one the gate acts on, so service activation still needs a project row. `ids set|rm --global` writes the global scope, in the config home in files mode and as the global row in store mode. Each `ids list` entry carries `scope` (`project` or `global`). A project-scope store write verifies the project id first, and a store that cannot be reached is exit 5 `store_unreachable` for the gate and the `ids` verbs. A project saying `"connections": "store"` keeps only its connections and grants in the store, as before, and every other project resolves from its files exactly as before. The tier adds `records_mode()`, `RECORDS_MODE_KEY`, `STORE_COLLECTIONS`, `STORE_TABLES`, the two table names and `StoreRecords(held=...)`. `connection_table_steps()` becomes `record_table_steps()` with steps `0005`–`0008`, `STORE_TABLES_VERSION` moves to `(1, 1)`, and `connections_mode()` answers `store` under `"records": "store"` too. Machine quarantine and the harness deny rule stay in files. Every capability carries the change through `sync-contract`.

## 2026-10-13 — A node is named by `AGENT_NODE_NAME` where the machine declares it

`node_name()` returns the value of `AGENT_NODE_NAME`, stripped, where the machine declares one, and `socket.gethostname()` where it declares none or declares it empty, so a machine without the declaration is named as before. A container's host name is its container id and changes on every redeploy; a container node that declares its name now keeps it, and with it the store-mode grants naming it and the rows a service records under it. The tier adds `NODE_NAME_ENV`. Every capability carries the change through `sync-contract`.

## 2026-10-12 — A project's connections and grants can live in its store

A project whose `project.json` says `"connections": "store"` resolves its connections, grants and default pointer from two tables in its store, `capabilities_connections` and `capabilities_connection_grants`, through `StoreRecords`, which `open_records` returns for it; every other record stays in files, and a project without that key resolves from its files exactly as before, store or no store. A connection row belongs to no project and is withheld until the project's grant enables it; the project's grants are the rows carrying its id as `agent_id`, a grant naming this node (`node_name()`, the host name) read before the one for every node, field by field, and a null `enabled` or `allow_write` decides nothing. Selection, grant before use (`connection_not_granted`), the write gate, the read-only switch and the `connections` report behave as in files mode; a store that cannot be reached is exit 5 `store_unreachable`. `open_records` takes `project_root`, `project_id` and `application_name`, the tier adds `node_name()`, `connections_mode()`, `connection_table_steps()` and `Records.mode_of()`, and the `read_only` refusal's hint names `capabilities set <name> grant <id>`. The tables migrate under the ledger owner `capabilities` when a project is imported or a store record is written. Every capability carries the change through `sync-contract`, and every connection-bearing capability now pins `capabilities-contract==0.4.1`, the library the store is reached through.

## 2026-10-09 — The store tier keeps records in files only and decides nothing about a database

Breaking. The store tier no longer carries a database: `Store`, `SQLiteStore`, `PostgresStore`, `StoreRecords`, `open_store`, `default_store_path`, `records_mode`, `Scopes` and the machine store setting readers (`read_store_setting`, `find_store_setting`, `store_setting_url`, `check_store_setting` and their companions) are gone, with the `sqlite3` import and the records and project-registry tables they created. `open_records(envelope, global_dir, project_only=False)` returns the files adapter, and refuses a `project.json` that declares a `store` other than `files` with `bad_store_mode`; `CAPABILITIES_STORE_MODE` is not read. The connection and grant resolution `FileRecords.connections` performs, field-wise grants and the project blessing included, is unchanged. The capability core region drops `_store_mode`, `_store_source_label` and `_identifiers_scopes`. Which database a capability's own tables live in is the shared database library's answer alone. Every capability carries the change through `sync-contract`, the `service/store.py` copies included.

## 2026-10-09 — `migrate` and `migrate status` for a capability that keeps tables

A capability that declares `TABLES = True`, with a `_tables()` builder returning its steps and schema version, answers `<name> migrate`, which applies its pending steps to its tables in the machine's store through `capabilities-contract` under the library's lock, and `<name> migrate status`, which reports `state` (`current`, `pending`, `checksum_mismatch`, `schema_too_new`), both versions and the applied, pending and changed steps without a lock. `migrate` reads no policy row: it answers to the machine ceiling, and `migrate`, not `migrate status`, to the read-only switch. A capability that declares no tables leaves `migrate` to its own parser. `manifest` carries `tables`. Every capability carries the change through `sync-contract`.

## 2026-10-08 — The store tier reads the family's store setting file

`read_store_setting()` reads `$XDG_CONFIG_HOME/agentkit/store.json` (`~/.config/agentkit/store.json` when `XDG_CONFIG_HOME` is unset), an `agentkit.store.v1` file carrying the password and an optional `db_schema`, and falls back to the manager's former pair, `$XDG_CONFIG_HOME/capabilities/store.json` and `credentials.env`, only while that file is absent. A file of an unknown `agentkit.store.*` version is refused as `store_setting_too_new`, and a field the format does not have as `bad_store_setting`. `check_store_setting()` admits `sslmode` `disable` for a local host - a Unix socket directory, `localhost` or a loopback address - and `store_setting_url()` carries a socket directory as a parameter. The tier adds `find_store_setting()`, which also says where the setting was found, `store_setting_path()`, `store_url_override()` (`AGENTKIT_STORE_URL`, then `CAPABILITIES_STORE_URL`), `store_host_is_local()`, `store_setting_version()` and `store_setting_document()`. A machine with only the former pair reads as before. Every capability carries the change through `sync-contract`.

## 2026-10-07 — The store tier reads a store setting that names its schema

`read_store_setting()` reads a `capabilities.store.v2` setting as well as a v1 one and returns `db_schema`: the schema a v2 setting names, else `agentkit`. A v2 setting naming a schema that is not a lowercase identifier, or that is `public`, `information_schema` or `pg_*`, is refused as `bad_schema_name`; `check_store_schema_name()` carries that rule. A v1 setting reads as before, with `db_schema` `agentkit`. Every capability carries the change through `sync-contract`.

## 2026-10-04 — Machine reads outside a project, and the policy state in `connections`

A capability may declare `MACHINE_READS`, a tuple of read verbs, beside `WRITE_DEFAULT`. Outside any project a declared verb uses the connections declared globally whose grant does not resolve to `enabled: false`, each one read-only: a write through it exits 4 `read_only`, and `connections` names each one under `machine_reads` with the scope `machine`. Every other verb outside a project, and every verb inside one, resolves its connections as before, and the policy gate, the machine ceiling and the read-only switch apply as before. `<name> connections` now also carries `policy`, the capability's effective policy state: `effective`, its `source` (`machine`, `project`, `global` or `default`) and the `machine` ceiling. A capability that declares no `MACHINE_READS` changes in nothing else. Every capability carries the change through `sync-contract`.

## 2026-10-04 — The store tier reads the machine's store setting

The store tier carries `read_store_setting()`, which returns this machine's store setting and its password from the manager's files, or None when the machine has none, and writes nothing, with `store_setting_url()` to turn it into a connection URL. Nothing calls it yet, so no capability's behaviour changes. Every capability carries it through `sync-contract`.

## 2026-10-03 — The machine ceiling and machine-service calls in the gate

The gate reads this machine's ceiling, `$XDG_CONFIG_HOME/capabilities/machine.json`, before it resolves a project or a policy row: a capability quarantined there refuses its operational verbs and `doctor` with exit 4 `quarantined` in every project and outside any, while `help`, `stub`, `manifest` and `connections` keep working. A capability with no entry, or a machine with no file, behaves as before. A service that declares `service.machine` passes a `<name> service <verb> ... --machine` call without resolving a project or a policy row; under the read-only switch such a service's `init`, `start`, `run`, `reload`, `join` and `leave` are refused, and its `join` requires explicit project enable like `init`, `start` and `run`. A capability without `service.machine` treats `--machine` as before. Every capability carries the change through `sync-contract`.
