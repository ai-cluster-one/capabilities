# capabilities — change log

## 2026-10-25 — `node supervise` supervises the service itself, and a machine service runs once per node from placement

`capabilities node supervise <name>` now supervises its service in its own process, as `deployment runner` did: on each reconcile it reads the gate for this node, takes, renews and releases the service's lease (`deployment_service_leases`, under deployment's name and migration ledger entry, made where the store holds none yet), applies the restart policy, holds a service that exits 4 idle, writes a failure's exit code and stderr tail onto the lease, reports the node seen and keeps this node's row in `capabilities_service_instances`, with the same record and lock under the project's `capabilities/deployment/state/runners/`, so `deployment services` and a runner of an older release see one supervisor. It takes `--every N`, `--restart POLICY` and `-- <command...>`, which is how `deployment runner` hands its service over unchanged, and no longer needs deployment installed. A placed service with no project command that declares a machine one (`service.machine`) is one node-run job for the node, `<capability>.machine` (on a Mac `capabilities.node-machine.<capability>`), running `capabilities node supervise <name> --machine`: one machine process for every agent here that places it, each under its own lease where the service is exclusive, joined to and left from the service's own list through its `service join|leave`, with one instance row per agent; where a machine process it did not start already runs the service here, it starts none beside it and changes no list.

`capabilities node supervise --probe` answers `{"supervises": true}` and starts nothing, which is how `deployment runner` tells this manager from an older one that cannot take its service.

## 2026-10-25 — A Mac's node manager: a launchd agent per placed service, and `node install`

`capabilities node run --launchd` is the node's service manager on a Mac: it keeps one launchd agent of this OS user per service placed on the node, `~/Library/LaunchAgents/capabilities.<agent slug>.<capability>.plist` (labelled by the agent's id where its slug is `machine`, so it never takes a `capabilities.machine.*` agent of deployment's machine scope), whose program is a launcher of the same name running `capabilities node supervise <name> --agent <id>` in the agent's folder, with its logs in `$XDG_STATE_HOME/capabilities/node/launchd/`, and none for any other service. It loads, replaces and takes down each job on its own, loads again a job that is not loaded, and answers a `service restart` with `launchctl kickstart -k`, so `capabilities service start|stop|move|status|restart` work on a Mac as on a box. `capabilities node install [--apply]` installs it once per OS user as the launchd agent `capabilities.node`, after running `deployment handover` in every folder whose services it will run, so the old host agents are booted out before the node manager starts their services; without `--apply` it changes nothing and answers what it would do, which is how a machine's migration is announced before it runs. `--apply` is refused under the read-only switch.

## 2026-10-25 — A node's service manager, and one set of handles for every service

`capabilities node run --supervisor <dir>` is the service manager of a node whose supervisor is Supervisor: run as one of its programs, it keeps one program in `<dir>` per service placed on this node, for every agent the store links to the node whose folder here is bound to it - its own agent's folder being the one it runs in where the store records none, as on a box - and none for any other, applied with `supervisorctl update`. Each program runs `capabilities node supervise <name> --agent <id>` in the agent's folder, which reads the deploy command and restart policy from the installed descriptor at each start and runs it under `deployment runner`. It reconciles on a timer (`--every`, default 60) and within seconds of a placement change, which `place`, `unplace`, `place --all` and `enable|disable|inherit --project --node` now announce through the store's change channel, and it answers a restart asked through the store. `--services` limits it to the services its box carries. Its programs are the supervisor's, so it stops and starts again while the services keep running; while the store cannot be read it changes nothing, and it reports the node seen on each reconcile.

`capabilities service start|stop|move|status|restart` place or unplace a service (start and move as `place --node`, stop as `unplace`, from this node by default or `--all`) and wait up to `--wait` seconds for each node's row in `capabilities_service_instances`: start answers once the row is `ready` or `degraded`, and exits 6 `service_<state>` with the row as the error's detail otherwise; stop answers once the nodes hold no row; restart asks the node's manager and answers once the row's `started_at` moves. `service status` reads every node's row and writes nothing. start, move, stop and restart are refused under the read-only switch.

## 2026-10-25 — `node rekey` moves a node's service instance rows

`capabilities_service_instances.node` (capabilities-contract 0.23) is one of the columns `capabilities node rekey` moves from a node's old id to its new one, with every other column that names a node.

## 2026-10-25 — `dev run` and `dev live` hand down a value kept once for the machine

Where a session payload's manifest declares a setup field `shared` (capabilities-contract 0.22), the user-config tier `dev run` hands down, and the Telegram credentials `dev live start` passes to the payload, ask `~/.config/capabilities/shared.env` under the field's shared name before the capability's own `credentials.env`, as the capability itself does. A project's env files still win, `--project-only` still hands down no user-config value, and a key no field declares shared resolves as before.

## 2026-10-25 — `dev live` borrows the Telegram register the store holds

`capabilities dev live start <session> telegram` borrows the service's register (`telegram_channels`: per channel, the watermark, the `/set` overrides and the reserved jobs) where a Telegram service keeps it in the store and the project names no database of its own, so the session payload reads the machine's database in the session's schema while the canonical service reads it in the machine's own. Before the payload starts, the payload opens its register in the session schema and the canonical rows of the project's connection replace the session schema's; restoring (`dev live stop`, `dev live recover`) carries the session schema's rows back before the canonical service restarts, once, so a recovery repeated after the restart does not carry them again. The takeover therefore catches up what arrived during the switch, and the restored service answers nothing a second time. The takeover lease, which `dev live start` and `dev live status` show, carries `register` (`canonical_schema`, `lane_schema`, `project_id`, `connection`, `borrowed`, `rows`, or the `reason` nothing was borrowed where either schema holds no register table). A project whose own `.env.local` / `.env` names its database, and a payload or canonical service that keeps its register in a file, take over as before. Jobs and prompts stay in the session schema, as before.

## 2026-10-24 — A node has an id and a label: the node registry, `node id` and `node rekey`

A node is a row of the node registry `capabilities_nodes`, keyed by the id the machine resolves for itself (`capabilities node id`: a Mac's from its hardware, any other machine's from `~/.config/capabilities/node-id`, minted there once; `AGENT_NODE_ID` overrides) and shown by its label; `capabilities_agent_nodes` keeps what belongs to an agent and a node together - the folder, the master and may-write flags - and names the node by its id. A reader from before the registry still finds a node's fields on its links, a copy the store keeps of the node's row (capabilities-contract 0.21.1, which the manager now requires). `node list` carries each node's `label`. `node add <id> --label TEXT --kind ...` registers a node by its id (a node another agent already has is linked as it is); `node set <id|label> --label TEXT` renames it, changing that one row and no row that names the node; `node remove` removes the link, and the node's row once no agent lives on it; `node seen` stamps the node's row. `node id [--set <id>]` prints this machine's id, where it came from and the label it gives itself, and `--set` keeps a server's id in its config home (refused on a Mac). `node rekey <old id> [<new id>] [--dry-run]` moves a node from the id it is known by - a node registered before ids keeps its name as its id - to this machine's id or the one given, in one transaction across every column of the store that names a node, refusing while a live lease names the old id and changing nothing when run again; where the machine already registered itself under its id, an agent linked on both keeps one link, on the new id. `init`, `agent materialize` and `migrate` register this machine by its id and label; they no longer need `AGENT_NODE_NAME`, and `node_unnamed` is gone (`node_unidentified` where a machine resolves no id). A dev lane is handed this machine's id as `AGENT_NODE_ID`. Breaking: a node verb takes an id where it took a name, and `node add` needs `--label` for a node new to the registry. Each machine registered before node ids moves once, on that machine with its services stopped: `capabilities node rekey <its old name>`.

## 2026-10-24 — The manager validates a capability's setup presentation

Audit, source check and install validate a manifest's optional `setup`: an object of `title` (non-empty text), `guide` (`url`, an http(s) URL, and `steps`, a non-empty list of non-empty text) and `verify` (the name of one verb), each optional, and no other key. A manifest without `setup` validates as before.

## 2026-10-24 — The global master retires its config home's gate, identifiers and global settings files

`capabilities migrate --retire-records [--root PATH]...` moves the config home's gate (`capabilities/settings.json`), identifiers files (`<name>/identifiers.json`) and global settings files to one dated backup, `$XDG_CONFIG_HOME/capabilities/retired/records-<UTC stamp>/`, each at its path below the config home, on any node, the global master's included, once the store this project (outside one, this machine) reads holds the global rows. It moves them only when every value they hold is a global row of the store with the same value, and refuses, moving nothing, before `global_migrated_at` (`global_not_migrated`), while a value is missing from the store or differs there (`records_not_in_store`, `detail.values` naming each file, capability, key and reason), while a file cannot be read (`files_unreadable`), and while an agent root on this machine has not moved (`agents_unmigrated`, roots found as `--discard` finds them), since an agent not yet moved still reads identifiers and settings from these files. Connections files stay with `--retire-connections`; credentials, env and session files stay where they are. It answers `{ok, global_migrated_at, config_home, backup, retired [{file, backup}]}`. With that and `--retire-connections`, a master's `migrate --report` can answer `config_home.files` empty, which `--discard`, refused on a master, could not; the report's `config_home.reason` and the migrate-to-database guide name both. `--discard`, `--retire-connections` and `--global` are unchanged.

## 2026-10-24 — A routine the agent switched off leaves its routine index

`build` leaves out of the routine index it composes from the store each routine of the agent's own that `routine disable` switched off. A routine switched off still counts toward reading the routines from the store rather than the folder, so an agent whose routines are all off gets an index with no routine in it, not the folder's. A store whose routine tables predate switching a routine off is read as before.

## 2026-10-24 — `agent state` reads an agent across its nodes in one call

`capabilities agent state <id|slug>` answers, for an agent the store holds, every node with its row as `node list` gives it, its `address` (the row's, else the `ip` of the Coolify server it was created on, asked through `coolify servers` and the node's connection; `address_source` says which, `address_error` why none was found), `seen_seconds_ago`, `live`, the gate of each capability a policy row names with the layer that decided it (`source` project, global, machine or default, `node` the node the row was for), the services placed there and the live leases it holds in `deployment_service_leases`; and, per capability with a service installed here or placed on a node, its descriptor's `placement`, its declared `nodes` (null until a descriptor declares `single` or `several`), the nodes it is placed on and the nodes holding its lease. `live` is deployment's answer, read with `deployment node list` in the agent's folder on this machine; where deployment is not installed or the agent has no folder here it is null and `liveness.reason` names why. It writes nothing, needs no project, is allowed under the read-only switch, and exits 6 `agent_unknown` for an agent the store does not hold.

## 2026-10-24 — A capability's main identifier field is validated with its declarations

Wherever the manager validates a manifest it accepts `"identity": true` on one `connections.fields` entry, the field a capability marks as its connections' main identifier, and reports a problem where the flag is not a boolean, marks a secret, or marks more than one field.

## 2026-10-24 — A shared service is placed on every node at once, and `place` shows where a service runs

`capabilities place <name> --all` places a shared service on every node of this project's agent (the nodes `node list` names). It checks every node before writing anything: where any node would refuse - the capability disabled there (`disabled_on_node`), or a row this node may not write - nothing is written, and the error carries the first refusal's code with `detail.refused` naming each node, code and message. It then places node by node, each its own write; a write that fails part-way exits non-zero with `detail {placed, failed}`, and running the command again finishes it. It answers `{placed, nodes, placement, changed, placed_on, enabled_on_nodes?, gate}`; an exclusive service is refused (`placement_exclusive`, exit 6), since it moves with `place --node`, and an agent with no registered node exits 6 `no_nodes`. `capabilities place <name>` with neither `--node` nor `--all` writes nothing and answers `{capability, placement, placed_on, holder, lease, agrees, gate}`: for an exclusive service `lease` is the row deployment's runner holds in `deployment_service_leases` and `holder` its node while it is live, and `agrees` says whether the holder is one of the placed nodes (with nothing placed, whether no node holds it), so it reads false while a move is under way until the lease names the new node; a shared service takes no lease, so the three are null. That report is allowed under the read-only switch. `place --node` and `unplace --node` answer as before.

## 2026-10-24 — A node reports itself seen

`capabilities node seen` sets `last_seen_at` on this project's agent's row for the node the process runs on (`AGENT_NODE_NAME`, else the host name) to the store's now, and answers `{ok, project, agent_id, node, last_seen_at, store}`. It takes no node name, since a node reports itself and no other; a node not registered exits 6 `node_unknown`, and the read-only switch refuses it like the other node writes. `deployment runner` runs it on every reconcile, and `deployment help` says when a node counts as live.

## 2026-10-24 — A folder an agent is raised in does not name it

`capabilities init` gives an agent's row a slug from its folder's name only where the folder makes the agent - init registered the row, or is creating the agent - or still holds the agent's older project.json, settings file or legacy envelope. A folder bound with `--id` to an agent the store already holds, such as a node's `/app`, no longer names an agent that has no slug and no name: the row keeps no slug (`agent.slug` null in init's answer) instead of becoming `app`. A slug carried from a project.json or taken from the agent's name is given as before.

## 2026-10-23 — `path --json` names the store as the home of a layer the store holds

In `capabilities path --json`, a layer of `context`, `assets` or `routines` the agent keeps in its store is answered in `layers` as `{"where": "store", "read": <command>, "folder": <path>}` - `read` the command that lists it (`context list`, `assets list`, `routine list --store`), `folder` where its import and export default to - in place of the path of a folder that may be gone. A layer is held in the store as `build` decides it: context where the store holds a project document or no context folder is there, routines where the store holds one, assets where the store holds an asset document or file. A layer in a folder, and every layer while the store does not answer, is its folder's path as before. A reader that took every `layers` value as a path reads a store-held layer as an object: the shipped `context` and `routine` take `folder` from it. An older copy of either beside this manager fails against a store-held layer until `capabilities update <name>` brings it current: an older `context` in `import` and `export` without DIR, an older `routine` in `import` and `export` without DIR and in `titles` and `title`, each ending with a `TypeError` naming a `dict`.

## 2026-10-23 — A service moves between nodes without turning its capability off on either

A policy row naming a node carries two answers apart: `enabled`, whether the capability's CLI is usable on that node, and `service`, whether the project's bundled service of it is placed there. `capabilities place <name> --node <node>` and `capabilities unplace <name> --node <node>` (store mode, project rows only) change the service alone and never where the capability is usable. A service's descriptor declares how many nodes run it at once as `service.placement`, `exclusive` (the default) or `shared`, which install, audit and source check validate; placing an exclusive service takes it off every other node in the same write, so one `place` moves it, and the CLI stays usable on the node it left. Placing where the project has no row naming the node writes one that also enables the capability there (`enabled_on_node`); placing where that row disables it is refused (`disabled_on_node`, exit 6). `enable --node` and `disable --node` keep writing both answers alike, so they place and unplace as before; `disable --node` and `inherit --node` now say when they took a service off a node (`unplaced`, `warning`) and point at `place`/`unplace`. `connections import` writes, for each capability the project enables itself whose service the files ran, the project's row naming this node with the service placed (`service {placed, unchanged}`), so a service keeps running where it ran once the gate is read from the store; `migrate` writes its placement rows with the service placed. The manager requires `capabilities-contract` 0.17, whose ledger adds the column and fills it so that every service placed today stays placed, and keeps a manager on an older library placing with `enable --node` as before.

## 2026-10-23 — An install or update replaces a capability whose directory the filesystem will not rename

`install` and `update` set the installed payload aside by renaming its directory; where the filesystem refuses that rename as a cross-device link (EXDEV) - a capability a container image installed, in that container's overlay layer - they copy it aside and remove it instead, and the new payload lands as before, with the old one restored if it cannot. A node of the standard image updates its baked capabilities at boot rather than warning `could not update` and running the payload it has.

## 2026-10-23 — A new agent's id is twelve hex characters, and `agent rekey` moves an agent to a new id

`init` mints a new agent's id as twelve lowercase hex characters with no prefix; the `prj_` form and the UUID older agents carry are still accepted wherever an id is read. `capabilities agent rekey [<new id>] [--dry-run]`, run in an agent's folder, moves the agent from the id it is bound to to the one given (twelve lowercase hex characters, exit 6 `input` otherwise) or one it mints, which must be held nowhere in the store (`id_in_use`). In one transaction it rewrites every row of the store's schema whose text column holds the old id whole, holding off inside that transaction the triggers of those tables that would refuse the move, and rolls back where any row still holds it (`rekey_incomplete`); text that only mentions the id stays as history. It refuses, changing nothing, while an unexpired lease row in the store or a machine service's project list on this machine names the agent (`agent_services_running`, each named with how to stop it) and for an agent holding asset files (`rekey_assets_files`), whose objects are stored under the id. It then rebinds the env file of the folder it runs in (another folder this node's row records is named, not written), sets `CAPABILITIES_PROJECT_ID` on each server node created through a coolify connection with `coolify env set`, and names every other node in `unreached` with what to run there; on another Mac the same command finds the store already moved and rebinds that folder alone. `--dry-run` writes nothing and lists every row with its key (the primary key, else the first unique index), the triggers, the files and resources it would write, the running services and what would refuse.

## 2026-10-23 — `agent materialize` and `init --id` take the bare twelve-hex agent id, and a materialize refused while it wires leaves nothing written

`init --id` and `agent materialize` accept an agent id of twelve hex characters, as well as `prj_` and twelve hex characters and the UUID, and refuse any other form with exit 6 `input`; `agent materialize` checks the id the store holds before it writes anything. Where the wiring `agent materialize` runs after writing the folder's `.env.local` and this node's row is refused - an unreadable `.claude/settings.json`, say - it puts the `.env.local` and the node's row back as they were and removes the folders it made that are left empty, so the refusal leaves no binding behind.

## 2026-10-23 — An agent the store holds is put in a folder on this machine by one command, and its node records the folder

`capabilities agent materialize <id|slug> <folder> [--claude] [--codex]` puts an agent the store holds in a folder on this machine: it registers this machine (`AGENT_NODE_NAME`, `node_unnamed` without it) among the agent's nodes with that folder - a new row kind `mac` on a Mac, else `server`, neither master nor writing - writes `CAPABILITIES_PROJECT_ID` and `CAPABILITIES_PROJECT_ID_ROOT` into the folder's `.env.local`, creating the folder where it is missing, and then binds, wires and builds it as `init --id` does. Before writing anything it refuses an agent the store does not hold (`agent_unknown`), a folder bound to another agent by its env files, an older binding or the environment, or recorded as another agent's folder on this node (`folder_bound`), and an agent that already lives in another folder on this node that is still bound to it (`agent_elsewhere`); a recorded folder that is gone or bound elsewhere is moved. Run again it changes nothing (`changed: false`). `capabilities agent list` answers every agent the store holds with its nodes and the folder it lives in on each, inside a project or outside one. `node list` and every node answer carry `folder`, and `init` gives this node's row the folder it runs in where the row records none and no other agent's row holds that folder here, so an agent already on a machine gets its folder recorded by `init` or `agent materialize` run in it. The manager requires `capabilities-contract` 0.16, whose ledger adds the column.

## 2026-10-23 — The routine index carries the global routines an agent has enabled

## 2026-10-23 — The global layer is the store's once it holds the global rows, and `migrate --retire-connections` retires the config home's connections files

Outside any project, `enable`, `disable` and `inherit` with `--global` write the store's global policy row (`gate` names `store:<schema>.capabilities_policy`) once the store this machine reads holds the global rows, and `list` reads the global gate and counts `machine_connections` through the same global layer - the store's rows, with a config-home file answering only for what the store holds no row of - instead of switching to the store only once no connections file is left. A configured store that does not answer refuses such a write with exit 5. Before the global rows exist, or with no database, the config home's files answer and are written as before.

`migrate --retire-connections` runs on any node, the global master's included: it checks that every connection each `$XDG_CONFIG_HOME/<name>/connections.json` declares is a row of the store with the same fields, grant fields aside, and only then moves those files to `$XDG_CONFIG_HOME/capabilities/retired/connections-<UTC stamp>/<name>/connections.json`, leaving credentials, env and `*.session` files and every other file where they are. It refuses before `global_migrated_at` (`global_not_migrated`), and moves nothing while a connection is missing from the store or differs there (`connections_not_in_store`, exit 6, each one named) or a file cannot be read (`files_unreadable`). The manager requires `capabilities-contract` 0.15, which writes every connection, grant and default pointer to the store once it holds the global rows.

## 2026-10-23 — An agent folder needs no ContextKit binding

A folder bound by `CAPABILITIES_PROJECT_ID` alone is an agent for `build`, `session-start`, `hooks install` and `hooks check`, which work there instead of refusing with `not_contextkit_bound`; only a folder with neither a ContextKit binding nor an id is still refused. Such an agent's context is written to `.capabilities-generated/context.md`, with the same composition and marker as a bound agent's, and every host link points at it: `.claude/rules/CONTEXT.md` for Claude and the root `.contextkit.md` for Codex. Its body root, collaboration mode and onboarding are its row's in `capabilities_agents`, its layers keep their own names in that body root, and it has no global context folder. A ContextKit-bound agent builds, wires and resolves exactly as before.

The agent row gains `body_root` and `collaboration_mode`, which `agent show` answers and `agent set --collaboration-mode ask|direct` writes. The envelope of an agent without a ContextKit binding sits at `<root>/<body_root>/capabilities`, read from its row when the envelope record holds no standing answer and recorded there with the id it was read for; while the store does not answer the last recorded answer stands whatever its age, with none an existing `<root>/capabilities` folder is the envelope, and only without that folder either does the manager refuse with `store_unreachable` (exit 5).

`hooks install` on such an agent retires the standalone capabilities wiring of the hosts it wires and writes a manager-owned block naming the agent's host files into the root `.gitignore`; a `.claude/settings.json` keeps everything besides the manager's hook. `init --id` in a folder without a ContextKit binding wires the agent's hosts as `hooks install` does - the hosts its flags name, Claude when none - instead of the standalone wiring, and plain `init` brings current a host whose hook already runs `capabilities session-start` rather than adding the standalone wiring beside it. `doctor` no longer reports an agent's Codex hook as legacy wiring.

`agent convert` turns a ContextKit-bound agent into one bound by its id alone as one change: preflighted and refusing before it writes anything, it carries `[body] root`, `[collaboration] mode`, `[onboarding]` and the `.contextkit` icon into the agent's row, builds at the new path, repoints and rewires the wired hosts, removes the old output and `.contextkit/`, writes the `.gitignore` block, and in a Git repository leaves the host files and the old binding's files untracked and staged without committing. A `[sources]` entry is refused as a retired setting, as is anything in `.contextkit/` the conversion would lose; a second run changes nothing and says so. The manager requires `capabilities-contract` 0.14, whose ledger adds the row's columns.

## 2026-10-22 — A project is named by CAPABILITIES_PROJECT_ID and its root; its slug is its agent's row

Breaking for a process that relied on `CAPABILITIES_PROJECT_ID` without `CAPABILITIES_PROJECT_ID_ROOT`: an id in the environment without its root binds no folder. It proves in the same transaction that the store resolves this project's identifiers and gate as its files do, each from the same scope, and then records `"records": "store"` in `project.json` in place of `"connections": "store"`. A row that differs, a project row the files lack, or a global row that would change what this project resolves refuses the whole import with exit 6 `import_conflict`, and nothing is written. Its JSON adds `identifiers` and `policy` reports and the two tables, and `previous_mode` answers `files`, `connections` or `store`. A project left at `"connections": "store"` keeps working as it is until it is imported again. In store mode `enable`, `disable` and `inherit` write the project's row (stamping its verified id) or the global row, each for every node, and their `gate` names the store's table. `list`, `context` and `ids <name>` read the store. `doctor` reports a records store it cannot use as drift instead of stopping.

## 2026-10-13 — The running node is named by `AGENT_NODE_NAME` where the machine declares it

The node a store-mode grant is matched against, and the `node` that `capabilities connections import` and `capabilities get <name> grant <id>` answer with, is the value of `AGENT_NODE_NAME` where the machine declares one, and its host name as before where it declares none. A container node that declares its name keeps the grants naming it across redeploys, when its host name, the container id, changes.

## 2026-10-13 — A composed `memory` contribution tells ContextKit the memory is carried

`capabilities context` now composes the line `<!-- contextkit:memory-contribution -->` directly above the context contribution of `memory` whenever that contribution is composed, and nowhere else. `contextkit build` reads that line and leaves out its own projection of the project's memory folder, so a ContextKit-bound project that keeps a `memory/` folder beside its store carries its memory once instead of twice. A `memory` contribution that is missing, unreadable, over its ceiling or empty carries no such line, so ContextKit goes on projecting the folder and the session is never left without memory. Every other capability's block is unchanged. Run `capabilities help` for the details.

## 2026-10-13 — A capability's declared context contribution is composed after its stub, and `memory` is core

A capability may now declare a context contribution in its manifest: `"contribution": {"path": "state/<file>.md", "max_bytes": <n>}`, a Markdown file inside its own state folder in the project envelope and the most UTF-8 bytes to compose from it, from 1 to 32768. Where the capability is enabled, `capabilities context` - `--fragment` and the host modes alike - places that file directly after its stub line. Composing reads the file and nothing else: a contribution that is missing, unreadable, over its ceiling, or declared malformed is replaced by one line saying it is unavailable and pointing to `<name> render`, and every other part of the context, that capability's own included, is composed as before. `capabilities audit`, `source check` and `install` validate the declaration; a malformed one, or one with a key other than `path` and `max_bytes`, fails the manifest check and is refused at install with exit 6 `manifest_invalid`. A capability that declares none is unchanged. `memory` joins the core tier, so its first install from the official catalogue arrives allowed and enabled globally. Run `capabilities help` for the details.

## 2026-10-12 — `connections import` moves a project's connections and grants into its store

`capabilities connections import` writes a project's connections and grants, as its files resolve them, into the contract's two tables in the project's store, proves in the same transaction that the store resolves the same set, and records `"connections": "store"` in its `project.json`. A row the store already holds unchanged is left alone, so a second run changes nothing; a differing row, or a grant of the project the files lack, refuses the whole import with exit 6 `import_conflict` and writes nothing. It stamps the project id, so it refuses where the id is not verified, and it is refused under the read-only switch. In a store-mode project `capabilities get <name> grant <id>` answers the row that applies on this node with `node` and `is_default` added, and `capabilities set` writes connections, grants (which may carry `node` and `is_default`) and `connection.default` into the store, `records.mode` answering `store`. `capabilities doctor` treats a store-mode project's unusable store as drift, and lists under `information`, never as drift, each `agent_id` holding grants that ContextKit's registry (`contextkit_agents`) does not know, or that the registry is absent from the store. A project that was never imported is unchanged. Run `capabilities help` for the details.

## 2026-10-11 — A store behind Supabase's transaction pooler is refused at connect

The manager now uses `capabilities-contract` 0.4.1. A transaction-mode pooler keeps no session between transactions, so the schema binding, prepared statements and notifications a connection relies on are lost through one, and it is not supported. A database setting that points at Supabase's transaction pooler - a host under `pooler.supabase.com` on port 6543 - is refused before anything is sent to it, as `transaction_pooler`, with a hint naming the session pooler: the same host on port 5432. Every other database, the session pooler included, is reached as before.

## 2026-10-09 — `sync-contract` no longer writes a service's records module

`capabilities sync-contract` no longer writes `service/store.py` into a bundled service, and `sync-contract --check` no longer reports a `service_module` drift. A service that reads its settings or documents reads the files itself.

## 2026-10-09 — The database is resolved per project by the shared library; records are files only; no SQLite store

Breaking. The manager no longer decides where a database is. It asks the shared database library, `capabilities-contract` 0.4.0, which the script header now pins exactly (in place of `psycopg2-binary`), and which resolves a project's database through one cascade: the `AGENTKIT_DB_*` keys in the project's `.env.local` and `.env`, then the process environment, then the machine's store setting file `$XDG_CONFIG_HOME/agentkit/store.json`. Removed, with no compatibility path: `AGENTKIT_STORE_URL`, `CAPABILITIES_STORE_URL` and `CAPABILITIES_STORE_PASSWORD` as overrides, the former pair `$XDG_CONFIG_HOME/capabilities/store.json` and `credentials.env` (neither read, written nor removed), the local SQLite store and its default `~/.local/state/capabilities/store.db`, and the records-in-the-database mode: a `project.json` declaring `"store": "db"` is refused with exit 6 `bad_store_mode`, one declaring `"store": "files"` keeps working, and no verb creates a table. `store show [--project PATH]` reports every level for the current project or the one named - what each holds with its secrets redacted, the files or variables it came from, and which is in force - in a new shape `{configured, project, in_force, setting, error, levels}`; `store doctor [--project PATH]` probes the database in force, whichever level answered, with the same TLS, plain-text-refused and schema checks, and still exits 3 `no_store_setting` when no level answers. `store set` and `store unset` write only the machine file, which `store set` proves the library reads before replacing it. `relabel` writes only the project identity and its answer drops `store_registry`. `dev run` hands its child no store variable. `path store` is gone. Run `capabilities help` for the details.

## 2026-10-09 — Install, update and release migrate a capability's tables

`capabilities install`, `capabilities update` and the release that reconciles this machine run `<name> migrate` once the payload is in place, when its manifest declares `tables`, so its tables in the machine's store reach its code where the code arrives. The result carries `migrate`: `{ok, applied, version}`, or `{ok: false, exit, error}` for a refusal - no store configured, the store unreachable or busy, the capability quarantined - which leaves the payload installed; the capability's first call then migrates on its own.

## 2026-10-08 — The store setting moves to the family's file

`capabilities store set` now writes the machine's store setting to `$XDG_CONFIG_HOME/agentkit/store.json` (`~/.config/agentkit/store.json` when `XDG_CONFIG_HOME` is unset): one `agentkit.store.v1` file, the password inside it, written whole through a temporary file and a rename at mode 0600, naming `db_schema` only when `--schema` is given. It is the file ContextKit and AgentKit share, and its format is SHEBANG.md's "The store setting". It refuses to replace a file of a format version it does not know (exit 6 `store_setting_too_new`), and `--sslmode disable` is admitted for a local host - a Unix socket directory, `localhost` or a loopback address - and refused elsewhere as before. While that file is absent the setting is read from the files `store set` wrote before, `$XDG_CONFIG_HOME/capabilities/store.json` and the password in `credentials.env`, which `store set` leaves as they are and `store unset` removes with the new file. `store show` adds `path`, the file's absolute path, and `exists`; a value read from the old files reports the source `legacy`. `AGENTKIT_STORE_URL` overrides the setting ahead of `CAPABILITIES_STORE_URL`, and `in_force` and `overridden_by` name whichever is in force. `store doctor` skips the plain-text-refused check for a store on this machine (`skipped: true`), and passes a local store set to `sslmode disable` on a working connection without TLS. Run `capabilities help` for the details.

## 2026-10-07 — The store setting names its schema, the doctor proves it, and `store unset`

`capabilities store set --schema NAME` records the schema inside the store's database that tools bind to, writing a `capabilities.store.v2` setting with the name in `db_schema`; the name is a lowercase identifier and `public`, `information_schema` and `pg_*` are refused (exit 6 `bad_schema_name`). Without `--schema` the setting is written as `capabilities.store.v1`, as before, and binds `agentkit`. `capabilities store show` reports `db_schema` with its source, `default` when the setting names none. `capabilities store doctor` also proves the role may use that schema - `USAGE` and `CREATE` on it when it exists, `CREATE` on the database when it does not yet - under `checks.schema`, and reports `db_schema`; it exits 7 when the role may not. `capabilities store unset` removes the setting and its password, keeping every other key in the manager's credentials tier, and is refused under the read-only switch. A v1 setting keeps working unchanged. Run `capabilities help` for the details.

## 2026-10-04 — The machine's store setting, the one store pointer

`capabilities store set` records the Postgres this machine's store lives in: host, port, database, user, an `sslmode` of `require`, `verify-ca` or `verify-full` (anything weaker is refused) and an optional root certificate in `$XDG_CONFIG_HOME/capabilities/store.json`, and the password, taken from stdin, a file or a named environment variable and never from argv, in `$XDG_CONFIG_HOME/capabilities/credentials.env` at mode 0600. ## 2026-10-03 — A machine ceiling above both policy scopes, and machine services declared

Each installed capability is `allowed` or `quarantined` on this machine, in `$XDG_CONFIG_HOME/capabilities/machine.json`, which only the manager writes. A capability with no entry is allowed, so every capability installed before this release stays allowed and nothing is migrated.
