# capabilities — change log

## 2026-10-17 — The migration meets a whole machine: second checkouts verify only, a connection can be renamed for one agent, and the discard weighs every root nearby

`migrate --global` brings the contract's tables to this code's version before it plans (dry run and apply), naming the steps under `tables_upgraded`, so a store whose tables a released manager left at 1.1 no longer crashes it, and its `gate_flips` count only agents that read the same database. A second checkout of an agent - a linked git worktree of its main checkout, a root other than the one its open migration started in, or a root whose files are behind another root of the same id that already keeps the records in the store - only verifies: it names its main checkout and differences under `second_checkout`, never writes, removes or freezes the agent's rows, and until the agent has moved refuses `second_checkout` naming the main checkout. A connection whose stored spec differs from an agent's files can be answered `{"rename": "<name>"}`: the agent's own is written under that name and its grants, default and settings `connection` follow it, the stored one left to the others; answering `store` makes the agent adopt the stored spec, so verify passes and the agent is not left frozen. `migrate --discard` refuses without `AGENT_NODE_NAME` (`node_unnamed`) and on the master node of any agent it weighs (`master_node`), and weighs every root holding an envelope or a ContextKit binding below the folders the listed roots sit in and below each `--root`, refusing while one has not moved or has no id. `migrate --report` counts historical notes (assets/, memory/, snapshots/, change logs) apart from live readers under `historical_notes`. `capabilities list` counts machine connections from the store once the config home holds no connections file and the global rows exist. Run `capabilities help` for the details.

## 2026-10-16 — Install writes no policy file, dev sessions get a schema of their own, and the migration closes its carry-overs

`install` writes no policy file anywhere: a core capability's arrival enable is the store's global policy row (`global_policy {enabled, gate: store:<schema>.capabilities_policy}`) where a database resolves, kept where the store holds one already, and otherwise reported as `{enabled, pending, reason, hint}` with nothing written. `dev exec` and `dev run` give a session the machine's database bound to a schema of its own, `dev_<session>`, through `AGENTKIT_DB_*` and `AGENTKIT_DB_SCHEMA` (which then cannot be inherited), with `AGENT_NODE_NAME`; the session creates that schema marked as its own before the lane reaches it and drops it when the session ends by `finish`, `stop` or `gc`, never a schema that was already there or does not carry its mark, and names it under `database_schema`; for a project that reads its records from the store, `dev run` projects the capability's rows (the agent's registry row and nodes, its own and the global policy, connections, grants, identifiers and settings) into that schema instead of writing a temporary config home, and names `database_schema` and `projected_rows` in its diagnostic; without a database the lane is as before. `migrate --global` sets `global_migrated_at` only once every global row and settings document is written, so a run that stopped writes them again; an agent's migration reads its files over the global rows rather than over this machine's config home, so an agent made after `--discard` migrates cleanly; a write refused during an open migration refuses before any file (`capabilities/.gitignore` included) is written; `init` names the store's policy table as the gate of a store-mode or moved agent, and where no store is configured or reachable completes its offline part, while any other refusal of the project's records, a malformed project.json among them, stops it as before; the migration moves automations' `[agents.workers]` into harness profiles. Run `capabilities help` for the details.

## 2026-10-16 — `capabilities migrate` moves an agent's file-held configuration into the store

New verb `capabilities migrate [--dry-run|--apply] [--answers FILE]`, run in an agent on its master node (`AGENT_NODE_NAME`), moves its connections, grants and default pointer, identifiers and gate into rows naming it, each capability's project settings home into settings rows - `capabilities/tasks/conveyor.toml` folded in as the tasks settings' `escalation` table, and `capabilities/slack/policy.json` merged into the slack settings' allow-list, an entry both hold keeping the service's own and each user or channel only one holds, and each mode the two disagree on, asked as a question the dry run lists and the write waits for - and through each capability's new `migrate files` verb what the capability keeps of its own (automations definitions, profile and worker files, telegram's old worker settings, agentrooms' agents map, deployment placement as policy rows naming each target's node). The dry run, the default, writes nothing and lists what each part would write, every row the store holds differently, host paths in settings values, files that differ from their commit, other roots of the agent, one node per deployment target, and every question code cannot answer, each naming where its answer goes in the answers file. `--apply` refuses before writing without a database, without or with another node (`node_unnamed`, `node_mismatch`, `not_master`), before the global rows (`global_not_migrated`), with an older payload (`payload_outdated`) or with a question open (`question_open`); it registers the agent and its master on the first run, sets `migrating_since`, archives what git does not hold, stops the agent's launchd agents and pauses its services, writes, reads everything back and compares it both ways with the files (exit 7 `verify_failed`), and finalizes once every target node is registered (`target_node_unregistered` otherwise): `migrated_at`, `"records": "store"`, the files removed and the services resumed. A journal under `$XDG_STATE_HOME/capabilities/migrate/<agent>/` resumes an interrupted run; a second run changes nothing. `capabilities migrate --global [--apply]` writes the config home's gate, identifiers, connections, grants (`allow_write` only), default pointer and global settings as the global rows, listing every agent whose gate would flip, and sets `global_migrated_at`; `--discard` deletes the config home's record files without reading them once the global rows exist and no agent here still reads them; `--report` lists what remains on the machine and why. The import verbs keep working. Run `capabilities help` for the details.

## 2026-10-16 — The manager reads and writes a moved agent's records and settings in the store

For an agent whose `capabilities_agents` row has `migrated_at`, `capabilities get`, `set`, `enable`, `disable` and `inherit` read and write rows only, with the node authority and migration freeze of the records adapter: off the master a shared write is refused as `node_read_only`, a node allowed to write writes rows marked with its node, and during an open migration every write is `agent_migrating`. `capabilities set <cap> setting <key>` writes `<key>` as one top-level key of the capability's settings document and names the settings table as its source; `connection.default` still writes the grants. A store that cannot be reached while the records are opened is exit 5. Every other project behaves as before. Run `capabilities help` for the details.

## 2026-10-16 — The manager keeps the agent registry and the agent's nodes, and reads the project id from project.json alone

The store gains three kernel tables, migrated in the contract's ledger with the record tables: `capabilities_agents` (the agent registry, keyed by the project id, with name, description, a PNG icon and its SHA-256, onboarding status and routine, and the migration markers), `capabilities_agent_nodes` (an agent's nodes: kind `mac` or `server`, address, target, whether it is the master - at most one per agent - and whether it may write) and `capabilities_global` (one row). Where ContextKit's `contextkit_agents` table exists in the same schema, its rows are copied into `capabilities_agents` once, when the table is created. New verbs write them for the project a call runs in: `capabilities agent show [--icon-out PATH]`, `capabilities agent set` (`--name`, `--description`, `--icon PNG` or `--no-icon`, `--onboarding-status`, `--onboarding-routine`), and `capabilities node list|add|set|remove`; `add` and `set` refuse a second master with exit 6 `master_exists`, and the writes exit 4 under the read-only switch. `capabilities init` registers the agent row when a database resolves for the project and reports it under `agent`, never failing over it. The project id is read from `capabilities/project.json` alone and ContextKit is never asked for it, so `project_identity` answers the states `declared`, `undeclared`, `handed` and `mismatch` (a handed-down id project.json contradicts, named in `handed_id`) with `id` and `project_json_id`; it keeps `bound` (whether `.contextkit/config.toml` is present) and `contextkit_id` (the project's id where bound, else null), so a capability stamped with an earlier contract keeps resolving and writing as before. Where project.json declares no id and `.contextkit/config.toml` holds one under `[identity]`, the manager copies it into project.json once; `init` takes that id too, and otherwise mints one, also for a bound project whose binding holds none. The identity record under `$XDG_CACHE_HOME/capabilities/identity/` is no longer read or written. Run `capabilities help` for the details.

## 2026-10-14 — Without `CAPABILITIES_BIN`, the manager links beside its own link

A call that does not set `CAPABILITIES_BIN` now links, unlinks and looks for capability links in the directory that already holds the manager's own `capabilities` link - searched on `PATH`, then in `~/.local/bin` and `~/bin` - rather than choosing again from that call's `PATH`. An install, self-update or `doctor` run from an environment that lacks the shell's `CAPABILITIES_BIN`, such as a service, therefore uses the same directory as every other call on the machine. A machine an older manager left with its own link in two directories gets every capability link in both, and `self-update` relinks the second manager link to the new release as well (named under a new `also_relinked` in its JSON), so whichever one a call's `PATH` reaches runs the current manager. Where no such link exists the choice is as before: the first of `~/.local/bin` and `~/bin` that exists and is on `PATH`. `CAPABILITIES_BIN`, when set, still decides. Run `capabilities help` for the details.

## 2026-10-14 — `connections import` writes only the connections a project uses

`capabilities connections import` no longer writes every connection the workstation's config home could lend the project. It writes each connection the project's envelope declares, as before, and a config-home connection only where the capability is enabled for the project and the project may use that connection or points its default at it; grants follow the connections written. A config-home connection the project merely could resolve stays out of the store, and the JSON names it under a new `skipped` {<name> [<id>]}. Once the project uses one, running the import again from its files writes it, and a project already in store mode writes it with `capabilities set <name> connection <id> <spec>` and grants it with `capabilities set <name> grant <id> '{"enabled": true}'`. Rows already in the store are never removed, and one an earlier import wrote that still matches the files is reported unchanged. What a project uses resolves from the store as before. Run `capabilities help` for the details.

## 2026-10-13 — A manifest's `connections` and `settings` declarations are validated

Audit, source check and install now check a manifest's `connections` (`null`, or `fields`, `setup` and `link`) and `settings` (`null`, or `homes` and `keys`) wherever they validate a manifest: every field has a `key`, a `label`, a `help` and a known `type`, an enum its `choices`, a secret's `env` template its `{ID}`; every link method an argv carrying `--events`; every settings home one scope of `project`, `global` or `machine`, a format of `json` or `toml` and a relative path inside the capability's folder; every settings key a scope that has a home and an `apply` of `next_call`, `reload` or `restart`, and no secret. A manifest without them still validates.

## 2026-10-13 — `enable`, `disable` and `inherit` write the policy row for one node with `--node`

`capabilities enable|disable|inherit <name> --project|--global --node <node>` writes, or removes, the store's policy row naming that node (the name the node gives itself: `AGENT_NODE_NAME`, else its host name), and the result carries `node`; without `--node` they write the row for every node as before. Only the project's row naming a node places a capability's bundled service on that node, so this is how a service is turned on or off for one node. Files carry no node: in files mode, or outside a project, `--node` exits 6 `node_requires_store`, with a hint to move the project's records into its store with `capabilities connections import`. `disable --deny` takes no `--node`.


## 2026-10-13 — `connections import` moves a project's identifiers and gate into its store as well, under `"records": "store"`

`capabilities connections import` now also writes each scope's identifiers and policy entries into `capabilities_identifiers` and `capabilities_policy`: the envelope's under the project id, and the config home's as global rows, which every project reading that store shares. It proves in the same transaction that the store resolves this project's identifiers and gate as its files do, each from the same scope, and then records `"records": "store"` in `project.json` in place of `"connections": "store"`. A row that differs, a project row the files lack, or a global row that would change what this project resolves refuses the whole import with exit 6 `import_conflict`, and nothing is written. Its JSON adds `identifiers` and `policy` reports and the two tables, and `previous_mode` answers `files`, `connections` or `store`. A project left at `"connections": "store"` keeps working as it is until it is imported again. In store mode `enable`, `disable` and `inherit` write the project's row (stamping its verified id) or the global row, each for every node, and their `gate` names the store's table. `list`, `context` and `ids <name>` read the store. `doctor` reports a records store it cannot use as drift instead of stopping.

## 2026-10-13 — The running node is named by `AGENT_NODE_NAME` where the machine declares it

The node a store-mode grant is matched against, and the `node` that `capabilities connections import` and `capabilities get <name> grant <id>` answer with, is the value of `AGENT_NODE_NAME` where the machine declares one, and its host name as before where it declares none. A container node that declares its name keeps the grants naming it across redeploys, when its host name, the container id, changes.

## 2026-10-13 — A composed `memory` contribution tells ContextKit the memory is carried

`capabilities context` now composes the line `<!-- contextkit:memory-contribution -->` directly above the context contribution of `memory` whenever that contribution is composed, and nowhere else. `contextkit build` reads that line and leaves out its own projection of the project's memory folder, so a ContextKit-bound project that keeps a `memory/` folder beside its store carries its memory once instead of twice. A `memory` contribution that is missing, unreadable, over its ceiling or empty carries no such line, so ContextKit goes on projecting the folder and the session is never left without memory. Every other capability's block is unchanged. Run `capabilities help` for the details.

## 2026-10-13 — A capability's declared context contribution is composed after its stub, and `memory` is core

A capability may now declare a context contribution in its manifest: `"contribution": {"path": "state/<file>.md", "max_bytes": <n>}`, a Markdown file inside its own state folder in the project envelope and the most UTF-8 bytes to compose from it, from 1 to 32768. Where the capability is enabled, `capabilities context` - `--fragment` and the host modes alike - places that file directly after its stub line. Composing reads the file and nothing else: a contribution that is missing, unreadable, over its ceiling, or declared malformed is replaced by one line saying it is unavailable and pointing to `<name> render`, and every other part of the context, that capability's own included, is composed as before. `capabilities audit`, `source check` and `install` validate the declaration; a malformed one, or one with a key other than `path` and `max_bytes`, fails the manifest check and is refused at install with exit 6 `manifest_invalid`. A capability that declares none is unchanged. `memory` joins the core tier, so its first install from the official catalogue arrives allowed and enabled globally. Run `capabilities help` for the details.

## 2026-10-12 — `connections import` moves a project's connections and grants into its store

`capabilities connections import` writes a project's connections and grants, as its files resolve them, into the contract's two tables in the project's store, proves in the same transaction that the store resolves the same set, and records `"connections": "store"` in its `project.json`. A row the store already holds unchanged is left alone, so a second run changes nothing; a differing row, or a grant of the project the files lack, refuses the whole import with exit 6 `import_conflict` and writes nothing. It stamps the project id, so it refuses where the id is not verified, and it is refused under the read-only switch. In a store-mode project `capabilities get <name> grant <id>` answers the row that applies on this node with `node` and `is_default` added, and `capabilities set` writes connections, grants (which may carry `node` and `is_default`) and `connection.default` into the store, `records.mode` answering `store`. `capabilities doctor` treats a store-mode project's unusable store as drift, and lists under `information`, never as drift, each `agent_id` holding grants that ContextKit's registry (`contextkit_agents`) does not know, or that the registry is absent from the store. A project that was never imported is unchanged. Run `capabilities help` for the details.

## 2026-10-11 — A store behind Supabase's transaction pooler is refused at connect

The manager now uses `capabilities-contract` 0.4.1. A transaction-mode pooler keeps no session between transactions, so the schema binding, prepared statements and notifications a connection relies on are lost through one, and it is not supported. A database setting that points at Supabase's transaction pooler - a host under `pooler.supabase.com` on port 6543 - is refused before anything is sent to it, as `transaction_pooler`, with a hint naming the session pooler: the same host on port 5432. Every other database, the session pooler included, is reached as before.

## 2026-10-09 — `sync-contract` no longer writes a service's records module

`capabilities sync-contract` no longer writes `service/store.py` into a bundled service, and `sync-contract --check` no longer reports a `service_module` drift. A service that reads its settings or documents reads the files itself.

## 2026-10-09 — The database is resolved per project by the shared library; records are files only; no SQLite store

Breaking. The manager no longer decides where a database is. It asks the shared database library, `capabilities-contract` 0.4.0, which the script header now pins exactly (in place of `psycopg2-binary`), and which resolves a project's database through one cascade: the `AGENTKIT_DB_*` keys in the project's `.env.local` and `.env`, then the process environment, then the machine's store setting file `$XDG_CONFIG_HOME/agentkit/store.json`. Removed, with no compatibility path: `AGENTKIT_STORE_URL`, `CAPABILITIES_STORE_URL` and `CAPABILITIES_STORE_PASSWORD` as overrides, the former pair `$XDG_CONFIG_HOME/capabilities/store.json` and `credentials.env` (neither read, written nor removed), the local SQLite store and its default `~/.local/state/capabilities/store.db`, and the records-in-the-database mode: a `project.json` declaring `"store": "db"` is refused with exit 6 `bad_store_mode`, one declaring `"store": "files"` keeps working, and no verb creates a table. `store show [--project PATH]` reports every level for the current project or the one named - what each holds with its secrets redacted, the files or variables it came from, and which is in force - in a new shape `{configured, project, in_force, setting, error, levels}`; `store doctor [--project PATH]` probes the database in force, whichever level answered, with the same TLS, plain-text-refused and schema checks, and still exits 3 `no_store_setting` when no level answers. `store set` and `store unset` write only the machine file, which `store set` proves the library reads before replacing it. `relabel` writes only the project identity and its answer drops `store_registry`. `dev run` hands its child no store variable. `path store` is gone. Run `capabilities help` for the details.

## 2026-10-09 — Install, update and release migrate a capability's tables

`capabilities install`, `capabilities update` and the release that reconciles this machine run `<name> migrate` once the payload is in place, when its manifest declares `tables`, so its tables in the machine's store reach its code where the code arrives. The result carries `migrate`: `{ok, applied, version}`, or `{ok: false, exit, error}` for a refusal - no store configured, the store unreachable or busy, the capability quarantined - which leaves the payload installed; the capability's first call then migrates on its own.

## 2026-10-08 — The store setting moves to the family's file

`capabilities store set` now writes the machine's store setting to `$XDG_CONFIG_HOME/agentkit/store.json` (`~/.config/agentkit/store.json` when `XDG_CONFIG_HOME` is unset): one `agentkit.store.v1` file, the password inside it, written whole through a temporary file and a rename at mode 0600, naming `db_schema` only when `--schema` is given. It is the file ContextKit and AgentKit share, and its format is SHEBANG.md's "The store setting". It refuses to replace a file of a format version it does not know (exit 6 `store_setting_too_new`), and `--sslmode disable` is admitted for a local host - a Unix socket directory, `localhost` or a loopback address - and refused elsewhere as before. While that file is absent the setting is read from the files `store set` wrote before, `$XDG_CONFIG_HOME/capabilities/store.json` and the password in `credentials.env`, which `store set` leaves as they are and `store unset` removes with the new file. `store show` adds `path`, the file's absolute path, and `exists`; a value read from the old files reports the source `legacy`. `AGENTKIT_STORE_URL` overrides the setting ahead of `CAPABILITIES_STORE_URL`, and `in_force` and `overridden_by` name whichever is in force. `store doctor` skips the plain-text-refused check for a store on this machine (`skipped: true`), and passes a local store set to `sslmode disable` on a working connection without TLS. Run `capabilities help` for the details.

## 2026-10-07 — The store setting names its schema, the doctor proves it, and `store unset`

`capabilities store set --schema NAME` records the schema inside the store's database that tools bind to, writing a `capabilities.store.v2` setting with the name in `db_schema`; the name is a lowercase identifier and `public`, `information_schema` and `pg_*` are refused (exit 6 `bad_schema_name`). Without `--schema` the setting is written as `capabilities.store.v1`, as before, and binds `agentkit`. `capabilities store show` reports `db_schema` with its source, `default` when the setting names none. `capabilities store doctor` also proves the role may use that schema - `USAGE` and `CREATE` on it when it exists, `CREATE` on the database when it does not yet - under `checks.schema`, and reports `db_schema`; it exits 7 when the role may not. `capabilities store unset` removes the setting and its password, keeping every other key in the manager's credentials tier, and is refused under the read-only switch. A v1 setting keeps working unchanged. Run `capabilities help` for the details.

## 2026-10-05 — A core capability arrives allowed and enabled globally

`capabilities install <name>` of a core capability (`tier` "core" in `list`) new to this machine, from the official catalogue, now leaves it `allowed` on the machine and writes an explicit global enable record, at the global scope `capabilities enable <name> --global` writes from the same directory; the JSON carries `global_policy {enabled, gate}`. A global entry the user already holds for it is kept and nothing is written. Under `CAPABILITIES_READ_ONLY` a core capability arrives as a standard one does, and an arrival whose global record cannot be written fails with nothing left behind. A standard capability, and a core name installed with `--from` or `--source`, still arrives quarantined with no policy written. Reinstalling or updating an installed capability changes neither its machine state nor its policy, and a bundled service still needs an explicit project enable. Run `capabilities help` for the details.

## 2026-10-04 — A capability's machine reads are validated wherever it is

`capabilities audit`, `source check` and `install` validate a capability's `MACHINE_READS` declaration: a tuple of strings, each a verb the capability's `help` names and none of them in its `WRITE_VERBS`. Audit and source check report a bad declaration as a `connections/machine-reads` failure, and install refuses it with exit 6 `machine_reads_invalid` before anything is installed. A capability that declares none is validated as before.

## 2026-10-04 — The machine's store setting, the one store pointer

`capabilities store set` records the Postgres this machine's store lives in: host, port, database, user, an `sslmode` of `require`, `verify-ca` or `verify-full` (anything weaker is refused) and an optional root certificate in `$XDG_CONFIG_HOME/capabilities/store.json`, and the password, taken from stdin, a file or a named environment variable and never from argv, in `$XDG_CONFIG_HOME/capabilities/credentials.env` at mode 0600. It is refused under the read-only switch. `capabilities store show` reports the setting and where each value came from without the password, and `capabilities store doctor` proves a TLS connection works, with the server version and the negotiated TLS, and fails when the server accepts plain text. The manager's own records in database mode now resolve their store from the setting; `CAPABILITIES_STORE_URL` still overrides it, and a machine with neither behaves as before. The manager now carries the Postgres driver. Run `capabilities help` for the details.

## 2026-10-03 — A machine ceiling above both policy scopes, and machine services declared

Each installed capability is `allowed` or `quarantined` on this machine, in `$XDG_CONFIG_HOME/capabilities/machine.json`, which only the manager writes. A capability with no entry is allowed, so every capability installed before this release stays allowed and nothing is migrated. Quarantined is effective-disabled in every project and outside any, whatever project or global policy says. `capabilities install <name>` of a capability new to the machine arrives quarantined, and `--allow` installs it allowed; reinstalling or updating keeps the state, and uninstalling drops it. `capabilities allow <name>` and `capabilities quarantine <name>` set it and answer `{capability, machine, changed}`, exit 3 when the capability is not installed and exit 4 under the read-only switch. Every `list` row gains `machine` and `machine_connections`, and a quarantined row reads effective `disabled` with source `machine`, so `inventory` and the generated context leave it out. Enabling a quarantined capability writes the entry and warns that it stays disabled. `dev install` installs the session payload allowed in the session's own isolated machine. The manifest's optional `service.machine` declaration is validated at install, audit, source check and verify, and `audit` also proves the ceiling refuses a capability enabled at both scopes. Run `capabilities help` for the details.

## 2026-10-02 — Check for updates without applying them

`capabilities update --check [<name>]` and `capabilities self-update --check` report the installed and the available payload or release, and whether an update is available, while installing, staging and switching nothing. `capabilities help` states their JSON and exit codes, and that every `search` row carries `installed`.

## 2026-10-02 — Print what changed since the installed version

`capabilities changelog` prints the change log of a capability, of the manager, or of the contract, by default only what changed since the installed version. Run `capabilities help` for its options.
