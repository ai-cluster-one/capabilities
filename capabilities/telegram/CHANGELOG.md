# telegram — change log

## 2026-10-13 — `telegram` declares what a person is asked for, and writes it through the contract

`telegram manifest` now declares a connection's fields under `connections.fields` (`api_id`, `secret_env`, `session`, `expected_account_id`, `gemini_secret_env`, `openai_secret_env`), each with its label, help, type, whether it is required and whether it is a secret, and `telegram connection add <id>` writes one connection from them: non-secret fields on argv with `--field KEY=VALUE` or in a JSON object on stdin with `--stdin`, a secret only on stdin, written to the scope's `.env.local` or `credentials.env` under its own env key. `telegram connection remove <id>` takes it out again with the secrets it wrote. The machine's prerequisites (`DEEPGRAM_API_KEY`) are declared under `connections.setup`, and `telegram setup` reports them while `telegram setup set` writes them to `credentials.env`, a secret only from stdin. Its settings (project `service/settings.json`, global `service/settings.json`) are declared under `settings`, with the keys a panel shows as controls, and `telegram settings` reads every document whole while `settings get|set|unset|put` write one key or one document, checked as telegram reads it. `telegram login --events` and `telegram login --phone --events` speak JSON lines on stdout - `qr` with its expiry, a new one each time one expires for up to five minutes, `phone_needed`, `code_needed`, `password_needed` with the account's hint, then `done` or `error` - and read each answer as one line on stdin, so no terminal is needed; both are declared under `connections.link`. Without `--events`, `login` renders its QR on stderr and asks for the two-step password through the terminal exactly as before. Bare `telegram help` ends with a section rendered from these declarations. Nothing else changes.

## 2026-10-13 — `telegram login` shows the QR by default; the phone number and code move behind `--phone`

Breaking for anyone who scripted the phone login. `telegram login` with no method flag now logs in by QR code, as `telegram login --qr` did: it renders the QR on stderr, waits for an already-authorized Telegram app to approve it, and asks for the 2FA password when one is set. The phone-and-code login is now `telegram login --phone`, which prompts for the number, or `telegram login --phone NUMBER`, which takes it, and then asks for the code and the 2FA password as before. `--qr` is still accepted and names the default; `--qr` and `--phone` together are refused. `help`, `deviations.md` and the not-logged-in hints of `doctor` and the other commands name the QR first and the phone second. The session file each way writes is unchanged.

## 2026-10-13 — A reply gate decision on claude runs without thinking, reads its chat's cached prompt, and asks for no session title

The schema a gate decision is held to no longer names the batch's message ids: it is the same for every run in a chat, narrowed only to the chat's allowed reactions. The harness carries that schema at the head of the prompt prefix it caches, so a schema naming the batch made every run's prefix new and no run read the cache; a chat's later runs now read the earlier run's cached prefix. A decision whose target is not a message of the batch is still read as `ignore`, as before. On Haiku 5.5, claude's CLI drops the gate profile's thinking off, because its own model table marks that model as refusing it, and the model then thought before every decision; `telegram-gate-claude` now sets the CLI's `CLAUDE_CODE_MODEL_CAPABILITIES` to take that mark off Haiku 5.5, so thinking off reaches it. The setting is undocumented, and a CLI that stops reading it brings adaptive thinking back and nothing else. The profile also names its session `telegram-gate`, so the CLI no longer sends a session-title request beside each decision. Nothing in the settings, the record or the decisions changes.

## 2026-10-13 — Groups can switch each trigger off, and a reply gate can decide whether a conversation needs the assistant

A group's `triggers` lists which mechanical triggers start a turn - `username` (the mention flag and `@username`), `alias`, `reply` - and without it all three do, as before. A group's `gate` block (`enabled`, `mode` `shadow` or `live`, `brief`, `context_messages`, `context_chars`, `max_batch`, `model`, `effort`) switches on the reply gate: messages no enabled trigger admits collect per channel, the channel's debounce restarts on each, and one light harness turn reads the batch and decides to ignore it, react to one message with one of the chat's allowed reactions, or reply to one message. `live` acts - the service sets the reaction, or queues a turn for the target that is told why it was woken and shows typing until it answers - and `shadow`, the default once the gate is on, logs and acts on nothing. Every run logs one `gate` record. The gate runs on the vendor of the channel's profile through the bundled `telegram-gate-claude` (`haiku`) and `telegram-gate-codex` (`luna`) profiles: its own system prompt, no tools, settings, hooks, skills or MCP, one turn, an answer held to a schema, no session saved, from an empty directory under the service's state; a codex gate run uses its own codex home, `$XDG_STATE_HOME/telegram/gate-codex-home` (or `TELEGRAM_GATE_CODEX_HOME`), which needs one `codex login` by the operator. Catch-up never runs the gate, and configured agents never enter it. The shipped `context.md` now tells a turn that an empty answer is silence and valid, and that a reaction answers a turn the gate woke. Nothing changes for a group without `triggers` or `gate`.

## 2026-10-12 — Rooms name the profile their turns run on; the worker settings go

Breaking. A room names a harness profile instead of a worker: a turn runs on the channel's `/set profile`, then `allowed_groups.<id>.topics.<topic>.profile`, then `allowed_groups.<id>.profile` or `allowed_users.<id>.profile`, then `defaults.profile` (the environment's `TELEGRAM_SERVICE_PROFILE` in its place), else `stub`; a call's task and the post-call summary run on `defaults.voice_agent.profile`, then that default. `worker` and `workers` at every position, a channel register row's `worker`, `model` and `workers`, and the environment's `TELEGRAM_SERVICE_WORKER` and `TG_WORKER` are no longer read: `service start` and `service run` exit 6 `profiles_migration_required` and a reload is refused while any is present, naming `telegram service migrate-profiles`, which reports the moves and with `--apply` (service stopped) writes one project profile per distinct worker and settings, named from the values, including a block for a worker its position does not run, rewrites the settings, the register and the job rows still to run, and prints the `TELEGRAM_SERVICE_PROFILE` value that replaces a set `TG_WORKER`; the deploy declaration names `TELEGRAM_SERVICE_PROFILE` in place of `TG_WORKER`. In chat, `/profiles` lists the profiles and which one the chat runs on (gated as `/status`), and `/set profile <name|default>` chooses one (gated as `/set`); `/set worker`, `/set model`, `/set effort|reasoning|speed|service-tier` and `/set <worker>.<field>` answer `nope:` pointing at both, and `/status` shows the profile in place of the worker lines. A job carries its profile in a new nullable `profile` column (store step `0004-job-profile`, schema 1.1); `jobs register` takes `--profile` and refuses `--engine` and `--model`, a worker's is pinned to the profile its turn runs on, and a row without one runs on `telegram-<engine>` with its model as before. A worker is told its requester's role in `TELEGRAM_AUTHORIZED_REQUESTER_ROLE`, so `telegram profiles save` inside a turn works for a role the control gate admits to `/set`. Start, reload and `service doctor` resolve and fit every profile the settings name. The seed settings name `"profile": "stub"`.

## 2026-10-12 — Every worker turn runs through callva-harness-runner

Dialogue replies, delegated jobs, call tasks, the post-call summary and the `service doctor` probe run through callva-harness-runner 0.10.0 on `telegram-<worker>`, with the worker's settings laid over it: `model`, claude's `effort` and `context`, codex's `reasoning_effort` (as `effort`) and `service_tier` (`fast` as `priority`). No setting, register field, job column or flag changes. What a room sees changes where the runner differs: a worker whose `model` is unset runs on its profile's model (`opus` for claude, the newest `sol` model for codex) rather than the CLI's own default; a delegated job ends at the profile's one-day `timeout_seconds` where it had no deadline; a claude or codex CLI older than the runner's tested range is refused and a newer one runs with a warning in the log; codex runs through its app-server, so no git-repository check applies and trusting the project for its hooks also loads its `.codex/config.toml`. `service start` and `service run` exit 6 `profile_refused`, and a reload is refused, when a worker the settings reach has a profile that does not resolve or fit; `service doctor` reports each pair's profile, layer and version, and `incompatible_harness`. The daemon's environment carries the runner's SDKs (about 0.5 GB more on disk, about 55 MB more resident); `service start` resolves it before launching the daemon. The CLI's environment is unchanged.

## 2026-10-12 — Harness profiles in the store, and `telegram profiles list|show|save`

Telegram now keeps harness profiles: callva-harness-runner profiles in the project's store, named `telegram-<something>`, resolved to the project's version, then the global one, then the two the bundle ships, `telegram-claude` (claude on `opus`) and `telegram-codex` (codex on the `sol` family). `telegram profiles list` and `show` report each with its layer, version, settings, rights and fit; `telegram profiles save` writes a new version at the project's scope only, refuses a bundled or global name, a profile the runner or telegram's fit refuses and a `${` value, takes `--base` and exits 6 `conflict` when overtaken, and from a worker saves only for a requester whose role may `/set`. `telegram migrate` applies the runner's `harness_profiles` table under its ledger `harness` before the job register's tables, the daemon does the same when it opens the register, and `migrate status` reports both, the runner's under `harness`. The runner is pinned in `service/profiles.py` (0.10.0), not in the CLI. How a room's turns run is unchanged.

## 2026-10-11 — A store behind Supabase's transaction pooler is refused at connect

`telegram` now uses `capabilities-contract` 0.4.1. A transaction-mode pooler keeps no session between transactions, so the schema binding, prepared statements and notifications a connection relies on are lost through one, and it is not supported. A database setting that points at Supabase's transaction pooler - a host under `pooler.supabase.com` on port 6543 - is refused before anything is sent to it, as `transaction_pooler`, with a hint naming the session pooler: the same host on port 5432. Every other database, the session pooler included, is reached as before.

## 2026-10-11 — The service reopens the job register's store connection after losing it

When the store or the network ends the job register's database connection while the Telegram session stays up, the service's next job tick opens a new connection and the queue keeps draining, rather than retrying the dead connection every tick until the Telegram session ends or the service restarts. The log says `jobs: lost the store connection, reopening it on the next tick` for it, and a session that loses its connection to Telegram is logged as `session lost its connection to Telegram` rather than as likely protocol drift.

## 2026-10-09 — The job register follows the project's database, and the service reads its settings from files

Breaking. `telegram` now uses `capabilities-contract` 0.4.0 and keeps its job register in the database the project resolves: the `AGENTKIT_DB_*` keys in the project's `.env.local` and `.env`, then the process environment, then the machine's store setting; `capabilities store show` shows which answers. `CAPABILITIES_STORE_URL` is no longer read, and the service's deploy descriptor no longer declares it: a deployed node takes `AGENTKIT_DB_*` from its server's environment. The daemon resolves the database for its own project once at launch and keeps it. `service doctor`'s `store` reports `level` and `sources` - which level of the cascade answered and the files or variables it came from - in place of `source`. The daemon reads its settings and documents straight from the project's `capabilities/telegram/` and then the config home's, with the same values as before, and `service/store.py` is no longer shipped.

## 2026-10-09 — `telegram migrate` brings the job register's tables up to date when asked

`telegram migrate` applies the pending steps to the job register's tables in the machine's store, and `telegram migrate status` reports where they stand without a lock and changes nothing. The manager runs `telegram migrate` when it installs or updates telegram, and the service runs it when it starts; every other call takes no lock and migrates only when it finds its tables missing or older than its code. `telegram` now uses `capabilities-contract` 0.3.0: a store that does not answer a connect within 10 seconds is reported as `store_unreachable`, and both ends of a connection send TCP keepalives, so the store drops a client that died without closing.

## 2026-10-09 — One stuck session on the store no longer stops it

`telegram` now uses `capabilities-contract` 0.2.1. Opening the store takes no lock once its tables are in place, so a session left holding the store's schema lock no longer hangs every command and service doctor behind it. Where a lock is still needed, it waits at most 10 seconds and then reports `store_busy`; a process killed while waiting leaves no session queued behind it, and a session that holds the lock without working is ended by the store within 5 seconds.

## 2026-10-08 — The store setting is read from the family's file

`telegram` now uses `capabilities-contract` 0.2.0, which reads the machine's store setting from `$XDG_CONFIG_HOME/agentkit/store.json`, the file `capabilities store set` now writes, and from the manager's former files while it is absent; `AGENTKIT_STORE_URL` overrides it ahead of `CAPABILITIES_STORE_URL`. A machine whose setting is in the former files behaves as before.
