# telegram — change log

## 2026-10-28 — A connection's session path set on one machine no longer sends another machine's login there, and a local file error is no longer reported as the network

A connection record is read by every machine that reaches its store, so a `session` path it carries is the path of the machine that set it. Each verb now resolves a named connection's session on the machine it runs on: the recorded path where a session already lives there or where it lies under this machine's home, and anywhere else `<state-dir>/<id>/session`, so signing a connection in on a node writes the session under that node's own state home rather than failing on another machine's folder. The machine that set the path keeps using it, and `telegram connections` reports the path each machine actually uses. A verb that cannot open or make a local file - such as the session's folder - exits 6 `local_file_error` naming the path, where it used to exit 5 `network_error` "network error reaching Telegram"; a failure reaching Telegram is still `network_error`.

## 2026-10-28 — `migrate` works on a store reached through a transaction pooler alone

`telegram migrate` and `telegram migrate status` apply and read the harness runner's profile table on a transaction connection, so a store whose one address is a transaction pooler (such as Supabase's on port 6543) is migrated and reported as any other; before, that step opened a session connection, which such a store refuses. Declares `capabilities-contract>=0.33,<1`.

## 2026-10-27 — A call recording fetches ffmpeg before it joins the call, so the first one on a machine without ffmpeg is captured

PyTgCalls writes a recording's capture through `ffmpeg` on PATH from the moment the call is joined, so where the machine had no ffmpeg the first recording failed at the join, before anything had fetched it. Every recording - the service's incoming calls and group calls, and `call_recorder` on a chat, with `--watch-groups` and with `--listen` - now fetches ffmpeg into `$XDG_STATE_HOME/telegram/programs/ffmpeg` before it joins, where none is on PATH, and the capture runs on that copy. The first such recording waits for the fetch; later ones find the copy. Where ffmpeg is on PATH nothing changes.

## 2026-10-27 — Call recording fetches its own ffmpeg on first use where none is on PATH, and `telegram manifest` declares it

Where `ffmpeg` is not on PATH, the first recording that needs it - its encode, the join of a recording a restart split, its duration, its waveform, a voice-agent call's stereo track - fetches ffmpeg through uv from the `imageio-ffmpeg` 0.6.0 wheel, a static build with libopus for linux and macOS on amd64 and arm64, and keeps it at `$XDG_STATE_HOME/telegram/programs/ffmpeg`, as the user and without root or a package manager. The service puts that folder on the end of its PATH, so an ffmpeg on the machine is still the one that runs and every later recording uses the fetched one where there is none. A fetch that fails leaves the recording failed with `ffmpeg_unavailable` naming what failed, as a missing ffmpeg did before. A recording's duration is now read from the `Duration:` ffmpeg prints rather than from `ffprobe`, which the wheel does not carry, so a recording no longer needs ffprobe. `telegram manifest` now carries `programs`, naming ffmpeg and what stops without it, so `capabilities doctor` can say it is missing.

## 2026-10-27 — One Telegram account is reached through one connection

`telegram connection add` and `telegram login` refuse a connection whose account another connection already holds on this machine, with exit 6 `number_linked`: `connection add` when the `expected_account_id` it gives is held, `login` before it starts when the connection names a held account, and a login that discovers its account right after the account is known, signing out the session it had just signed in. Nothing is written. The error carries `account` and `holder`, `{connection, owner}`, where `owner` is the project whose own connection it is and null for one the machine shares, as `whatsapp` shapes it, and its message and hint say to ask for access to that connection. The account's folder records the connection that holds it in `$XDG_STATE_HOME/telegram/<account>/linked-by.json`, written when `login` signs it in and, for an account signed in before this release, by the first connection a `doctor` proves it for. The holder logging in again is not refused, nor is another connection once the holder was removed. **For consumers:** two connection names for one account are no longer supported; a project that reaches a shared account under a name of its own keeps reading it, but cannot add or log in such a name again, and moves to a grant on the connection that holds the account.

## 2026-10-27 — `telegram connections` reports the keys the service reads

Every connection `telegram connections` reports now carries, after its app and session rows, one optional, masked row for each key its service reads: the Google key voice calls use (the connection's `gemini_secret_env`, else `GOOGLE_API_KEY`), the OpenAI key (`openai_secret_env`, else `OPENAI_API_KEY`) and `DEEPGRAM_API_KEY`, each with its winning tier and source - the agent's vault included - as for the other keys. A key that is unset is reported unset, and doctor's readiness gate is unchanged, since none of them is required. Without a connections registry the flat keys gain `GOOGLE_API_KEY` and `OPENAI_API_KEY`.

## 2026-10-27 — `telegram app-check` answers outside any project

`app-check` is a machine read, beside `connections` and `doctor`: `MACHINE_READS` declares it, so outside any project it reads no project's or the global policy, answers to the machine ceiling, and prints Telegram's verdict on the machine's app - or, with `--connection`, on the app a globally declared connection signs in through, read-only - where it used to exit 4 `not_enabled` unless telegram was enabled globally. It touches no account and no session. Inside a project it passes the policy gate as before. Help says so.

## 2026-10-27 — `service harness` says which harness sign-ins the service's turns need

`telegram service harness [--json]` prints `{harness, profiles, unresolved}`: `harness` is the sorted, distinct harness tools (`claude`, `codex`) of every profile a turn is configured to run on now, and `profiles` lists each such profile with its harness and where it is named - `settings` (each position the settings reach, as `service doctor` reads them: TELEGRAM_SERVICE_PROFILE or `defaults.profile`, the voice default, every user, group and topic), `chats` (each channel whose `/set profile` names it) and `jobs` (each open job: draft, waiting, running, or stopped on `quota` or `interrupted`, which the daemon resumes on its own; a job registered before profiles runs on `telegram-<engine>`). The chats and jobs are those of this project and its environment. Each name is resolved and fitted as a turn resolves it, with no turn run; one that does not resolve or fit is listed under `unresolved` with why, and needs nothing, and the stub needs nothing. It reads the store on one read-only connection, migrates nothing and writes nothing; a table the store does not hold yet holds no chats or jobs. A project that resolves no store answers an empty list with `store` `not_configured`. The manifest's `service` declares `sign_ins`, `{"harness": ["telegram", "service", "harness", "--json"]}`, and its `verbs` gain `harness`. Help says so.

## 2026-10-27 — `telegram connections` says whether each connection's session is on this machine

Every connection `telegram connections` reports carries `session`, `{"live": <bool>, "account": <text or null>}`, read from local files alone with no call to Telegram. `live` is true when the connection's `.session` file on this machine holds an auth key and the row Telethon keeps for the signed-in account (entity id 0), and no service here recorded the session unauthorized; an auth key alone is not a sign-in, since Telethon mints one at the first connect. The file is opened read-only. `account` is the account the connection records: the one `login` or `doctor` verified, else its `expected_account_id`. The daemon's health records `session_authorized`: false when Telegram no longer accepts the session, true once it signed in; `connections` reads that from the health beside the session, or the one the account's owner record names, for this session file, and the next service start clears it. The manifest's `connections` block declares `device_bound: true`: a connection is a session minted on one device, not a value that moves to another machine.

## 2026-10-27 — The service finds a key in the agent's vault, as the CLI does

The daemon and the call recorder resolve every credential they read - the Telegram app's id and hash, a connection's own hash, the voice keys, the Deepgram key and `TELEGRAM_SESSION` - through the CLI's own credential cascade, the shared library's, instead of a lookup of their own that read only the project's `.env.local`/`.env`, `credentials.env`, `shared.env` and the process environment. A key `telegram connections` reports as `vault:<agent>` is now found by the service as well, where the daemon used to exit with `TELEGRAM_API_HASH not resolved`. The order is unchanged: the project's files, then the machine's files, then the process environment, then the vault. The not-resolved message names the vault. `service/daemon.py` and `service/call_recorder.py` declare `capabilities-contract>=0.25,<1`, the first release that reads the vault.

## 2026-10-25 — `service doctor` names why the service cannot work

A failing `telegram service doctor` still prints its report and exits 5, and now also prints the contract's error envelope naming the first thing it found: `service_unhealthy` with the running daemon's health and last error (for a session that is not signed in, `session not authorized — exec in and run: telegram login ...`), `worker_unavailable` with the profile that cannot run a turn, or the job register's own store code. A supervisor that runs the doctor, such as `deployment runner`, records that as why the service is unusable. A route skipped on this node is listed under `skipped_settings`, as `{setting, project, reason}`, beside the `warnings` that already named it, and the doctor stays ok.

## 2026-10-25 — A route of another machine is skipped on this node instead of stopping the service

A `project` route on a group, a topic, a member or a direct user that holds for every node - a settings row naming no node, or any route kept in files - and lies outside this node's home and the agent's folder is left out of the settings this node runs on, instead of stopping the service as `service_settings_invalid`. The daemon logs `warning: <path> -> <folder> is skipped on this node: ...` at start and on each reload, `service doctor` lists it under `warnings`, and `service validate` under `skipped_routes`. A request that route would carry is refused in its chat, naming the route, rather than run in the agent's own folder. A route this node's own settings rows supply is judged as before and still stops the service, and a malformed route is refused on every node.

## 2026-10-25 — The Deepgram key is kept once for the machine

The script declares `capabilities-contract>=0.22,<1`.

## 2026-10-24 — The service's register is in the store, so a node takes over where the last one stopped

The register - per channel the watermark (the last message handled), the reserved dialogue jobs, the `/set` overrides and the voice-echo senders - is a row per channel in `telegram_channels`, keyed by project, environment, connection and channel, created by step `0006-channels` of the register's ledger (version 1.3), instead of `register.json` under the machine's service state dir. A session reads it when it starts, and the daemon writes the rows that changed in one transaction, so a job leaving its row and the watermark passing it are one commit, and the store never lets the watermark move back. A service the deployment lease moves to another node mid-conversation catches up what arrived during the switch and answers each message once. A write the store does not take is kept and written with the next one; a session does not start while the store cannot be read. The first session on a node carries an existing `register.json` into the store - per channel the newer watermark wins, the store's copy a tie - and records it in `register.imported.json`; the file is never written again, and one still carrying `/set worker` or `/set model` fields is refused before anything is carried in. The `/set` overrides stay on the channel's row, not in the project's telegram settings: they are a person's choice for one channel, made there.

## 2026-10-22 — The service's prompts are versions in the store

The service's prompts - `context`, `delegation`, `job-worker`, the voice prompts and each `context.<name>` - are kept as versions in `telegram_prompts`, a table of telegram's own that the register's ledger creates as step `0005-prompts` (version 1.2). Each save is a new version, one per key is active, and the store refuses any change to a saved version, so earlier versions stay readable. `telegram prompts import [DIR]` saves the service directory's files, `export [DIR]` writes the active versions back as files, `put <key>` saves one version (`--base` refuses a save over a version the writer did not read, exit 6 `conflict`), and `list`, `versions <key>` and `show <key> [--version ID]` read them. The daemon reads a key's active version, and its file only while the store holds no version of that key, so a project that has not imported keeps running on its files as before; while the store does not answer, the daemon keeps the versions it last read and reads the file of any key it has not read yet. Reference documents stay files.

## 2026-10-21 — A connection whose network flow died fails in seconds

`telegram` uses `capabilities-contract` 0.7.2. Its store connections give a network flow up once data sent on it has gone unacknowledged for 20 seconds (`tcp_user_timeout`), which keepalives cannot notice since none is sent while data waits, and send keepalives after 15 seconds idle, every 5 seconds, 3 probes: a connection whose flow stopped carrying packets without a FIN or a reset fails in about 20 seconds as a lost connection instead of waiting until the store ends the session, and a plain read that loses it that way runs once more on a new connection. A connection lost where `telegram` catches nothing ends the command as `store_unreachable`, exit 5, as before.

## 2026-10-20 — A read is a transaction of its own in one round trip

`telegram` uses `capabilities-contract` 0.6.0. On its working connection a plain read that would open a transaction, and any statement in autocommit, reaches the store in one round trip - the transaction's start, the schema binding and the commit go with it - and leaves the connection idle, never `idle in transaction`, so a transaction-mode pooler hands its server session on as soon as the store answers; a write still opens a transaction that its commit closes, and a write whose commit may have reached the store is never sent twice. A connect that fails is tried again after jittered, doubling pauses, and once a store did not answer, a further connect to it is refused at once as `store_unreachable` for a doubling pause of at most 30 seconds rather than dialled again on every statement.

## 2026-10-20 — The daemon exits when its environment leaves the disk

A uv cache prune deletes the environment the daemon runs from while it keeps running, and every worker turn it starts then dies on the missing interpreter, each message ending as a silent `ignore`. On every periodic sync the daemon now checks that its interpreter and the harness launcher are still on disk; when one is gone it marks its health `unhealthy` with the missing path and exits non-zero, so a supervisor that restarts a failed service (launchd's `KeepAlive`, a container's restart policy) starts it again on a rebuilt environment.

## 2026-10-20 — A conference recording outlasts a pause in incoming audio

When a conference's capture stops growing, the recorder asks Telegram whether this account is still listed in the call and keeps recording while it is, logging once that it held on. It closes the recording as `capture_stalled` only when the account is no longer listed or the question cannot be answered, so a pause in which every incoming channel lapsed no longer ends a recording the caller is still in. Direct calls are unchanged.

## 2026-10-18 — One working connection per process

Every connection it opens on the transaction path is the process's one working connection, which the library lends to each operation and keeps until the process exits, so a command connects once rather than once per read; a connect that fails is tried again, and a working connection the store or the network lost is replaced, a statement that lost it before anything of its transaction reached the store running once more on the new one and a commit never sent twice.

## 2026-10-18 — Connections go to the store's transaction address

`telegram` uses `capabilities-contract` 0.5.0. The job store and the profile lookups connect on transaction connections, at the store's transaction address where one is named. With one address everything reaches it as before.

## 2026-10-16 — `telegram service doctor` runs the live harness turn only when asked with `--live`

`telegram service doctor` no longer starts a claude or codex session: under `workers` it reports each distinct profile the settings name as `resolved`, with the harness, model, layer and version it resolved to, or `failed` with why when it does not resolve or fit, and spends nothing. `telegram service doctor --live` runs the one live turn per profile it ran before, held to `defaults.worker_timeout`, and reports the harness's own verdict in place of `resolved` (`accepted`, `model_refused`, `quota_exhausted`, `not_authenticated`, `binary_missing`, `timed_out`, `incompatible_harness` or `failed`). `workers` now carries `live`, saying which of the two ran. A doctor called by a watchdog or a control panel no longer leaves a session behind on every call; the deploy descriptor's doctor command is unchanged, so it no longer probes either. `ok`, the exit codes and every other key are as before.

## 2026-10-14 — The assistant service lets every conference chain settle before it joins

A conference invite whose chain answered within two seconds used to be joined at once, and most such joins ended the call within seconds, once for everyone in it. Every accepted invite is now held until the newest block of its chain has stood unchanged for the settle time, as invites whose chain answered slowly already were, so the assistant is heard about four seconds later in every conference; a chain still growing when the settle budget runs out is declined whichever way it first answered. No verb, output or setting changes.

## 2026-10-13 — `telegram service schema` prints the settings as JSON Schema, and `telegram service validate` judges a proposed document without writing it

`telegram service schema` prints the settings the service holds itself to as JSON Schema (draft 2020-12), built from the same key sets, choices and bounds the service validates against, so a document it refuses is one a reload refuses. Under `x-` keys it carries what a settings panel needs: `x-apply` on each top-level key (`restart` for `connection` and `environment`, `reload` for the rest), `x-keyed-by` and `x-entry-label` on each map (users and members by Telegram user id, groups by chat id, topics by forum topic id, each named by `name`), `x-inherits` where an absent value comes from (a topic's `profile` from its group's, then `TELEGRAM_SERVICE_PROFILE`, then `defaults.profile`; a group's or user's `worker_timeout` from `defaults.worker_timeout`; and so on), `x-layers` for rights that merge or replace, `x-rights-from` on a topic, which inherits its group's rights, `x-document` on each prompt file setting and `x-documents` for the service's own prompts. `telegram service validate` reads a whole proposed document on stdin, or with `--key KEY` one key's JSON value put over the document held now, lays it over the other scope as the service does, and judges it as a reload would without writing anything: refused, it exits 6 `service_settings_invalid` with the full path the reload names; accepted, it prints the keys that change, whether a reload takes them or a restart is needed, and each prompt file the settings name with its document key, which `telegram context show|edit|put` reads and writes. Nothing a running service or an existing command does changes.

## 2026-10-13 — One Telegram app per machine that every account inherits, and `telegram app-check` to ask Telegram about it

The app every account signs in through is now a machine prerequisite: `TELEGRAM_API_ID` and `TELEGRAM_API_HASH` are declared under `connections.setup`, both required, the hash a secret, so `telegram setup set --field TELEGRAM_API_ID=<id> --stdin` with `{"TELEGRAM_API_HASH": "<hash>"}` on stdin writes them once to `credentials.env` and a control panel asks for them once, before any account. A connection's `api_id` and `secret_env` are no longer required: a connection naming neither signs in through the machine's app - in every command, `doctor`, `connections` (which reports the inherited keys as `TELEGRAM_API_ID` and `TELEGRAM_API_HASH` with where each resolved) and the assistant service - so adding a second account needs no app credentials. A connection that names its own app keeps it: an app is an id and its hash taken together, so a connection naming its own `api_id` takes the hash its `secret_env` names, else the one under its own key `TELEGRAM_<ID>_API_HASH` where `connection add` writes it, and is never paired with the machine's hash; one whose hash does not resolve is still refused as `missing_secret`, and one naming a `secret_env` with no `api_id` is still refused as `incomplete_connection`. ## 2026-10-13 — `telegram` declares what a person is asked for, and writes it through the contract

`telegram manifest` now declares a connection's fields under `connections.fields` (`api_id`, `secret_env`, `session`, `expected_account_id`, `gemini_secret_env`, `openai_secret_env`), each with its label, help, type, whether it is required and whether it is a secret, and `telegram connection add <id>` writes one connection from them: non-secret fields on argv with `--field KEY=VALUE` or in a JSON object on stdin with `--stdin`, a secret only on stdin, written to the scope's `.env.local` or `credentials.env` under its own env key. `telegram connection remove <id>` takes it out again with the secrets it wrote. ## 2026-10-13 — `telegram login` shows the QR by default; the phone number and code move behind `--phone`

Breaking for anyone who scripted the phone login. `telegram login` with no method flag now logs in by QR code, as `telegram login --qr` did: it renders the QR on stderr, waits for an already-authorized Telegram app to approve it, and asks for the 2FA password when one is set. The phone-and-code login is now `telegram login --phone`, which prompts for the number, or `telegram login --phone NUMBER`, which takes it, and then asks for the code and the 2FA password as before. `--qr` is still accepted and names the default; `--qr` and `--phone` together are refused. `help`, `deviations.md` and the not-logged-in hints of `doctor` and the other commands name the QR first and the phone second. ## 2026-10-13 — A reply gate decision on claude runs without thinking, reads its chat's cached prompt, and asks for no session title

The schema a gate decision is held to no longer names the batch's message ids: it is the same for every run in a chat, narrowed only to the chat's allowed reactions. ## 2026-10-11 — A store behind Supabase's transaction pooler is refused at connect

`telegram` now uses `capabilities-contract` 0.4.1. A transaction-mode pooler keeps no session between transactions, so the schema binding, prepared statements and notifications a connection relies on are lost through one, and it is not supported. A database setting that points at Supabase's transaction pooler - a host under `pooler.supabase.com` on port 6543 - is refused before anything is sent to it, as `transaction_pooler`, with a hint naming the session pooler: the same host on port 5432. Every other database, the session pooler included, is reached as before.

## 2026-10-11 — The service reopens the job register's store connection after losing it

When the store or the network ends the job register's database connection while the Telegram session stays up, the service's next job tick opens a new connection and the queue keeps draining, rather than retrying the dead connection every tick until the Telegram session ends or the service restarts. The log says `jobs: lost the store connection, reopening it on the next tick` for it, and a session that loses its connection to Telegram is logged as `session lost its connection to Telegram` rather than as likely protocol drift.
