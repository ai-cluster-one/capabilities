# calcomc — deviations

This file's sole purpose is to hold `calcomc`'s deliberate, justified departures from the [SHEBANG](../../SHEBANG.md) defaults, kept apart so an audit reads them as choices, not drift (DOCTRINE — *[Deviations are allowed — and recorded](../../DOCTRINE.md#deviations-are-allowed--and-recorded)*). Each realizes the *intent* of the pattern in the terms of a tool that **wraps another CLI's authentication rather than calling an API** — calcomc puts one account's Cal.com API key in front of the official `calcom` CLI and forwards to it.

## Transport is a subprocess passthrough to `calcom`, not an HTTP/JSON API

calcomc makes no network calls of its own. It resolves a key, sets it in the child environment, and `subprocess`-execs `calcom`. So the inline dependency set is empty (`dependencies` is absent) — no `httpx`, no client. The *resilient-HTTP* intent (backoff, `Retry-After`, 4xx→2/3/6 mapping) is realized by the `calcom` CLI and the Cal.com API v2 client it embeds for forwarded commands; calcomc's only network-shaped failure is `doctor`'s one `calcom me show` round-trip, which maps a rejected key to exit 2 and an unreachable or failed `calcom` to exit 5, and a timeout to exit 5.

## Forwarding is transparent — calcom owns the forwarded command's contract

For everything except its own verbs, calcomc inherits stdio and execs `calcom` with the args verbatim: `calcom`'s stdout, stderr, and **exit code pass through unchanged**. This is what lets `--json`, prompts, and colors behave exactly as in `calcom` itself, and it is why calcomc never maps or re-documents the surface (the surface is `calcom help`). Consequently the `_emit`/`_die` JSON envelope and the exit-code taxonomy apply **only to calcomc's own layer** — key resolution, the gate, `doctor`, and `calcom`-not-on-PATH. A forwarded command returns a `calcom` exit code, which is not drawn from calcomc's taxonomy. The intent — a stable, machine-checkable contract where auth is always distinguishable — holds for calcomc's own layer (exit 2 = key problem) and is delegated to `calcom` for the rest.

## The write gate classifies the ACTION, not the first word

`WRITE_VERBS` normally lists first-position domain verbs. calcom's surface is `<group> <action> [args]`, nested up to three levels (`teams members add`, `org-roles permissions set`, `team-workflows routing-forms delete`), so the first word is a resource group and carries no read/write meaning at all. calcomc therefore classifies on the **action**: the last word of the command *path* — the leading run of non-option tokens — that appears in calcom's known action vocabulary. `READ_ACTIONS` is the allowlist; `WRITE_ACTIONS` (bound to `WRITE_VERBS`, so the standard gate still fires on a top-level write like `api-key-refresh`) names the rest. Two properties make this safe rather than merely convenient: option **values** are excluded from the scan, so free text passed to `--title` or `--reason` can never be read as an action; and an action calcomc does not recognize is treated as a **write**, so a command this tool has not seen is refused rather than waved through. The gate is applied at dispatch — after connection selection, before the key resolves or `calcom` is execed — so a write on a read-only connection exits 4 regardless of whether the key is present or calcom is installed. This is the one place calcomc reasons about the surface it otherwise treats as opaque.

## calcomc requires a resolved key and refuses ambient auth

The `calcom` CLI, with no `CAL_API_KEY` set, falls back to this machine's stored session at `~/.calcom/config.json` — whichever account last ran `calcom login`. calcomc deliberately does **not** allow that: if no key resolves for the selected connection it exits 2 rather than forwarding, so a command can never run on another account's ambient credentials by accident. The refusal *is* the scoping guarantee. For the same reason `login` and `logout` are calcomc-owned refusals (exit 6) rather than forwarded words: they write the stored session calcomc never reads, and identity here is declared as a connection. And because the same stored config can also carry an `apiUrl`, calcomc **pins `CAL_API_URL`** in the child environment on every invocation — the connection's `api_url`, else the public default — so a stored config can never redirect an authenticated call to another endpoint.

## `doctor` is `calcom me show`, plus exit code 7

`doctor` proves health with the cheapest authenticated round-trip the account surface offers — `calcom me show --json` — and reports the account id, email, username, and time zone, plus the API base the connection resolved to. It runs **per connection** (every configured connection bare; one with `--connection <id>`), emitting `{ok, connections: {<id>: {…}}}` and exiting `0` only when every connection is healthy, else the first failure's category. calcom's absence is reported per connection (the round-trip's `OSError` becomes that connection's category-5 finding), not a single top-level refusal. calcomc adds one domain exit code beyond the taxonomy: **7 = wrong account** (a connection's key resolves to an account other than its `expect_email`), named in `calcomc help`.
