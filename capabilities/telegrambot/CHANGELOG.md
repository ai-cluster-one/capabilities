# telegrambot — change log

## 2026-11-08 — Channels, jobs and prompts go with their agent, at telegrambot 2.1

Step `0008-keys` (telegrambot 2.1, core 4.0) keys the channels, seen marks, jobs, job slots, job amendments and prompts to their agent (`ON DELETE CASCADE`), a job's slots and amendments to their job, and a job keeps its row and loses the node it ran on where that goes (`ON DELETE SET NULL`). The prompts guard admits the cascade of a deliberate delete and nothing else. A reference to an agent or node the store no longer holds is settled when the step runs, kept in `telegrambot_premig_m9`. Runs on capabilities-contract 0.45 and callva-harness-runner 0.12.0. No verb, flag or JSON key changes.

## 2026-11-08 — Replies reach Telegram formatted, not as raw Markdown

What the service sends for a turn - the answer, its progress lines, what the turn or a job sends into the chat, a file's caption and a job's result - reached the chat as the model wrote it, `**` and backticks included. The transport now renders that Markdown into Telegram's message entities and sends them with no parse mode, so no character needs escaping: bold, italic, strikethrough, inline code, fenced code blocks (with their language), links, quotes and flat lists render; a heading becomes a bold line, a table a code block as written, and a list item a `•` line. Text that is not markup - `2*3*4`, `snake_case`, `<tag> &` - arrives whole, and a backslash keeps a marker literal. A reply is cut at 4096 UTF-16 units, as Telegram counts them, and an entity across a cut continues in the next part. A part whose formatting Telegram refuses is sent once more as the same text without it, so a reply is never lost to its formatting. The shipped turn and job mechanics name the forms Telegram renders and ask for no headings, tables or nested lists. The voice echo and the `send` verb still send text as written. No verb, flag, environment variable or output key changes.

## 2026-11-08 — A sender's role can name the profile their turn runs on

A role can now name its own harness profile under the new settings key `roles.<role>.profile`, validated like every other profile key; `profiles list` names it at that position, and `service harness` counts it among the profiles a turn may run on. A turn from a sender whose role names one runs on that profile, in place of the chat's or topic's and over a chat's `/set profile`, so ordinary group members can run on a read-only profile while the supervisor's turns keep the chat's. A role that names none runs on the chat's or topic's profile as before, and background jobs keep `job_profile`. The profile's sandbox and tools are the profile's own; nothing else about a turn changes. No verb, flag, environment variable or output key changes.

## 2026-11-07 — A connection is named by its id: telegrambot's tables go to schema major 2

A connection - a bot - is keyed by the opaque id the store gives it, and called by its label; `--connection` takes either. Step `0007-connection-ids` (schema 2.0, reading the core at 3.0) gives `telegrambot_channels`, `telegrambot_seen`, `telegrambot_jobs`, `telegrambot_job_amendments` and `telegrambot_job_slots` two columns in place of `connection`, exactly one of them set: `connection_id`, the id of a bot the store holds, with a foreign key that removes the rows with their connection, and `file_connection`, the id of a bot only files hold - a files-mode project, or a machine's own connection lent to a store-mode project - whose rows keep working as before. Every key and index takes whichever is set where the name was, and a write puts the id in `connection_id` where the store holds that connection, else in `file_connection`. A name the store's map of the cutover resolves takes its id; any other stays, unchanged, a files connection's. Every case over the convenient case: the shape of a node's `coolify_connection_id` and `coolify_address`. The step crosses only through `capabilities store upgrade`; outside it a store at major 1 is refused with `store_upgrade_needed`. A bot's folder made under its connection's former name, its MTProto session included, is moved to `<state>/<id>` the first time the bot is used, saying so on stderr, so history reads sign in with the session they had. `jobs list` and `jobs active` still answer `connection` on each job, now the id. Declares `capabilities-contract>=0.44,<1`. No verb, flag, environment variable or output key changes.

`inventory` names each bot by its connection's label, where it named the id.

`doctor` and `service doctor` name each bot by its connection's label: what a bot lacks, why it is not served (`skipped`, keyed by label), its row under `bots` and each problem line, where each named the id.

## 2026-11-05 — The harness profiles are `harness_profile_versions`, behind the store upgrade

telegrambot migrates the harness runner's profile table before its own, so it now pins `callva-harness-runner` 0.11.0, whose step takes that table to schema major 2 as `harness_profile_versions` with the agent in `agent_id`, and declares `capabilities-contract>=0.43,<1`, the library that reads the store's core tables by their new names. The move crosses only through `capabilities store upgrade`, which migrates the harness owner through telegrambot as its further owner; outside it, telegrambot refuses a store still at schema major 1 with `store_upgrade_needed`, naming that command. telegrambot's own tables, which already name the agent `agent_id`, stay at 1.0, and `telegrambot_prompts` keeps its name. Profiles resolve and save as before. No verb, flag, environment variable or output key changes.

## 2026-11-05 — History reads a supergroup the bot is in

`history`, and a turn's read back, refused every supergroup with `chat_unreachable (ChannelInvalidError)`: the read named the channel with access hash 0, which `channels.getMessages` does not accept. The reader now asks `channels.getChannels` for the channel first, which accepts hash 0 from a bot that is a member, takes the access hash Telegram answers with, and keeps it for as long as the reader lives, so a long-running service asks once per supergroup. A supergroup the bot is not in is still refused as `chat_unreachable`; private chats and basic groups read as before.

## 2026-11-04 — An agent's own Telegram channel through a bot

New capability. One connection is one bot and holds everything that bot needs - the BotFather token, the App api_id and api_hash that let it read history, and the Deepgram key for voice - each as a value sealed into the agent's vault or a reference to a key held there, so a connection is whole on any machine. A new connection refers to the machine's shared `DEEPGRAM_API_KEY` where the machine holds one; nothing else stands in for a key the connection does not name.

New messages arrive and every write leaves over the HTTP Bot API; history is read back from Telegram by message number through an MTProto session the bot's own token signs in. Nothing keeps a copy of the conversation. `doctor` reports the bot, its privacy mode, a webhook that would stop polling, history readiness and voice readiness, and names what a connection lacks. `seen` lists the chats, topics and people the bot has seen; `history`, `download`, `send` and `react` act on one chat; `prompts` keeps the agent's own prompt over the shipped standard; `profiles` and `jobs` reach the harness profiles and the background work.

The bundled service runs once per machine for every project that joins it, or in one project: one getUpdates poll per bot, direct chats, groups and forum topics, one person's messages within the debounce as one turn, roles for commands and for tools, harness profiles, background jobs, the reply gate in shadow or live mode, voice transcription with a per-chat echo switch, `/status`, `/stop`, `/stop N`, `/profiles`, `/reload` and `/set`, and a bound on turns other bots start in a row, on by default. Its state is the project's store: `telegrambot_channels`, `telegrambot_seen`, `telegrambot_prompts` and the job tables.
