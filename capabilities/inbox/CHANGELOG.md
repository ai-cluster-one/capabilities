# inbox — change log

## 2026-11-08 — An item goes with its agent, and keeps itself when the node it was put from goes, at inbox 1.3

Step `0006-keys` (inbox 1.3, core 4.0) keys `inbox_items`: an item goes with its agent, and keeps itself, losing `node`, when the node it was put from is removed (`ON DELETE SET NULL`). The item guard admits that and the cascade of a deliberate delete and nothing else, and the change notice stays quiet under it. A reference to an agent or node the store no longer holds is settled when the step runs, kept in `inbox_premig_m9`. Runs on capabilities-contract 0.45. No verb, flag or JSON key changes.

## 2026-11-05 — An item links to the thing it came from, and an ask can be answered in words alone

`inbox ask`, `inbox talk` and `inbox notify` take `--source-label L --source-ref R`, both or neither: the label the person reads for the thing the item came from and the asker's own reference to it, each one line of at most 200 characters. inbox reads neither; `show`, `status` and `list` return them as `"source": {"label", "ref"}`, null where the item names none, and the store keeps them among what an item asks, which never changes. An ask answered with `inbox answer <id> --reply TEXT` and neither yes nor no records the answer `other`, whose words are the whole answer; the on-answer command receives `INBOX_ANSWER=other` with the words in `INBOX_REPLY`, and the store refuses `other` without a reply. The word after `--reply` is the reply whatever it holds, a leading dash included. Ledger step `0005-source-other` (inbox tables 1.2) adds `source_label` and `source_ref` and admits `other` as an answer; items put before it name no source.

## 2026-11-05 — Whatever is put before a person is written for someone deciding, and every agent's context says so

`inbox stub`, the line the manager composes into the context of every agent where `inbox` is enabled, now carries the rule for anything an agent puts before a person in the Inbox, itself or through another tool: say what this is, why it comes up now, what is needed from the person, and which answer you recommend and why, in plain language with no code, file paths, line numbers, commit or task ids, or internal names, under a title that says the matter itself. The manifest's `summary` carries the same text, since the stub is that summary closed by its discovery pointer. `inbox help` points `ask`, `talk` and `notify` at it. It is an instruction to the writer and not a check: nothing an item says is refused for its wording, and every verb answers as before.

## 2026-11-03 — Every item carries the harness session that put it in and the node it was put from

`inbox ask`, `inbox talk` and `inbox notify` record the harness session the command runs in, as the harness names it in the environment of every command it runs: `CLAUDE_CODE_SESSION_ID` for Claude Code, `CODEX_THREAD_ID` for Codex. `ask` gains `--session ID` as `talk` has it, naming another session of the same agent instead. A session is this agent's where the harness's own session store holds it as started in the project's folder, or in a folder inside it that is no project of its own, by the first `cwd` its file records: Claude Code's transcript `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/*/<id>.jsonl`, Codex's rollout `${CODEX_HOME:-~/.codex}/sessions/*/*/*/rollout-*-<id>.jsonl`. Any other session, the one the environment names included, is refused with exit 6 `foreign_session`, since the agent whose session it is puts the item in itself. An ask or a talk with no session is refused with exit 6 `no_session` unless it gives `--on-answer`, so a caller that runs in no harness session - a service, an automation, `tasks` run by none - keeps putting items in through its command; a notify records the session where there is one and needs none. Every item records the node it was put from, by the id `capabilities node id` answers, in the new column `node`, and `show`, `status` and `list` return `session` and `node` for every kind. Ledger step `0004-session-node` (inbox tables 1.1) drops the check that kept `session` to a talk, adds `node`, and keeps it among what an item asks, which the store never lets change; items put before it keep a NULL node.

## 2026-11-03 — A go-between to the person: items an agent puts in, the person answers, and the asker's command takes the answer

`inbox` keeps the items agents put before the person in the PostgreSQL the project resolves, one row each in `inbox_items`, migrated under the `inbox` ledger. The agent is the project the command runs in, by its declared id, never an argument. `inbox ask` puts in a question for yes or no with the words for each answer and the one the agent recommends, `inbox talk` a message to answer in words, `inbox notify` something to know; `--key` makes a repeat by the same agent return the item it already put in, and `--on-answer` leaves the command that takes the answer. `withdraw` takes a question back, `status` and `wait` read the asker's own item and its answer, and `deliver` runs the asker's due on-answer commands. The person reads with `list` (the inbox or the archive view, by agent, kind and time, newest first in pages with a cursor), `show` and `count`, answers with `answer`, and marks items with `read`, `unread`, `archive` and `unarchive`. The first answer is final: a second is refused, and the store refuses any change to an answer once given. An on-answer command runs as written through `sh -c`, in the asking agent's folder with that agent's own environment, the answer reaching it only in `INBOX_*` environment variables; a failed run leaves the answer recorded and the item undelivered, and is run again on a doubling interval from 30 seconds up to an hour. Every change raises the agent's version of `inbox_changed` in the store's change versions. `inbox service run|status|doctor`, once per machine for the projects that join it or in one project, starts `inbox deliver` in a served agent's folder when an answer is announced for it and when a failed delivery falls due; a delivery is claimed under a lease, so it runs once wherever the agent's folder is.
