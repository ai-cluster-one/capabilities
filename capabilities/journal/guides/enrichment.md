# Enrichment — summarising and tagging entries with `journal`

The `journal` CLI is a pure adapter: it lists, reads, stores, chunks, and
searches entries. It does not interpret content. **Summaries and tags are
generated by the host agent**, which reads a transcript, writes the enrichment,
and saves it back through `journal update`. This guide is the procedure for
doing that well; the orchestration itself — cadence, which entries, when —
belongs to a routine in the consuming project, which names this procedure by
role.

## The contract the tool gives you

- `journal list --has-summary false` — the worklist: entries with no summary.
  It carries metadata only, so the listing stays cheap however long the
  transcripts are.
- `journal read <id>` — one entry as JSON. `message` is the transcript to
  summarise; `language` is the language code once it is known.
- `journal update <id> --summary "…" --type "…" --language "…" --tags "a,b,c"`
  — saves the enrichment and stamps `enriched_at`.
- `journal chunk <id>` — splits the transcript into embedding chunks. Chunks
  inherit the entry's language and tags, so **chunk after updating**, never
  before.

## One entry, one subagent — batches run in parallel

Reading a transcript fills context. To protect the main conversation,
**delegate each entry to its own subagent**. Because every subagent touches
exactly one row and writes only that row, batches run **concurrently** without
contention — and each entry staying in its own context window is what keeps
one entry's themes from bleeding into another's summary.

```
for each batch of entries (5-8 at a time):
    1. Spin up ONE subagent per entry in the batch, all at once
    2. Each subagent independently:
       a. `journal read <id>`            → the transcript
       b. classifies monologue vs dialogue, detects the language
       c. writes the summary and extracts tags
       d. `journal update <id> …`        → saves the enrichment
       e. `journal chunk <id>`           → regenerates the chunks
       f. reports and is destroyed (its context, and the transcript, freed)
    3. The main thread collects the batch's results, then starts the next batch
```

Never process several entries inside one subagent: that is the one thing that
produces cross-contaminated summaries.

## Subagent prompt template

```
You are processing a single journal entry. Follow these steps exactly:

STEP 1 — read the entry:
    journal read <ENTRY_ID>
  The output is JSON; `message` holds the transcript.

STEP 2 — classify:
  a) type — MONOLOGUE (one person thinking aloud) or DIALOGUE (a conversation).
     A transcript carrying a single speaker label is a monologue.
  b) language — the language code of the content ("ru", "en", "et", …).

STEP 3 — write the summary. It must be:
  - Plain text: no markdown, no headings, no bullet points.
  - 2-4 sentences capturing the key topics and themes.
  - Written in the SAME LANGUAGE as the entry.
  - Specific — name the concrete topics, projects, people and ideas discussed.
  - Free of meta-commentary ("the author discusses…", "this entry is about…").

STEP 4 — extract tags. They must be:
  - Specific to the actual content: projects, people, concepts, places, states.
  - Lowercase, hyphenated for multi-word tags ("business-model", "morning-routine").
  - Generous — 5 to 15 per entry, so the entry is findable from several angles.
  - Both the broad theme AND the specific detail.
  - Never generic filler ("personal", "thoughts", "journal") — those match
    everything and therefore find nothing.

STEP 5 — save it:
    journal update <ENTRY_ID> --summary "…" --type "monologue" \
        --language "ru" --tags "tag-one,tag-two,tag-three"

STEP 6 — regenerate the chunks so they carry the new language and tags:
    journal chunk <ENTRY_ID>

STEP 7 — report: the entry id, its date, type, language, tag count, chunk
count, and the summary.
```

## Where the enrichment then lives

Enrichment is what makes the store searchable, and each level reads a different
layer of it:

- `journal search <query>` — summary, tags and type together. The first reach.
- `journal scan <query>` — summaries only, with a snippet around each hit.
- `journal grep <query>` — the transcripts themselves, for an exact phrase.

Re-running `journal update` on an entry overwrites the fields it is given and
re-stamps `enriched_at`; re-running `journal chunk` replaces that entry's
chunks wholesale. Both are safe to repeat — a better summary is one `update`
away.
