# slacker — change log

## 2026-10-20 — A read is a transaction of its own in one round trip

`slacker` uses `capabilities-contract` 0.6.0. On its working connection a plain read that would open a transaction, and any statement in autocommit, reaches the store in one round trip - the transaction's start, the schema binding and the commit go with it - and leaves the connection idle, never `idle in transaction`, so a transaction-mode pooler hands its server session on as soon as the store answers; a write still opens a transaction that its commit closes, and a write whose commit may have reached the store is never sent twice. A connect that fails is tried again after jittered, doubling pauses, and once a store did not answer, a further connect to it is refused at once as `store_unreachable` for a doubling pause of at most 30 seconds rather than dialled again on every statement.

## 2026-10-20 — `search` finds messages by their text

`slacker search <query> [--limit N] [--sort score|timestamp]` searches message text across every conversation the linked account can see, through Slack's own search (`search.messages`), so it reaches messages the store never captured and needs neither the store nor a running capture. Slack's query modifiers (`in:`, `from:` and the rest) apply as they do in the client. Each match names its conversation (`channel`, `channel_name`, `kind`), its `ts` and time, its `thread_ts` — read from the permalink when Slack leaves it off a reply — its author and its permalink, so `history <channel>` and `thread <channel> <thread_ts>` read it in place. No match is a successful answer with `count` 0; an invalid session exits 2, a refused read 6, and an unreachable Slack 5 (`slack_unreachable`). Proven in the lane against a local Slack Web API; a search of the person's own workspace is the owner's check after release.

## 2026-10-20 — `link` reaches a real Chrome

`slacker link` dials Chrome's DevTools socket without an `Origin` header, which a real Chrome requires of a client it was not told to allow; before this, Chrome answered 403 and `link` stopped with an unhandled error before the sign-in page could be used. A handshake Chrome still refuses is now the refusal `devtools_refused`, pointing to the paste route. The Chrome it opens uses a mock keychain, so the temporary profile never asks for the macOS keychain.

## 2026-10-20 — Link a workspace by signing in through a Chrome window

`slacker link [<id>]` links a workspace without copying a token or a cookie. On a machine with Google Chrome and a display it opens the installed Chrome with a fresh temporary profile and Chrome's remote-debugging channel, loads the Slack sign-in page, and waits while the person signs in normally — password, magic code, SSO, 2FA — clicking and typing nothing. It then reads the workspace `xoxc-` token from the page's own `localStorage` `localConfig_v2` and the shared `d` cookie over the DevTools protocol, writes them through the existing connection surface (secrets to the credentials file, never to the registry, a log, or output), closes the window, deletes the temporary profile, and proves the link with the same check `doctor` runs. With several workspaces signed in it names them and links the one asked for (by `--workspace` team id, domain or name, or an id that matches one), or asks over the `--events` stream. With no Chrome, a closed window, or a sign-in that times out it refuses with a hint to the paste route and leaves no partial connection. The ceremony drives no bundled browser and adds no dependency — the DevTools channel is spoken over the `websocket-client` library `slacker` already ships — and never reads the person's everyday Chrome profile. Manual paste linking (`connection add <id> --stdin`) is unchanged and stays the fallback. The protocol exchange is proven in the lane against a fake DevTools peer and a real local `/json` endpoint; the live sign-in through a real browser is the owner's check after release.

## 2026-10-19 — Read-only pilot: link a workspace, read it, capture it

`slacker` reads one Slack workspace as the person who links their own web-client session — the workspace `xoxc-` token and the shared `d` cookie — the way `whatsapp` and `telegram` emulate their vendor's client. It is read-only: there is no verb that writes to Slack. `doctor` and `whoami` prove the session (`auth.test`), the linked user and the workspace, and check the connection's `team_id` / `expect_user` bindings; `conversations` lists what the account can see (DMs, group DMs, public and private channels), each a member conversation; `history` and `thread` read a conversation and its replies, from the store and reaching to Slack when it cannot cover the request, a thread whenever the store lacks a reply its parent counts; `sync` brings each member conversation forward incrementally against a per-conversation cursor, deduplicated on the message ts. The capture lives in the project's Postgres database in `slacker_*` tables keyed by the workspace account (its team id), built by `migrate`. A bundled `capture` service (`slacker service run`) holds the session's event stream and writes new messages, edits, deletions, thread replies and reactions into the store as they arrive (a reply moves only its parent's reply count, never its text), backfilling through the sync cursor on every reconnect so a drop loses no channel message and doubles nothing; a thread reply posted during a drop is not in Slack's channel history and is read with `thread --fresh`. A sync brings a conversation forward from its cursor completely, and the cursor moves only over a range that joins what the store already covers; a sync from the cursor cut short by a rate limit resumes on the next sync below what it already fetched, so a deep gap closes over successive rounds. Dependencies are permissively licensed: `slack_sdk` (MIT), `websocket-client` (Apache-2.0), on `capabilities-contract` 0.5.1. The realtime socket carries the `d` cookie and the web client's origin, a gateway error frame is a failed connect, the service health counts captured events, and quote marks a browser console prints around a pasted token or cookie are dropped. The interactive browser-driven linking and the rate limits remain to be verified against the live service; the session is the person's own, used transparently with no concealment, monitoring bypass or client-identity spoofing.
