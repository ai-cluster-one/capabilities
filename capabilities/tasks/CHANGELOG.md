# tasks — change log

## 2026-10-06 — A scan carries each task's runs, their cost and its blockers

Every row of `tasks list` and `tasks search`, with or without `--full`, gains `runs` - `{count, by_worker, cost_usd, without_cost}`: every raise of the task in all and by worker, the sum of the `cost_usd` its raises' metrics recorded (null when none did), and how many recorded none - plus `blocked_by`, the metadata key as stored, and `blocked_by_status`, mapping each name it lists to the status of the task it names, null for a name matching no task. A `tasks watch` line's task row, being a `list` row, carries them too. They are computed in the scan's own query, so a page is still one query. Existing fields are unchanged. Run `tasks help` COLLECTIONS for the fields.

## 2026-10-06 — A turn that lost its raise is ended instead of working on unclaimed

The beat of `tasks run` keeps time by whichever of the wall clock and the monotonic clock has moved further, so a machine that slept renews when it wakes rather than a whole beat later, and a wall clock set back holds back no renewal. A turn whose raise is lost - the store answers that it is no longer running or that its lease has run out, or the lease the last renewal wrote runs out with no renewal reaching the store - is ended at once with everything it started, instead of working on for up to its timeout on a task that was put back and with every write refused. `run` says `{"lease_lost": {...}}` on stderr, its answer carries `lease_lost` with the reason, and the raise's detail, when it can still be closed, begins `lease lost:`. A renewal that fails is still tried again within seconds on a new connection, and each failure is now said on stderr as `{"beat_failed": {...}}` and counted in the answer's `beat_failures`. The service's log line for a turn names `lease_lost` and `beat_failures`. Run `tasks help` ONE TURN OF THE CONVEYOR for the details.

## 2026-10-06 — A store outage, a dead turn and a raise left open no longer stall a lane

A command that cannot reach the store - every verb a worker's turn calls, and `tasks run` itself - no longer exits 5 at once: it asks again after 1s, then at a doubling interval of at most 30s, for the window `TASKS_STORE_RETRY_SECONDS` names, 180 unless set and resolved as a connection value is, says so once on stderr as `{"store_away": {...}}`, and exits 5 `unreachable` only once the window is spent; 0 asks once. A store that answers and refuses the role, password or database is refused at once, and `tasks doctor` never waits. `tasks run` now holds its task by a short lease from the claim and renews it from a thread of its own while its process lives - every sixth of the window, between 2s and 30s apart, to the window and three beats more, 270s unless the window is changed - never past `limits.lease_seconds` from the claim, which keeps its meaning as the longest a raise may hold its task. A turn whose process is killed or crashes is therefore closed as abandoned and its task put back by the next claim within minutes instead of hours, the way any lapsed lease is, while a store outage shorter than the window lapses no live turn. A claim no longer fails with a unique-key conflict on a task in todo or waiting that an open raise still holds: it passes the task over, names it under a new `passed_over` entry with verdict `held`, the raise and until when its lease runs - in `claim` and `run` answers and the service's log line - and takes the next one; `claim --key` and `run --key` naming such a task refuse with exit 6 `conflict` naming the raise. `claim` by hand renews nothing and holds the lease it is given. Run `tasks help` STORE, ONE TURN OF THE CONVEYOR and EXECUTION for the details.

## 2026-10-05 — A hook deferral leaves no row in the task's history

A worker's `before` hook that defers a task - exit 75 with a moment on its last line - still sets the task's pickup to that moment, and no longer records the move in the task's history: the row it wrote, with actor `hook:<worker>`, was written every time a lane was held and carried nothing a reader needed. The trail is unchanged, it never had an entry, and `run` and the service log still name each deferral under `passed_over`. Rows such a deferral wrote before this version stay in the store until removed. Run `tasks help` HOOKS for the contract.

## 2026-10-03 — Find the task a run was for, for many runs in one call

`tasks runs --run SYSTEM:REF [--run ...] [--since WHEN] [--project ID | --all-projects]` goes from runs to the raises they were: given the handles a harness knows its runs by - `--run claude:<session id>`, repeating - or a period with `--since`, it answers `{"runs": [...]}`, one row per matching raise, oldest first, each carrying `execution`, `task_id`, `project_id`, `unique_key`, `title`, `worker`, `status`, `started_at`, `ended_at`, `run_system` and `run_ref`. Its scope is the one `list` reads, and `--all-projects` reads every project in the store. A run no raise names answers no row and is not an error, and the call is one query on one connection however many runs it names. The schema gains the index `task_executions_run_idx` on `(run_system, run_ref)`, added beside what is there, so a store without it is brought up to it by the first command that reaches it. `tasks runs <task>` is unchanged. Run `tasks help` RUNS for the contract.

## 2026-10-03 — A store connection the path dropped no longer holds the service or a turn

A connection whose path to the store dropped while the store never closed it - a laptop that slept, a network that went away - used to leave the daemon, or a turn, waiting on its answer for ever, and a SIGTERM was not taken while it waited. The daemon now severs its question connection, or its listener's round trip, when no answer is back within 45s, counts the connection lost and asks for it again as it does any lost connection, so it keeps waking at its poll and a stop is taken within that bound. Every store connection, a turn's and every command's included, carries TCP keepalives, and where the platform has it a one-minute bound on data left unacknowledged. `tasks service doctor` fails when the running daemon's planned wake is overdue by more than twice that bound, since nothing else keeps it from its wake. Run `tasks help` SERVICE for the details.

## 2026-10-03 — One machine process can serve every project that joins it

The service gains a machine mode: one process on the machine serves every project that opted in, each as its own slot, so the projects on one machine share one process, one listener and one question connection per store, and an optional cap on the turns they run at once. A project opts in with `tasks service join`, run in a project that enables tasks for itself, and leaves with `tasks service leave` (or `tasks service leave --machine --project <id-or-slug>` from anywhere); they write the opt-in list `$XDG_CONFIG_HOME/tasks/service/projects.toml`. `join` refuses a project without a durable id, one whose records are in the store, one whose `.env` or `.env.local` sets the store secret, one whose connection entry leaves a non-secret value to the environment, and one whose slug another joined project has. The machine process is `tasks service run --machine` (or `start --machine`), declared to supervisors in the manifest as `service.machine`; it runs from its state root `$XDG_STATE_HOME/capabilities/machine/tasks/`, loads no project's environment, follows the list without a reload, and starts each project's turns as project mode does, in the project and on its default connection. Its settings are `$XDG_CONFIG_HOME/tasks/service/config.toml` (`max_parallel`, `shutdown_grace_seconds`), written by `tasks service init --machine`; under its cap projects with work get turns in rotation. `tasks service status --machine`, `doctor --machine`, `reload --machine`, `stop --machine [--end-turns] [--force]` and `logs --machine [--project <slug>]` operate it, and every project on the list is `served`, `paused`, `refused` or `error` with the reason, one project's trouble leaving the others served. In a joined project `service start` and `run` exit 4 `joined_to_machine_service` and `service stop` refuses while the machine process serves it; `status`, `reload`, `doctor`, `logs`, `pause`, `resume` and `init` keep working and speak of the machine process. A project that has not joined runs exactly as before. Run `tasks help` SERVICE for the details.

## 2026-10-03 — Running turns outlive the service; `stop --end-turns` ends them

Stopping or restarting the service no longer ends its running turns. However the daemon stops - `tasks service stop`, SIGTERM from a supervisor's restart or unload, SIGINT on a foreground `service run`, a crash - it stops claiming and exits within a tick, and every running turn keeps running and settles its own task. Every turn the daemon starts is recorded in `turns/<id>.json` in its state, and the next daemon to serve the project adopts every recorded turn whose process is still the one recorded: it counts against the lane and project caps, is never claimed twice, appears in `tasks service status` turn rows with `adopted: true`, and its end is logged with exit unknown; a recorded turn that ended meanwhile is logged as ended while unwatched. Every status turn row gains `adopted`. `tasks service stop --end-turns` is now the one act that ends running turns: it waits `shutdown_grace_seconds`, then ends the rest and settles what they held, as `stop` did before. Anything that stops a `tasks` daemon expecting its turns to end must pass `--end-turns`; `--force` ends the turns only with it. Run `tasks help` SERVICE for the details.

## 2026-10-03 — The service serves its project as one slot of a dispatcher

The service is a dispatcher over a set of projects, one slot each, and in project mode the set is the one project it runs in; a project-mode daemon does what it did apart from what follows. Every line of the service log reads `<moment> tasks service [<project-slug>]: <message>`, and every lane and turn `tasks service status` lists carries `project`, the slug; status also gains `state` (`served`, `paused`, `refused` or `error`) and `reason`, and no other field changes. Before it asks the store anything at a wake, and again before it starts a turn, the daemon checks that the project folder and its project.json with the id it serves are there, that tasks is enabled for the project itself, and that the connection is still granted and allows writes outside the read-only switch; while a check fails the project is `refused`, or `error` for a folder that is gone, with the reason in status and once in the log, and nothing is asked or started for it until a check passes, with no restart. The daemon no longer reads the project's `.env` and `.env.local`: each turn reads them itself over the environment the daemon was started with, with the same precedence, so an edit to either reaches the next turn without a restart, and a turn no longer inherits `CLAUDE_PROJECT_DIR`. Run `tasks help` SERVICE for the details.

## 2026-10-03 — The service holds its store connections

The service asks the store its own questions - whether a lane would take work, whether a claim would put something back, the next pickup, whether the store notifies, and bringing it up to this version - over one connection it holds beside the one it listens on, instead of opening a connection per question, so an idle daemon opens no connections after it starts. The store cuts off a question that runs past 30s and the daemon opens that connection again, as it does any connection it loses, after 1s and then at a doubling interval of at most 30s. The listener carries a `select 1` every 2 minutes, and the other connection does when nothing else went over it for as long, so a proxy does not close either as idle. `tasks service status` shows a `stores` list: per store, how many connections the daemon has opened to it, when it last opened one, whether it is listening, and the error that has it away. Turns are unchanged and open their own connections. Run `tasks help` SERVICE for the details.

## 2026-10-02 — Bring a store behind by additive changes up to date without being asked

A store behind this version by additive changes only - a table, a column that is empty or defaulted, a trigger and the function it runs - is brought up to it by the first command that reaches it, read or write, and by the service when it starts listening and at every poll, so installing or updating `tasks` no longer leaves the store behind until someone runs `tasks migrate --apply`. It is applied once, under a lock the store holds for the schema, and reported as one `{"migrated": ...}` line on stderr and in the service log. No backup is taken, because dropping what was added restores the store. A change that is not additive is still applied only by `tasks migrate --apply`, after a backup, and nothing is applied on its own while one is pending; a connection without allow_write, the read-only switch and a role that may not create are served as before. Run `tasks help` STORE for the rule.

## 2026-10-02 — Watch the store's changes over one held connection

`tasks watch [--project ID | --all-projects]` is a read that stays: it holds one connection, listens for the store's change notification, and prints one JSON line per change to a task its scope reads - `task_changed`, `activity_added`, `run_started`, `run_ended` - each carrying the task as a `list` row, with a `ready` line first and a `counts` line after each burst. On a lost connection it reconnects with backoff, catches up what was touched meanwhile and prints `resync`. It exits 0 on SIGTERM or when its stdin closes. The notifications come from new triggers, so a store needs `tasks migrate --apply`; until then `watch` refuses with exit 5 and `doctor` reports the store behind. Run `tasks help` WATCH for the line shapes.

## 2026-10-02 — Pause and resume the service without stopping it

`tasks service pause [--reason TEXT] [<worker>...]` stops the daemon starting new turns, on every lane or on the named ones, while running turns finish and the daemon keeps running; `tasks service resume [<worker>...]` lifts it. The pause is runtime state, so it needs no reload, survives a daemon restart and leaves `service doctor` ok. `tasks service status` shows it. Run `tasks help` SERVICE for the details.
