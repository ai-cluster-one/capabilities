# tasks — change log

## 2026-10-10 — Each project's store is resolved for that project, and a turn uses its daemon's

tasks resolves its store through capabilities-contract 0.4.0 for the project it stands in: the `AGENTKIT_DB_*` keys in the project's `.env.local` / `.env`, then the process environment, then the machine's store setting file. The machine service resolves each project it serves for that project's root as it admits it, and holds one listener and one question connection per distinct store, shared by every project on it; a project that resolves no store is reported refused and asked again rather than stopping the process, and `service run --machine` and `start --machine` no longer refuse on a machine with no store setting. A turn the service starts is handed its daemon's store as `AGENTKIT_DB_*` in its environment and resolves only that level, so it reaches the database its daemon listens on even after an edit to the project's env files; the turn still reads every other key of those files. `tasks run` hands its engine and hooks its store the same way, and any process carrying `TASKS_EXECUTION` resolves only that level, so the agent's own `tasks` commands reach the store its raise lives in. `doctor` reports `store` as the setting in force - its level, sources and where it points, secrets redacted - and `status --machine` names each store's `level` and `sources`. `CAPABILITIES_STORE_URL`, `CAPABILITIES_STORE_PASSWORD` and `AGENTKIT_STORE_URL` are no longer read, and the service's deploy descriptor declares the `AGENTKIT_DB_*` keys instead. A connection carrying the retired `db_*` keys or `secret_env` is no longer refused with `store_in_connection`; those keys are ignored.

## 2026-10-10 — The machine service starts through launchd when launchd supervises it

`tasks service start --machine` hands the start to the launchd job that supervises the machine service when launchd has one loaded, instead of spawning a copy beside it: it runs `launchctl kickstart gui/$UID/<label>`, waits until the process launchd started reports itself running, and answers `"started_by": "launchd"` with the `label`. The machine process learns its job from launchd itself: started by launchd, `service run --machine` writes `launchd.json` into its machine state root with the label `XPC_SERVICE_NAME` names, when launchd reports that job's pid as the process, its parent or its process group, so the label is never composed from a naming convention. `service start --machine --detached` starts a copy by hand even while the job is loaded. Where no job is recorded or loaded - no `launchd.json`, no `launchctl`, or the job booted out - `start --machine` starts a detached copy as before. `service status --machine` carries `supervisor` (`launchd`, `pid`, `last_exit_code`, or null) and, while no machine process runs, a `hint` naming how to start it, which `service doctor --machine` repeats in its problem. `stop --machine` is unchanged and stops whichever process runs.

## 2026-10-09 — `service/store.py` is no longer shipped

The service never read the copy of the records layer the bundle carried as `service/store.py`, and it is gone. Nothing the service does changes.

## 2026-10-09 — `service join` no longer refuses database-mode records

`tasks service join` and the machine service no longer refuse a project with `database_mode_unsupported`: records are kept in files only, and a `project.json` declaring `"store": "db"` is refused by the records layer with `bad_store_mode`.

## 2026-10-09 — The store is the machine's: tasks keeps its tables in the store setting's schema, and a connection names no store

Breaking. tasks no longer reaches PostgreSQL through its connection. Every command, `doctor`, `watch`, the project service and the machine service reach the store the machine's store setting names - set with `capabilities store set`, or AGENTKIT_STORE_URL or CAPABILITIES_STORE_URL for a test or a development session - through the shared database library, `capabilities-contract`, which the script header now pins. The tables live in the schema the setting binds, renamed `tasks_tasks`, `tasks_activities`, `tasks_changes` and `tasks_executions`, with their functions `tasks_touch_updated_at`, `tasks_notify_claimable` and `tasks_notify_watch` and every index, constraint and trigger named `tasks_*`, under tasks' own migration ledger beside every other tool's tables. The notification channels `tasks_claimable` and `tasks_watch` and their payloads are unchanged; a payload's `schema` is the bound schema. With no store configured every command, `doctor`, `service run`, `service start` and `service doctor` refuse with exit 6 `store_not_configured`, naming `capabilities store set`.

The connection names no store. `db_host`, `db_port`, `db_user`, `db_name`, `db_sslmode`, `db_schema` and `secret_env` leave the connection keys and `TASKS_DB_PASSWORD` leaves them and the service's deploy environment, which now takes CAPABILITIES_STORE_URL and CAPABILITIES_STORE_PASSWORD instead. A connection that still carries any of those keys is refused with exit 6 `store_in_connection`, naming the keys and `capabilities store set`, by every command, `doctor`, `service join` and the check the service makes before every action; it keeps its `timezone`, `allow_write` and grants. The machine service holds one listener and one question connection for every project it serves, and `service join` no longer refuses `project_secret_set` or `connection_incomplete`.

`tasks migrate` and `tasks migrate status` are the contract's: `migrate` applies the steps the tables lack under the library's lock, `migrate status` reports `pending`, `current` or what `migrate` would refuse without a lock, the manager runs `migrate` when it installs or updates tasks, the service runs it once as it starts, and any other command that finds the tables missing or older brings them up once, saying `{"migrated": {"schema", "applied"}}` on stderr. `manifest` reports `tables: true`. `migrate --apply`, its `would_*`, `backfilled` and `rested` answers, the catch-up a command made before it was served, `schema_behind`, and `doctor`'s `tables`, `behind`, `blocked_by_in_metadata` and `in_progress_stored` are gone with `schema.sql`; `doctor` answers `store` - where the setting was read and its schema - and `tables`, where they stand.

The first step moves a store the previous release kept in schema `tasks` into the bound schema whole: the four tables and the three functions are moved and renamed, not copied, so every id, trail entry, recorded move, raise and open lease is the one it was, and the emptied schema `tasks` is dropped. It moves only from the previous release's shape - every column it added, no task stored as `in_progress`, no `blocked_by` left in a task's metadata - and only into a schema that does not already hold `tasks_tasks`; otherwise `migrate` refuses, changes nothing and names the previous release's `tasks migrate --apply`.

To upgrade: run the previous release's `tasks migrate --apply` if `tasks doctor` there still warned of anything; stop the tasks service; set the machine's store with `capabilities store set`, naming the database that holds schema `tasks`; remove `db_host`, `db_port`, `db_user`, `db_name`, `db_sslmode`, `db_schema` and `secret_env` from every connection in `capabilities/tasks/connections.json`, and `TASKS_DB_PASSWORD` from the env files; run `tasks migrate`, which moves schema `tasks` into the store's schema; then start the service again. Run `tasks help` STORE for the contract.

## 2026-10-07 — `in_progress` is shown while an open raise holds a task and never stored; each raise has one lease writer

A claim now opens a raise and writes nothing to the task: its status, assignee, pickup and `blocked_by` stay where they rest, no move is recorded in its history, and `updated_at` does not move. Every reader derives `in_progress` from one rule - an open raise holds the task, a raise still running whose lease has not run out: `show`, `list` and `search` rows with or without `--full`, `ready`, `counts`, a `watch` line's row and its counts line, and the task in the answers of `claim` and `release`. `--status in_progress` on `list`, `search`, `ready` and `counts` finds exactly the tasks an open raise holds, and `--status todo` or `waiting` the tasks resting there that none holds. The words printed are the ones printed before - `draft`, `todo`, `in_progress`, `waiting`, `complete`, `closed`. Once the raise ends the task shows the status it rests in, which is where the claim found it unless the work moved it. A raise whose lease ran out shows its task as resting at once, before a claim sweeps it.

Since nothing moved the task, nothing puts it back. A raise that ends without a move - failed, cut off, closed as abandoned when its lease lapsed or `service stop --end-turns` ended its turn, or handed back with nothing named - leaves the task exactly where it rested, a task taken from `waiting` still waiting. The lapsed-lease sweep only closes the raise. `release` closes the raise and moves the task only to the `--status` it is given and to the new `--assignee`, judged as before, a move into `waiting` naming whom it waits for or refused with exit 6 `input` rather than landing in `draft`; `--outcome ok` with no `--status` keeps completing the task, the one landing kept for a claim worked by hand, while `--outcome failed` no longer returns it to `todo` and `--outcome handback` no longer moves it to `waiting` or `draft`, and the answer no longer carries `instead_of_waiting`. `run` closes its raise without moving the task, scoring it against where the task rested when it was claimed: ended, ok; moved to `waiting` or `draft`, or a wait passed to another name, handback; a pickup it set still ahead, ok marked `waiting`; a new `stage` or assignee in `todo`, ok marked `handoff`; moved from `waiting` to `todo`, ok; and where it rested, failed and marked `cut_off`, so the same worker's next raise continues that session - including a turn that set the status it found, since that moves nothing. A park, at the attempts ceiling without an escalation chain or for a worker missing a profile or routine, is the one move a run still makes: to `waiting` on its assignee, or to `draft` when it names nobody or was waiting. A waiting task an open raise holds is not returned to `todo` by the wait sweep while it is held.

Each raise has exactly one lease writer. A turn the service started - the one `tasks run` handed a receipt to write - renews nothing: on the same beat it reads the lease the service last wrote, and ends itself as `lease_lost` when the store says the raise is no longer running or its lease ran out, or when the lease last known runs out with no reading reaching the store, `lease_lost` then saying the service renews it no longer. The service is that lease's one writer, on its beat and just before it starts any turn, renewing to the `limits.lease_seconds` the turn's receipt now states, or its worker file's for a receipt that states none. A `run` started by hand renews its own lease as before, and `claim` by hand renews nothing. A turn whose service stops keeps its raise only within the lease last written: a daemon serving the project again before it runs out adopts the turn and renews it, and a turn no daemon adopts ends itself when it runs out, its task where it rested; until now such a turn ran on to its end on its own beat.

A store may still hold tasks a claim or a person stored in `in_progress`, which no claim takes. `tasks migrate --apply` returns each, store-wide and in the same transaction, to the status it rests in: the one it stood in before its latest move into `in_progress` as its history records it, the status a claim took it from or the one a person moved it from by hand - `todo` when its history records no such move, and `draft` where it would wait on nobody - with a status row by actor `tasks:migrate` and the touch trigger held off. It answers `rested` by project with counts by status, `by_hand` naming who moved each there, and `without_record`; a second run moves nothing. `tasks migrate` without --apply reports the same under `would_rest`, and `tasks doctor` names the project's own under `in_progress_stored` with a warning. Run it while no turn of an earlier version runs, since such a turn still lands its task by the status it finds. No column or table is added. Run `tasks help` EXECUTION, ONE TURN OF THE CONVEYOR, SERVICE, COLLECTIONS, WATCH and STORE for the contract.

## 2026-10-07 — `blocked_by` is a field of its own, validated when written and honoured on every open task

A task's blockers move out of its metadata into `blocked_by`, a column of task ids on the task. `add` and `set` take `--blocked-by <task>[,<task>...]`, each a key in the task's project or an id in any project, kept by id, once each and in the order given; `set` replaces the whole list, and `--clear blocked-by` empties it. A write is refused with exit 4 `policy` before anything is written when a name is no task - a key names a task only in its own project, so another project's task is named by id - when the list names the task itself, or when a blocker waits on it in turn through blockers still open; a draft is accepted. The claim now honours it on every open task: no claim, by the service or by hand, takes a task in `todo` or `waiting` while its `blocked_by` lists a task that has not ended or an id that names no task, `claim --key` and `run --key` refuse one, naming the blockers, and `ready` leaves it out; a blocker that ended, complete or closed, holds nothing and stays listed. A waiting task returns to `todo` on its own when every blocker has ended, as before, and entering `waiting` still empties a list whose blockers have all ended unless the same call names them. The claim scan's blocker dead ends - an id naming no task, the task itself, a draft, a cycle - now read the field and apply to `todo` as well as `waiting`, and an escalation empties the field as it let go of the metadata key, naming the blockers still open by key in its entry. A worker's `writes` answers for the field under `metadata` naming `blocked_by`, as before: giving blockers to a task that lists none is an addition any worker may make, replacing or emptying them needs the scope, and a frame whose scope names it tells the turn to use `set --blocked-by`.

A store gains the empty column from the next command, as any additive change. `tasks migrate --apply` then moves, in the same transaction and store-wide, every `blocked_by` a task kept in its metadata into the field - ids as they are, keys resolved in the task's own project - and removes it from the metadata, with the touch trigger held off so no task reads as having moved; it answers `backfilled` with counts by project. A name that resolves to no task, and a value that is not a list, stays in the metadata, where nothing reads it, and is listed under `backfilled.by_project` and named by `doctor` under `blocked_by_in_metadata` with a warning; running it again moves nothing more. `tasks migrate` without --apply reports the same under `would_backfill`. Until `migrate --apply` runs, a blocker left in the metadata holds nothing. A command that cannot bring a store up to date - a read-only connection, a role that may not create - reads every task as blocked by nothing and refuses a write of blockers with exit 6 `schema_behind`.

Every `tasks list` and `tasks search` row, with or without `--full`, carries `blocked_by` as the ids the field lists, empty rather than null when there are none, and `blocked_by_status` keyed by those ids, null for an id that names no task. `show` and every task row print the field as `blocked_by`.

Deprecated, for one release: `tasks meta set <task> blocked_by '[...]'` writes the field with the same names and refusals as `set --blocked-by`, and `tasks meta rm <task> blocked_by` empties it; both answer `deprecated`, say it on stderr, and stop taking the key in the next release. A value that is not a list of names is refused with exit 6. For the same release every task row whose metadata holds no `blocked_by` of its own shows the field's ids there too, so a reader of `metadata.blocked_by` still finds them; read the top-level `blocked_by` instead. Run `tasks help` FIELDS, METADATA VALUES, DEAD ENDS and STORE for the contract.

## 2026-10-07 — A task that can never move is escalated by any claim, and a write that would leave one there is refused

A run's first claim - of any worker of the project, by hand or by the service - now scans the project's open tasks in one read, after the sweeps, for dead ends decided from the store and the worker files alone: a task in `todo` or `waiting` on a name that is a worker here that no enabled, readable worker takes there by status, type, assignee and tags, which is also what a task on a worker switched off or on an unreadable worker file comes to, a worker's `on_request` types counting as taken and a waiting task whose wait ends on its own by its pickup or blockers counting as taken by a worker that takes it in `todo`; a task every taker of which names a profile or routine that is not there; and a waiting task whose `blocked_by` names no task, names a draft, or waits on it in turn through blockers still open. A task on a person or on nobody, and one an open raise holds, is never one. In a project that sets an escalation chain each is escalated at once, with the rule and its particulars as the entry's why, so a task whose worker cannot run is escalated rather than claimed and parked; without a chain nothing moves and `run` names each under `dead_ends`, as does the service's log line. A task named with --key is left to that run. The service starts a claim at its poll for a dead end its project's chain would move, as it does for a lapsed lease. An escalation now lets go of the task's `blocked_by` as it lets go of its pickup, naming in its entry the blockers still open, because a waiting task with open blockers is taken by no worker's filter and would be hidden from the name it went to. `add`, `set` and `release` refuse with exit 4 `policy` a write that would leave a task in `todo` or `waiting` on a worker name no enabled worker takes there, naming the rule and what that worker takes; a person's name is still any name, and a task of another project is not judged. `meta set` refuses with exit 4 a `blocked_by` naming something that is no task or closing a cycle, and `add`, `set` and `release` refuse `in_progress` to every writer, since only a claim opens the raise that holds a task there. `tasks doctor` lists on each worker, as `lands_untaken`, every place its `writes.held` lets its turn land the task it holds - `todo` or `waiting` on a worker name - that no enabled worker takes, and warns of it. The watch trigger no longer announces a hold episode's row as `run_started`, and a store whose trigger function predates that reads as behind and is brought up to it by the next command. No column or table is added. Run `tasks help` ESCALATION for the contract.

## 2026-10-07 — Two handler points speak one vocabulary; a hold writes nothing to the task; usage limits hold the lane; one cool-down

A worker's `before` and `after` hooks are the conveyor's two handler points and answer in one vocabulary by their exit: 0 go; 75 hold, until the moment on the last stdout line when it prints one; 76 escalate at once along the project's chain, the last line the reason; any other ending - another exit, a timeout, a command that cannot start - a hold with no moment, and escalate where the project sets no chain, or the chain goes nowhere, is a hold too. A `before` hold writes nothing to the task any more: no pickup, no history row, no `updated_at`; `run` and the service's log name it under `passed_over` with `verdict` `hold`, `until` when there is a moment, `said` and `why`, replacing the verdicts `defer` and `skip` and `pickup_set`, and the service remembers it and starts no turn for the task before the moment, or before its next poll. With an escalation chain, a task whose raises in place reached the worker's attempts is escalated before its hook is asked, and how long a task has been held back is counted from the first hold in its place rather than from its last move, so a task that waited its turn is not escalated at its first hold: that first hold is recorded as one row among the task's raises, marked `hold` in its metrics, which is no raise - `runs`, the scan's `runs`, attempt numbers, raises in place and resumes leave it out - and it stops counting, with nothing written, once a raise starts on the task, the task moves, or its lane is held after it began. The `after` hook is now also given TASKS_RAISE_DETAIL, TASKS_RAISE_METRICS, TASKS_HARNESS_EXIT, TASKS_HARNESS_FAILURE and TASKS_HARNESS_SAID, and its answer applies: hold holds the worker's lane - no claim of that worker, the service's or by hand, takes a task until the moment, or for its cool-down without one - recorded on the raise as `metrics.lane_hold` and reported as `lane_held`, so it holds across a service restart; escalate moves the task unless it ended; a failing hook, which used to change nothing, now holds the lane for the worker's cool-down, and is still noted as `after_hook`. Shipped after-raise handlers read Claude Code's and Codex's usage-limit sentences - the five-hour and weekly limits alike - and hold the lane until the reset they name and a minute more, at most eight days ahead, or for 30 minutes when they name none or the harness is not logged in; such a raise is marked `exhausted` and is no attempt, and the lane's tasks run no stall clock while it is held. These replace the exhaustion hold, which set a task's pickup, and the service's retry delay with one cool-down derived from the last raise: a task whose last raise failed or was abandoned is not claimed again, by the service or by hand, until the worker's new `limits.cool_down_seconds` (60 unless set) has passed; `--key` is not held by it or by a lane hold. `limits.hold_seconds_on_exhaustion` is read as `cool_down_seconds`, a service settings file's `retry_delay_seconds` still loads and is read as the cool-down of workers that name none, and `doctor` and `service doctor` name both as deprecated; `service status` no longer shows `retry_delay_seconds`, and its `deferred` lists the hooks' holds. The schema is unchanged apart from a table comment. Run `tasks help` HOOKS and ESCALATION for the contract.

## 2026-10-06 — A task its worker cannot move is escalated along the project's chain to a person

A project may name `capabilities/tasks/conveyor.toml` beside its workers, with `escalate_to`, an ordered list of names whose last is a person (a name no worker file has), and `stall_after`, a duration, 6h unless set. With it, a worker's claim - `tasks run`, by hand or by the service - escalates a task instead of taking it in two cases: its `before` hook holds the task back, by deferral or skip, after it has been refused longer than `stall_after`, and then no deferral is set; or its raises in place, the raises that started since its status or assignee last moved and have ended, except those marked `exhausted`, have reached the worker's `limits.attempts`, which then counts raises in place instead of the whole-life count that parks a task. How long a task has been refused, since when it stood in place and its raises in place are derived from the task's history and raises, and the schema is unchanged. Escalating moves the task to `waiting`, its pickup let go, on the name after its assignee in the chain, or the first name when its assignee is not in it, with one trail entry and the history rows by actor `tasks:scan` naming the reason - the hook's last line, or the attempts and `park_hint` - since when it stood in place and its raises in place; a task assigned to a person is never escalated. Only the claim of the task's own taker escalates it, so a task waiting its turn in a busy lane, or in a paused lane, is never escalated, and `tasks service status` gains `pause.waited`, each paused lane's oldest due task and how long it has waited. `run` reports each move under `escalated`, `would_escalate` without --apply, and the service's log line names it; a task named with --key that its claim escalates is refused with exit 6 after the move. `tasks doctor` shows the settings as `escalation`, refuses with exit 6 `conveyor_invalid` a chain ending at a worker, naming before its end a name that is no worker here, or naming a worker that is off or takes no waiting task assigned to it, and warns a project with enabled workers and no chain; a file that cannot be read refuses `run` the same way. A project without the file runs exactly as before. Run `tasks help` ESCALATION for the contract.

## 2026-10-06 — The service keeps the lease of every live turn it started

The tasks service now renews the lease of the raise each of its running turns reported, as a second beat beside the turn's own: on the turn's beat, and again just before it starts any turn, since every claim sweeps lapsed leases. It renews only for a turn whose process is still the one it recorded, only a raise still running and opened by that turn's execution on the task it reported, to the same short lease and never past `limits.lease_seconds` from the claim, and never shortens a lease or reopens a closed raise. A turn whose own beat stalls while its process lives therefore keeps its task, and a lease lapses only once both the turn and the service are gone. A renewal that fails is said once in the service log and tried again. Nothing else changes. Run `tasks help` ONE TURN OF THE CONVEYOR for the details.

## 2026-10-06 — A scan carries each task's runs, their cost and its blockers

Every row of `tasks list` and `tasks search`, with or without `--full`, gains `runs` - `{count, by_worker, cost_usd, without_cost}`: every raise of the task in all and by worker, the sum of the `cost_usd` its raises' metrics recorded (null when none did), and how many recorded none - plus `blocked_by`, the metadata key as stored, and `blocked_by_status`, mapping each name it lists to the status of the task it names, null for a name matching no task. A `tasks watch` line's task row, being a `list` row, carries them too. They are computed in the scan's own query, so a page is still one query. Existing fields are unchanged. Run `tasks help` COLLECTIONS for the fields.

## 2026-10-06 — A turn that lost its raise is ended instead of working on unclaimed

The beat of `tasks run` keeps time by whichever of the wall clock and the monotonic clock has moved further, so a machine that slept renews when it wakes rather than a whole beat later, and a wall clock set back holds back no renewal. A turn whose raise is lost - the store answers that it is no longer running or that its lease has run out, or the lease the last renewal wrote runs out with no renewal reaching the store - is ended at once with everything it started, instead of working on for up to its timeout on a task that was put back and with every write refused. `run` says `{"lease_lost": {...}}` on stderr, its answer carries `lease_lost` with the reason, and the raise's detail, when it can still be closed, begins `lease lost:`. A renewal that fails is still tried again within seconds on a new connection, and each failure is now said on stderr as `{"beat_failed": {...}}` and counted in the answer's `beat_failures`. The service's log line for a turn names `lease_lost` and `beat_failures`. Run `tasks help` ONE TURN OF THE CONVEYOR for the details.

## 2026-10-06 — A store outage, a dead turn and a raise left open no longer stall a lane

A command that cannot reach the store - every verb a worker's turn calls, and `tasks run` itself - no longer exits 5 at once: it asks again after 1s, then at a doubling interval of at most 30s, for the window `TASKS_STORE_RETRY_SECONDS` names, 180 unless set and resolved as a connection value is, says so once on stderr as `{"store_away": {...}}`, and exits 5 `unreachable` only once the window is spent; 0 asks once. A store that answers and refuses the role, password or database is refused at once, and `tasks doctor` never waits. `tasks run` now holds its task by a short lease from the claim and renews it from a thread of its own while its process lives - every sixth of the window, between 2s and 30s apart, to the window and three beats more, 270s unless the window is changed - never past `limits.lease_seconds` from the claim, which keeps its meaning as the longest a raise may hold its task. A turn whose process is killed or crashes is therefore closed as abandoned and its task put back by the next claim within minutes instead of hours, the way any lapsed lease is, while a store outage shorter than the window lapses no live turn. A claim no longer fails with a unique-key conflict on a task in todo or waiting that an open raise still holds: it passes the task over, names it under a new `passed_over` entry with verdict `held`, the raise and until when its lease runs - in `claim` and `run` answers and the service's log line - and takes the next one; `claim --key` and `run --key` naming such a task refuse with exit 6 `conflict` naming the raise. `claim` by hand renews nothing and holds the lease it is given. Run `tasks help` STORE, ONE TURN OF THE CONVEYOR and EXECUTION for the details.

## 2026-10-05 — A hook deferral leaves no row in the task's history

A worker's `before` hook that defers a task - exit 75 with a moment on its last line - still sets the task's pickup to that moment, and no longer records the move in the task's history: the row it wrote, with actor `hook:<worker>`, was written every time a lane was held and carried nothing a reader needed. The trail is unchanged, it never had an entry, and `run` and the service log still name each deferral under `passed_over`. Rows such a deferral wrote before this version stay in the store until removed. Run `tasks help` HOOKS for the contract.

## 2026-10-03 — Find the task a run was for, for many runs in one call

`tasks runs --run SYSTEM:REF [--run ...] [--since WHEN] [--project ID | --all-projects]` goes from runs to the raises they were: given the handles a harness knows its runs by - `--run claude:<session id>`, repeating - or a period with `--since`, it answers `{"runs": [...]}`, one row per matching raise, oldest first, each carrying `execution`, `task_id`, `project_id`, `unique_key`, `title`, `worker`, `status`, `started_at`, `ended_at`, `run_system` and `run_ref`. Its scope is the one `list` reads, and `--all-projects` reads every project in the store. A run no raise names answers no row and is not an error, and the call is one query on one connection however many runs it names. The schema gains the index `task_executions_run_idx` on `(run_system, run_ref)`, added beside what is there, so a store without it is brought up to it by the first command that reaches it. `tasks runs <task>` is unchanged. Run `tasks help` RUNS for the contract.

## 2026-10-03 — A store connection the path dropped no longer holds the service or a turn

A connection whose path to the store dropped while the store never closed it - a laptop that slept, a network that went away - used to leave the daemon, or a turn, waiting on its answer for ever, and a SIGTERM was not taken while it waited. The daemon now severs its question connection, or its listener's round trip, when no answer is back within 45s, counts the connection lost and asks for it again as it does any lost connection, so it keeps waking at its poll and a stop is taken within that bound. Every store connection, a turn's and every command's included, carries TCP keepalives, and where the platform has it a one-minute bound on data left unacknowledged. `tasks service doctor` fails when the running daemon's planned wake is overdue by more than twice that bound, since nothing else keeps it from its wake. Run `tasks help` SERVICE for the details.

## 2026-10-03 — One machine process can serve every project that joins it

The service gains a machine mode: one process on the machine serves every project that opted in, each as its own slot, so the projects on one machine share one process, one listener and one question connection per store, and an optional cap on the turns they run at once. A project opts in with `tasks service join`, run in a project that enables tasks for itself, and leaves with `tasks service leave` (or `tasks service leave --machine --project <id-or-slug>` from anywhere); they write the opt-in list `$XDG_CONFIG_HOME/tasks/service/projects.toml`. `join` refuses a project without a durable id, one whose records are in the store, one whose `.env` or `.env.local` sets the store secret, one whose connection entry leaves a non-secret value to the environment, and one whose slug another joined project has. The machine process is `tasks service run --machine` (or `start --machine`), declared to supervisors in the manifest as `service.machine`; it runs from its state root `$XDG_STATE_HOME/capabilities/machine/tasks/`, loads no project's environment, follows the list without a reload, and starts each project's turns as project mode does, in the project and on its default connection. Its settings are `$XDG_CONFIG_HOME/tasks/service/config.toml` (`max_parallel`, `shutdown_grace_seconds`), written by `tasks service init --machine`; under its cap projects with work get turns in rotation. `tasks service status --machine`, `doctor --machine`, `reload --machine`, `stop --machine [--end-turns] [--force]` and `logs --machine [--project <slug>]` operate it, and every project on the list is `served`, `paused`, `refused` or `error` with the reason, one project's trouble leaving the others served. In a joined project `service start` and `run` exit 4 `joined_to_machine_service` and `service stop` refuses while the machine process serves it; `status`, `reload`, `doctor`, `logs`, `pause`, `resume` and `init` keep working and speak of the machine process. A project that has not joined runs exactly as before. Run `tasks help` SERVICE for the details.

## 2026-10-03 — Running turns outlive the service; `stop --end-turns` ends them

Stopping or restarting the service no longer ends its running turns. However the daemon stops - `tasks service stop`, SIGTERM from a supervisor's restart or unload, SIGINT on a foreground `service run`, a crash - it stops claiming and exits within a tick, and every running turn keeps running and settles its own task. Every turn the daemon starts is recorded in `turns/<id>.json` in its state, and the next daemon to serve the project adopts every recorded turn whose process is still the one recorded: it counts against the lane and project caps, is never claimed twice, appears in `tasks service status` turn rows with `adopted: true`, and its end is logged with exit unknown; a recorded turn that ended meanwhile is logged as ended while unwatched. Every status turn row gains `adopted`. `tasks service stop --end-turns` is now the one act that ends running turns: it waits `shutdown_grace_seconds`, then ends the rest and settles what they held, as `stop` did before. Anything that stops a `tasks` daemon expecting its turns to end must pass `--end-turns`; `--force` ends the turns only with it. Run `tasks help` SERVICE for the details.

## 2026-10-03 — The service serves its project as one slot of a dispatcher

The service is a dispatcher over a set of projects, one slot each, and in project mode the set is the one project it runs in; a project-mode daemon does what it did apart from what follows. Every line of the service log reads `<moment> tasks service [<project-slug>]: <message>`, and every lane and turn `tasks service status` lists carries `project`, the slug; status also gains `state` (`served`, `paused`, `refused` or `error`) and `reason`, and no other field changes. Before it asks the store anything at a wake, and again before it starts a turn, the daemon checks that the project folder and its project.json with the id it serves are there, that tasks is enabled for the project itself, and that the connection is still granted and allows writes outside the read-only switch; while a check fails the project is `refused`, or `error` for a folder that is gone, with the reason in status and once in the log, and nothing is asked or started for it until a check passes, with no restart. The daemon no longer reads the project's `.env` and `.env.local`: each turn reads them itself over the environment the daemon was started with, with the same precedence, so an edit to either reaches the next turn without a restart, and a turn no longer inherits `CLAUDE_PROJECT_DIR`. Run `tasks help` SERVICE for the details.

## 2026-10-03 — The service holds its store connections

The service asks the store its own questions - whether a lane would take work, whether a claim would put something back, the next pickup, whether the store notifies, and bringing it up to this version - over one connection it holds beside the one it listens on, instead of opening a connection per question, so an idle daemon opens no connections after it starts. The store cuts off a question that runs past 30s and the daemon opens that connection again, as it does any connection it loses, after 1s and then at a doubling interval of at most 30s. The listener carries a `select 1` every 2 minutes, and the other connection does when nothing else went over it for as long, so a proxy does not close either as idle. `tasks service status` shows a `stores` list: per store, how many connections the daemon has opened to it, when it last opened one, whether it is listening, and the error that has it away. Turns are unchanged and open their own connections. Run `tasks help` SERVICE for the details.

## 2026-10-02 — Bring a store behind by additive changes up to date without being asked

A store behind this version by additive changes only - a table, a column that is empty or defaulted, a trigger and the function it runs - is brought up to it by the first command that reaches it, read or write, and by the service when it starts listening and at every poll, so installing or updating `tasks` no longer leaves the store behind until someone runs `tasks migrate --apply`. It is applied once, under a lock the store holds for the schema, and reported as one `{"migrated": ...}` line on stderr and in the service log. No backup is taken, because dropping what was added restores the store. A change that is not additive is still applied only by `tasks migrate --apply`, after a backup, and nothing is applied on its own while one is pending; a connection without allow_write, the read-only switch and a role that may not create are served as before. Run `tasks help` STORE for the rule.

## 2026-10-02 — Watch the store's changes over one held connection

`tasks watch [--project ID | --all-projects]` is a read that stays: it holds one connection, listens for the store's change notification, and prints one JSON line per change to a task its scope reads - `task_changed`, `activity_added`, `run_started`, `run_ended` - each carrying the task as a `list` row, with a `ready` line first and a `counts` line after each burst. On a lost connection it reconnects with backoff, catches up what was touched meanwhile and prints `resync`. It exits 0 on SIGTERM or when its stdin closes. The notifications come from new triggers, so a store needs `tasks migrate --apply`; until then `watch` refuses with exit 5 and `doctor` reports the store behind. Run `tasks help` WATCH for the line shapes.

## 2026-10-02 — Pause and resume the service without stopping it

`tasks service pause [--reason TEXT] [<worker>...]` stops the daemon starting new turns, on every lane or on the named ones, while running turns finish and the daemon keeps running; `tasks service resume [<worker>...]` lifts it. The pause is runtime state, so it needs no reload, survives a daemon restart and leaves `service doctor` ok. `tasks service status` shows it. Run `tasks help` SERVICE for the details.
