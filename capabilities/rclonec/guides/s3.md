# Wiring a connection to S3 and the S3-compatible stores

The S3 family is the easy case: a key and a secret, no OAuth, no application to register anywhere. One backend type reaches AWS and several dozen compatible providers, which differ only in a `provider` name and an endpoint.

```json
{
  "type": "s3",
  "options": {"provider": "<provider>", "region": "<region>",
              "endpoint": "<endpoint url>"},
  "secret_env": {"access_key_id": "<ENV_KEY>", "secret_access_key": "<ENV_KEY>"},
  "allow_write": false
}
```

AWS itself needs no endpoint — region is enough. Every other provider is selected by name and usually wants its own endpoint; `rclone help backend s3` prints the current provider list and what each one expects, and [rclone's S3 documentation](https://rclone.org/s3/) carries the per-provider detail.

A bucket is addressed as a path under the remote, so `<remote>:` lists buckets and `<remote>:bucket/prefix` reaches into one. To pin a connection to a single bucket, put it in the path you use rather than in the connection — or give the key itself a policy that reaches nothing else, which is the only limit that actually binds.

Prefer a key scoped by policy at the provider over a broad key held read-only here. `allow_write: false` stops this capability from issuing a write; it does not stop anything else on the machine that has the same key.

## The other key-and-secret backends

Backblaze B2, Cloudflare R2, Wasabi, MinIO, DigitalOcean Spaces, Hetzner, Scaleway, Storj and the rest are reached the same way — most through `s3` with their own `provider`, a few through their own backend type. `rclone help backends` lists every type the installed binary speaks, and `rclone help backend <type>` prints that one's options.

SFTP and WebDAV follow the same shape with a host, a user, and either a password or a key.
