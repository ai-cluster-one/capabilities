# deployment — change log

## 2026-10-28 — `node image` names the standard image's current release, and `node add` and `node create` default to it

`deployment node image [--json]` reads the registry of `ghcr.io/agenium-dev/agent-node` anonymously and answers its newest `<major>.<minor>.<patch>` tag, the release that publishes the image and moves `:latest` to it: the image reference alone, or with `--json` `{ok, version, image}`. A registry that cannot be read or holds no release exits 5 `image_release_unknown`. `node add` and `node create` take `--version` as optional and, without it, create the node from that release; a `node add` that resumes on a node it already made reads no registry. An explicit `--version`, `--repository` builds and `node update` answer and refuse as before.

## 2026-10-27 — `node add` takes a node from nothing to raised, step by step

`deployment node add <label> --server <uuid> --version <tag> [--memory <size>] [--services <name,...>] [--project <uuid>] [--environment <name>] [--connection <id>] [--wait <s>] [--events]` runs the whole path of adding a node on a server Coolify already runs: the Coolify project (given, else the one named after the agent, created when missing), the environment in it (created when missing, through `coolify projects environment create`), the node of the standard image as `node create` makes it, a wait until its container runs, then enrolment as `node enrol` does it. With `--events` each step is a `step` JSON line, started then done with its check or failed with its error, and the stream ends in `done` or `error`. A step that finds its work done keeps it, so running the same command again resumes after a failure. `node create` and `node enrol` answer and refuse as before.

## 2026-10-27 — `node login <node>` signs a tool or a device in on a node, as events

`deployment node login <node> claude|codex|gh --events` runs the tool's own headless sign-in (`claude auth login`, `codex login --device-auth`, `gh auth login --web` for github.com) in the node's container, reached as `node exec` reaches it, and speaks it as JSON lines on stdout: `link {url}`, `code {code}` (codex, gh), `code_needed` where claude asks for the page's code back (one line on stdin), `waiting`, then `done {result {ok, node, tool}}` or `error {exit, error {code, message}}` - `login_failed` with the tool's last words and exit code, `input_closed`, `node_unreachable`. SIGTERM, SIGINT or SIGHUP cancels it: the tool on the node is stopped and the stream ends in `cancelled` (exit 6).

`deployment node login <node> <capability> [--connection <id>] [--method <id>] --events` signs a device-bound connection (telegram, whatsapp) in on the node as a new device through the capability's own link ceremony, passed on as it speaks it, after one `devices` event naming the agent's other nodes the store reports holding a live session for the connection and the service's device limit (4 for WhatsApp). It never replaces a session: a node already live for the connection is refused (`already_signed_in`), `--recreate` is never passed, and a connection with no `expected_account_id` that another node holds a session for is refused (`connection_unbound`, naming the account to bind) since a failed first link would remove the shared connection.

`deployment node login claude|codex [--target <name>] [--print-command]` is unchanged; a harness other than claude or codex there is now refused with exit 6 `input` rather than by the argument parser.

## 2026-10-27 — `node update --memory` changes a node's memory limit

`deployment node update <node> --version <tag> --memory <size>` writes the node's Compose document with that memory limit instead of the one its container runs with, and redeploys the node, also when it already runs the tag; before, a node kept the limit `node create` gave it unless its Compose was edited by hand. The size is taken as `node create` takes it, and a malformed one is refused with exit 6 `input` before anything changes. A size equal to the running limit changes nothing, and without `--memory` the running limit is kept as before. The answer's `memory` is the limit written.

## 2026-10-26 — A box runs a service that has only a machine form

In store mode a container box now carries every installed service that declares a machine command (`service.machine`) and no project one (`service.deploy`), less `capabilities.exclude`, embedded whatever the runtime's shape, since it has no container of its own: it is listed in `embedded_services` and on the node service manager's `capabilities node run --services` list, so a placement on the node starts its `<name>.machine` program there. Before, only services with `service.deploy` reached that list, and such a service placed on a box ran nowhere. A host profile compiles none of them.

## 2026-10-26 — `machine handover` hands the machine services' agents to the node manager

`deployment machine handover [<name> ...] [--dry-run]` boots out each loaded `capabilities.machine.<name>` agent `machine sync` compiled - the named ones, or every compiled one when none is named - and takes its entry out of `~/Library/LaunchAgents`, as `deployment handover` does a project's agents, so the node manager's job for that service (`capabilities node install`, which runs it) is not left waiting on it; the machine watchdog goes with them once no other machine service agent stays loaded. The compiled files stay. It answers `{dry_run, ok, agents_dir, agents}` in `handover`'s shape and exits 6 when an agent could not be handed over; without --dry-run it is stopped by the read-only switch.

## 2026-10-26 — `node exec` forwards piped standard input to the command on the node

`deployment node exec <node> -- <command>` hands what is piped into it to the command run in the node's container, so `printf x | deployment node exec <node> -- cat` prints `x` and a value piped to `setup set --stdin` arrives. Every command the node verbs run before or beside their own - `capabilities`, `coolify`, `ssh` and the rest - now reads no standard input unless it is given some: before, the container lookup over SSH inherited the caller's pipe and drained it, so the command ran with an empty input and exited 0.

## 2026-10-26 — `node enrol` gives a node the agent's key instead of each secret its vault holds

`deployment node enrol` writes the agent's `AGENT_ENCRYPTION_KEY`, as it resolves here, into the node's `~/.config/capabilities/shared.env` on its config volume, on standard input, so the node opens the agent's vault in the store (`capabilities secrets`) and no secret the vault holds is copied to it. A secret kept only in a file or the environment here is still written into the capability's `credentials.env` on the node, as before. The answer carries `key {placed, fingerprint}` and `secrets_in_vault`, the names per capability that were left to the vault, which `secrets_skipped` no longer lists. A key here that is not the one the agent's vault is kept under is refused (exit 6 `key_mismatch`) before anything is written to the node. Needs capabilities-contract 0.25.

## 2026-10-26 — The agent-node guide says a node runs its scripts from the store

The agent-node guide says a node raised from the store holds no checkout of the agent's repository, so a tasks worker's hooks are stored hooks and an automation's script a stored body.

## 2026-10-26 — `deployment node update` writes the node's whole Compose document instead of reading it

`deployment node update` no longer reads the node's Compose document from Coolify, which a token without read:sensitive cannot (`compose_hidden`): it writes the service the whole document `node create` writes for it - the Compose service `agent`, node create's volume names, this agent's `CAPABILITIES_PROJECT_ID` and `CAPABILITIES_PROJECT_ID_ROOT`, the memory limit the node's container runs with, and the new tag - through `coolify service set-compose`, then redeploys it. Before writing it reads the node's one agent container over SSH with `docker inspect` and refuses with exit 6, changing nothing, when a volume the document mounts is not the one mounted at that path (`<resource>_<name>`) or the container mounts anything else but the image's anonymous volumes (`node_volumes_unconfirmed`), or when the container has no memory limit, more or fewer than one agent container exists, or its environment sets other keys than those two besides the image's own, Coolify's and a retired identity key the node no longer needs (`node_document_unconfirmed`, naming keys, never values). A retired `AGENT_NODE_NAME` or `AGENT_NODE_ID` is dropped and named in the new `env_dropped`; the answer adds `memory`, and `previous_image` is the image the container ran. A path the container mounts nothing at - `work` on a node created before node create declared it - gains the document's volume, new and empty, named in the new `volumes_added`; what the old container kept there outside a volume goes with it. A node with no agent container at all is refused (`node_document_unconfirmed`) and is brought back first with `coolify deploy <uuid>`. A node already on the tag with no volume to gain is not written, and is redeployed only when its container is not running, so running the update again finishes one that left the node down. It needs a coolify with `service set-compose` (`provider_not_ready` otherwise).

## 2026-10-26 — `deployment node update` moves a node of the standard image to a new tag

`deployment node update <node> --version <tag> [--wait 600]` moves a node `deployment node create` made from the standard image to `ghcr.io/agenium-dev/agent-node:<tag>` through the coolify connection its row names: it replaces the image of the node's Coolify service with `coolify service set-image`, redeploys it with `coolify deploy`, its volumes kept, and waits for its container to run that image, report healthy and read its agent running. It answers the node, the resource, the new and previous image, whether it redeployed, the volumes kept, and the container's image, health and agent state; a node not back in time exits 5 `node_not_raised`. A node already running the tag is not redeployed. A node built from a repository is refused with exit 6 `node_built_from_repository`, which names `coolify deploy <uuid>` to rebuild it; a resource not running the standard image for this agent with `node_resource_not_own`; and a coolify without `service set-image` with `provider_not_ready`, each before anything changes. The agent-node guide's update section names the verb, and its Work section names `worktree_root` in `capabilities path --json` as where the agent's checkouts and worktrees go.

## 2026-10-26 — enrol carries every usable capability's secrets and names what it leaves, a deploy whose check cannot reach the store is not rolled back, and a box never downgrades its manager

`deployment node enrol` carries the secret keys of every capability the agent can use - enabled for the project or globally - where it carried only the project-enabled ones, and reads the key a connection maps an option to (`option (ENV_KEY)`). Its answer adds `secrets_skipped`, each secret key it did not carry with the reason, and `environment_only`, per capability, each secret-looking key the capability's service reads from its environment (`service.deploy.environment`, the database's keys aside) that no connection reports - one read from the process environment alone, such as a compiled target's container environment - with `environment_only_hint`; keys only, never values. `deployment deploy` tries the check of a started deployment again, up to four times, while it fails as `store_unreachable` or `store_busy`; one that still cannot reach the store rolls nothing back, prints `"state": "deployment running, verification failed"` with the deployment and its `coolify wait`, and exits 5 `deployment_unverified`. A rollback that fails now reads `rollback=failed (<code>)`. A box whose manager home persists (`compiler.container.persistent_manager`) updates its manager at boot from the official source's tracked branch, not from the catalogue `CAPABILITIES_REF` pins, and never to a release whose change log is older than the installed one's; run `deployment sync` to recompile the entrypoint.

## 2026-10-26 — A node keeps its work on a volume, and no node is handed its identity in its environment

`deployment node create`, from the standard image and from a repository alike, gives a node a fifth volume of its own, `work` on `/home/agent/work`, the place for the agent's checkouts and git worktrees, so a redeploy keeps them; the answer's `volumes` lists it. agent-node 0.0.9 makes that folder and gives it to `agent`; on an older tag give it to the node's user once (`deployment guide agent-node`, **Work**). The node is told only `CAPABILITIES_PROJECT_ID` and `CAPABILITIES_PROJECT_ID_ROOT`: it no longer receives `AGENT_NODE_NAME`, its label being its row's alone, and `handed` names the two. `deployment sync` no longer writes `AGENT_NODE_ID` into the bundle of a target whose `node` is an id: the node resolves its id from the file enrol writes, so nothing overrides it, the `.env.example` says where it is kept, and `deployment deploy` empties `AGENT_NODE_ID` on the application rather than sending it. A target whose `node` is the name a node registered before ids is still keyed by, and a target without `node`, compile and deploy as before. A box of a target that declares an id must hold that id in `~/.config/capabilities/node-id` (`capabilities node id --set <id>`) on a persistent volume before it is redeployed.

## 2026-10-25 — `handover` finds every loaded agent of its folder, whatever compiled it

`deployment handover` takes, beside the agents this project's compiling left in its agents folder, every other launchd agent in `~/Library/LaunchAgents` or that folder whose program or working directory lies inside the project - such as one an older compilation left under another label - and does so whatever the project's runtime declares. Such an agent whose label ends in the name of an installed capability that bundles a service is handed over as that service, and reports it as `service`; one ending in `watchdog` as the watchdog; any other is reported as kind `other`, action `kept`, and left running. The node manager's own agents (`capabilities.*`) are never taken.

## 2026-10-25 — `runner` hands its service to the manager, every box compiles to it, and a handed-over Mac is not told to load its agents

`deployment runner <name> [--every N] [--restart POLICY] -- <command...>` keeps its arguments, its gate and its read-only refusal, and then hands the service, in the same process, to `capabilities node supervise <name> --every N --restart POLICY -- <command...>`, which does what the runner did, where the manager answers `capabilities node supervise --probe`; against an older manager, or none found here, the runner supervises the service itself as before, so updating deployment without the manager leaves every runner working. A files-mode box's `supervisord.conf` and a service in a Compose service of its own now compile to `capabilities node supervise` instead; host agents still run `deployment runner`, and `doctor` and `sync` take either process line as the runner. On a Mac whose node manager runs the project (its records in the store, and `capabilities.node` from `capabilities node install` in place), `doctor` no longer reports the compiled service agents as not installed or not loaded - only one loaded beside the node manager, as a warning naming `deployment handover` - and `next` lists only the agents that carry the body to a node, with the services started, stopped and restarted through `capabilities service`.

## 2026-10-25 — `handover` gives a Mac's host agents to the node's service manager, and a service runs once per machine

`deployment handover [--dry-run]` boots out a host-agents project's loaded service agents and its project watchdog and takes their entries out of `~/Library/LaunchAgents`, leaving the compiled files and the node-sync agents; `capabilities node install` runs it in every folder whose services the Mac's node manager will run. `deployment runner` now takes a lock per service in the project's state, so a second runner of the same service in the same project on one machine - a host agent loaded again beside the node manager's job - starts nothing and waits for the first to stop; a runner that cannot write its lock says so and runs its service without it, as it already ran without its state. The runner gives its service each environment default the compiled service carries (the descriptor's optional defaults, then the runtime's `environment_defaults`) where its own environment sets none, as a host agent's file and a box's Compose file already did, so a service the node manager starts runs with the same values.

## 2026-10-25 — A store-mode box runs its services through the node's service manager

In a store-mode project, a box's `supervisord.conf` runs one program for its embedded services, `capabilities node run --supervisor /tmp/agent-box-services --every <reconcile_seconds> --services <embedded>`, and includes `/tmp/agent-box-services/*.conf`, where that manager keeps a program per service the gate places on the node; it no longer compiles a runner program per embedded service. A files-mode box, and a service in a Compose service of its own, compile as before. `deployment runner` given no `--every` reads `service_policy.reconcile_seconds` from the project's runtime. `deployment node status` reports a node manager's program `<capability>.<agent id>` of its own agent as that capability.

## 2026-10-25 — A runner records in the store what runs on its node and whether it can do its work

While a service is placed on a node, `deployment runner` keeps the node's row of it in `capabilities_service_instances` (capabilities-contract 0.23), for exclusive and shared services alike. It writes the row on each start, failed start, exit, exit-4 hold and reconcile, and as `stopping` before it stops the service, and deletes it when the service is no longer placed there or the runner stops. A running service is `starting` until its declared `service.deploy.doctor` first answers, ten seconds after it started, and is asked again every reconcile, for at most 30 seconds. Exit 0 is `ready`, or `degraded` when the body names `skipped_settings`. Any other answer is `unusable`, with the message and code of the error envelope it printed, else the body's `problem`, else its exit code's category (`auth`, `not_found`, `policy`, `unreachable`, `input`). A service that exits non-zero, or cannot be started, is `failing`, with its exit code, stderr tail and time, and one that crashes as soon as it is restarted stays `failing` rather than `starting`. One held by exit 4 or by its restart policy is `held`, and one placed here while another node holds its lease is `waiting`. A project that declares no id keeps no row. A write the store does not take is said once on stderr and changes nothing about the service. The lease's own `last_error` is written as before. The script declares `capabilities-contract>=0.23,<1`.

## 2026-10-25 — A node deploy carries the value a capability keeps once for the machine

A setup field an installed capability declares `shared` (capabilities-contract 0.22) is kept in `~/.config/capabilities/shared.env` under its shared name. When `deploy` fills a node-placed service's required and optional environment, it now asks that file for such a field before the owning capability's own `~/.config/<capability>/credentials.env`, reading which fields are shared from the capability's installed manifest, so a value written once for the machine reaches the node, and an older per-capability value no longer outranks it. The project's env files still win, and a key no installed capability declares shared resolves as before.

## 2026-10-25 — sync replaces a launchd agent that runs its service outside the runner

On `host-agents`, a loaded agent of a compiled service whose process launchd holds is not `deployment runner <service>` - or, with no process, whose program is not the compiled launcher - runs its service outside the gate and the lease, as an agent loaded from an older compilation that ran `<capability> service run` directly does, and keeps it running on the Mac after the service is placed on another node. `deployment sync`, once it has written the artifacts, boots such an agent out, links the compiled agent in place of its installed file in `~/Library/LaunchAgents` and bootstraps it, so the runner then starts or stops the service as the gate places it; the result lists each under `agents` as `replaced`, or as `unloaded` or `failed` with the step and launchctl's answer, which is also an error finding. `sync --check` reports such an agent as an error instead of acting, and `deployment doctor` reports it as an error naming its label. An agent never loaded is still handed over by `deployment next`.

## 2026-10-24 — A service that fails hands back its error on its lease

When a service its runner holds the lease for exits with a non-zero code other than 4, or cannot be started, the runner writes the exit code, the service's last stderr lines (at most 2000 characters) and the time onto the lease row, in the new `deployment_service_leases` columns `last_exit`, `last_error` and `last_error_at` (deployment tables 1.1, an added step that every runner applies when it connects). Any machine reading the store can therefore see why the service stopped, and `deployment services` answers it as the lease's `last_error`, `null` until a failure is recorded; the runner's own `last_exit` carries the same `error` text. Another node taking the lease clears them, and a lease released, as on an exit-4 refusal, goes with its row as before. A shared service takes no lease and records nothing there.

## 2026-10-24 — A node made by `node create` is registered by an id, and enrolment puts it on its volume

`deployment node create <label>` mints the node's id and registers its row under it with that label; the container is told `AGENT_NODE_NAME=<label>`, the label it is shown by, and the answer names the id. `deployment node enrol` first writes that id onto the node's config volume with the node's own `capabilities node id --set`, so the node runs as its row from then on. `enrol`, `exec` and `remove` take a node's id or the label exactly one of the agent's nodes carries (`node_ambiguous` otherwise). `remove` checks that the resource runs the standard image for this agent (its `CAPABILITIES_PROJECT_ID`) rather than under the node's name, which may have changed since. Runners and service leases name the node by its id, through the contract. `deployment services` answers the node's `label` beside its id, and `node status` reports `node_id` and compares a target's declared `node` with it. A target's `node` is the id of the node its server runs as, or for a node registered before ids the name it is still keyed by: `deployment sync` writes it into the bundle as `AGENT_NODE_ID` in place of `AGENT_NODE_NAME`, so every container of the box and every redeploy is that one node. A target without `node` takes `AGENT_NODE_ID` from the server's environment, else the server's `AGENT_NODE_NAME` as the id, so a server that named such a box with `AGENT_NODE_NAME` keeps its node with nothing changed. deployment moves to `capabilities-contract>=0.21.1,<1`.

## 2026-10-24 — A command deployment runs that fails is named, with its own error

Where a command deployment runs fails, the `node_command_failed` message names the program and its verb and carries the command's own error: its standard error, or the message of the error envelope a capability prints. `sync`, `sync --check` and `doctor` on a ContextKit-bound checkout body now answer, for example, ``"`contextkit path` failed (exit 6): invalid collaboration.mode: bogus ..."`` rather than `contextkit failed (exit 6)` alone. Arguments are never named. A command fed standard input, and `ssh`, whose standard error carries the remote process's diagnostics, still answer with the command and its exit code only. A Coolify error envelope still passes through with its own code. The code and exit code are unchanged.

## 2026-10-24 — One command runs on a node with its output streamed back

`deployment node exec <node> -- <command> [<arg>...]` runs one command in the container of a node made by `node create`, over SSH to its server and `docker exec -i`, the path `node enrol` reaches it by, with no terminal: standard input is forwarded, standard output and standard error come back unchanged as the command writes them, so `telegram login --events` or `whatsapp pair --events` streams its JSON events to this machine, and the exit code is the command's own (255 when SSH cannot reach the server). It is refused under the read-only switch, like `node login`.

## 2026-10-24 — A generated image installs Codex 0.162.1

Generated agent-box images install Codex `rust-v0.162.1` in place of `rust-v0.147.0`. That is inside the range callva-harness-runner was tested with, so on a rebuilt box codex turns through the runner are no longer refused as `incompatible_harness`. An image that is already built keeps its codex until it is rebuilt.

## 2026-10-24 — Every runner reports its node seen, and a node seen within three reconciles is live

On each reconcile, whatever the gate answers, `deployment runner` reports its node up with `capabilities node seen`, which sets the node's `last_seen_at`; a node is therefore seen while any runner runs on it, on a Mac and on a node of the standard image alike, whether or not it holds a lease. A report that fails is said once on stderr and changes nothing else. `deployment node list` lists the agent's nodes with `seen_seconds_ago` and `live`, and `deployment help` defines a node as live when its `last_seen_at` is within three reconciles (3 x `service_policy.reconcile_seconds`, default 60) of now; a never-seen node is not live. Whether a given service runs is still proven by its live lease, not by its node being live. Requires a manager with `node seen`; beside an older one the runner says once that it cannot report and runs its service as before.

## 2026-10-23 — The runner places a service by its service flag, and runs a shared service without the lease

In store mode the runner places a service on a node by the `service` of the project's row naming that node (`capabilities place|unplace`), no longer by `enabled`, so a row that keeps the capability's CLI usable on a node without its service leaves the service off there; `deployment services` shows the row's `service`. A service whose descriptor declares `service.placement` `shared` runs on every node it is placed on and takes no lease (releasing one it held); an `exclusive` one, the default, keeps the lease and runs on one node at a time. `node enrol --services` places each service with `capabilities place`, which takes an exclusive service off the node it ran on before (`unplaced` in the answer) and leaves the capability usable there. `deployment guide agent-node` (**Move a service onto the node**) and `deployment guide profiles` (**Where a service runs**) describe moving a service with `place` and warn that `disable --node` turns the capability off on that machine. Requires `capabilities-contract` 0.17.

## 2026-10-23 — A node built on its server from a Dockerfile in a repository, with the host's Docker socket and same-path host directories

`deployment node create <node> ... --repository <url> --branch <branch> --dockerfile <path> [--context <dir>]`, in place of `--version`, makes a Coolify application that builds the node's image on the target server from that Dockerfile, `FROM` the standard image, with no CI and no registry; a private repository is cloned through `--deploy-key <uuid>` or `--github-app <uuid>`. The node keeps the three keys, the four state volumes and the memory limit, gets no domain and no automatic deploy on push, and only it takes `--docker-socket` (the host's `/var/run/docker.sock`) and `--host-dir <path>` (repeatable), each bound at the same path in the container as a Coolify host path, which Coolify never creates, writes or deletes. The answer names the application and its build deployment. `node enrol` reaches its container by the Compose project alone, and `node remove` deletes the application with its volumes and never a host path or what is in it. `node create --version` is unchanged. Requires the coolify capability's `storage add`, `--limits-memory` and `--no-autogenerate-domain`.

## 2026-10-23 — Help says how a person logs in on a node of the standard image

`deployment help`, under `node enrol`, says the logins are not handed to a node: a person makes them over SSH and `docker exec -it` into the node's container (labelled with the resource as Compose project and `agent` as service) with `claude auth login`, `codex login --device-auth` and `gh auth login`, which agent-node 0.0.2 and later carries and through which git reaches github.com over https. Each login is kept on the node's volumes.

## 2026-10-23 — A box that carries no body binds its agent by the id alone

The `agent-box-shell` entrypoint no longer lays an empty `.contextkit/config.toml` in the project root before binding it: the manager composes the context of a folder bound to its agent's id, so each boot still binds the root with `capabilities init --id`, wires the agent CLIs with `capabilities hooks install --claude --codex` and composes the context with `capabilities build`, now written to `.capabilities-generated/context.md`. Requires a manager that builds for a folder bound by its id.

## 2026-10-23 — A node of a store-only agent is created, enrolled and removed from the standard image

`deployment node create <node>` creates a Coolify resource through the coolify capability's connection: a Compose service of one container running `ghcr.io/agenium-dev/agent-node:<version>` with a memory limit (`--memory`, default `2g`), a volume of its own for each state path of the image (`~/.config`, `~/.local/state`, `~/.claude`, `~/.codex`), and only `CAPABILITIES_PROJECT_ID`, `CAPABILITIES_PROJECT_ID_ROOT` and `AGENT_NODE_NAME`, with no repository and no build; it then registers the node row with the connection, server and resource. `deployment node enrol <node> [--services ...]` reaches the container over SSH and docker exec, makes the node's X25519 key pair there and records the public key on the row, writes the agent's connection secrets into each capability's credentials file, except the coolify connection the node was created through, whose token stays on the deploying machine, and the store setting with the node's own `capabilities store set`, places the named services with `capabilities enable <name> --project --node <node>`, and waits for the node to raise its agent; secrets travel on standard input only. `deployment node remove <node> --yes` deletes that resource with its volumes and the node row, and touches nothing else on the server.

## 2026-10-22 — The Coolify application name falls back to the project's slug from its agent's row

Where ContextKit names no project, the Coolify application is named after the project's slug as `_project_slug` answers it (its agent's row in the store, else an older `project.json`'s, else its id). The envelope check accepts a project bound to its id, and help names store mode by the agent's records rather than `project.json`. Declares `capabilities-contract>=0.12,<1`.

## 2026-10-22 — A ContextKit-bound box is built and wired by the capabilities manager alone

The image of a ContextKit-bound project no longer installs ContextKit or runs any of its commands. `agent-box` builds run `capabilities init --codex --claude`, `capabilities doctor`, `capabilities hooks install --claude --codex` and `capabilities build`; `agent-box-checkout` boots run `capabilities init --codex --claude`, `capabilities hooks install --claude --codex` and `capabilities build`, and each body sync rebuilds with `capabilities build`, as `deployment node sync` does. The session hooks a box writes now run `capabilities session-start`, so a box's body sync no longer commits `contextkit session-start` hooks back to the branch. The `CONTEXTKIT_REF` build argument and the ContextKit installer are gone from the generated Dockerfile; a project that declared `CONTEXTKIT_REF` among its build args still has it compiled, and the image ignores it.

## 2026-10-22 — A box that carries no body raises a store-only agent by its id

A fourth container profile, `agent-box-shell`, compiles the agent box with no body: the image carries no project copy, the box clones nothing from Git, keeps no body volume or body sync, and installs and runs no ContextKit, whatever the deploying folder is bound to. Each boot binds the empty project root to the agent the store holds under `CAPABILITIES_PROJECT_ID` with `capabilities init --id` (laying an empty ContextKit binding first, which the manager's build requires), wires the agent CLIs with `capabilities hooks install --claude --codex`, composes the context from the store with `capabilities build`, and starts the compiled services under their runners, placed per node by the gate. The Compose file sets the id as the deploying folder resolves it at sync and otherwise passes it through from the server's environment; a box without it stops at boot. `deployment init`, `deployment setup` and `deployment sync` accept the profile; the other profiles are unchanged.

## 2026-10-22 — Every box is told which agent it runs

`deployment sync` writes the project's id, `CAPABILITIES_PROJECT_ID` as the project resolves it at sync, into the bundle's Compose file beside `AGENT_NODE_NAME`, so every container receives it, together with `CAPABILITIES_PROJECT_ID_ROOT` naming the box's project root, so only the project at that root takes it and a repository checked out beside it resolves its own; a service's own entry for either key is no longer written, since it would override the shared one. An image that runs `capabilities init` in its build (`agent-box`) sets the same two in its Dockerfile before the catalogue install and that step; a checkout image carries no project and sets neither. The id no longer travels in the project's files (`capabilities` 2026-10-22), so a box built from a fresh copy of a repository, or started on an empty volume, takes it from here. A project whose id does not resolve at sync compiles as before. `deployment` uses `capabilities-contract` 0.9.0.

## 2026-10-22 — A long build is followed to its end, and a rollback builds the release it names

`deployment deploy` and `deployment rollback` follow the Coolify deployment they started while Coolify reports it `queued` or `in_progress`, for at most an hour, and only then wait the usual ten minutes for the resource to be healthy, so a build longer than ten minutes is no longer reported as timed out and rolled back while Coolify is still building it; a deployment Coolify ends as failed or cancelled is reported failed and rolled back as before. The environment a deploy sends now carries the runtime's `compiler.build_args`, and a rollback, requested by hand or by a failed deploy, first sets the build args the runtime declares at the commit it returns to, so the image it builds is that release's rather than the one the environment was last set for, and `deployment node status` names the release the container runs.

## 2026-10-21 — `node status` reports what the node holds that no service accounts for

`deployment node status` carries `leftovers`, read in the node's container: the processes that are neither a Supervisor program nor descended from one, with pid, parent, age and command; the development sessions open longer than a day, or damaged; and the size of /tmp and of the uv cache. Nothing is ended or removed.

## 2026-10-21 — A connection whose network flow died fails in seconds

`deployment` uses `capabilities-contract` 0.7.2. Its store connections give a network flow up once data sent on it has gone unacknowledged for 20 seconds (`tcp_user_timeout`), which keepalives cannot notice since none is sent while data waits, and send keepalives after 15 seconds idle, every 5 seconds, 3 probes: a connection whose flow stopped carrying packets without a FIN or a reset fails in about 20 seconds as a lost connection instead of waiting until the store ends the session, and a plain read that loses it that way runs once more on a new connection. A connection lost where `deployment` catches nothing ends the command as `store_unreachable`, exit 5, as before.

## 2026-10-20 — A read is a transaction of its own in one round trip

`deployment` uses `capabilities-contract` 0.6.0. On its working connection a plain read that would open a transaction, and any statement in autocommit, reaches the store in one round trip - the transaction's start, the schema binding and the commit go with it - and leaves the connection idle, never `idle in transaction`, so a transaction-mode pooler hands its server session on as soon as the store answers; a write still opens a transaction that its commit closes, and a write whose commit may have reached the store is never sent twice. A connect that fails is tried again after jittered, doubling pauses, and once a store did not answer, a further connect to it is refused at once as `store_unreachable` for a doubling pause of at most 30 seconds rather than dialled again on every statement.

## 2026-10-18 — Each boot brings the capabilities to the catalogue the image names

A container's entrypoint installed at boot only the catalogue capabilities its registry lacked, so a node whose manager home persists (`compiler.container.persistent_manager`) kept the payloads an earlier image installed through every redeploy. Each boot now brings them to the catalogue at `CAPABILITIES_SOURCE`: a capability the registry lacks is installed as before; one installed from another catalogue is installed again from this one with `capabilities install <name>`, keeping its machine state; one already from this catalogue is updated with `capabilities update <name>` where `capabilities update --check` finds a different payload there; one installed from a local path or a registered source is left as it is. Where the manager's home persists, the manager is first brought to the release this catalogue carries with `capabilities self-update`, since an older manager refuses newer payloads. A boot already at the catalogue changes nothing. Run `deployment sync` and redeploy to pick it up.

## 2026-10-18 — One working connection per process, and none for a runner whose service is not running

`deployment` uses `capabilities-contract` 0.5.1. Every connection it opens on the transaction path is the process's one working connection, which the library lends to each operation and keeps until the process exits, so a command connects once rather than once per read; a connect that fails is tried again, and a working connection the store or the network lost is replaced, a statement that lost it before anything of its transaction reached the store running once more on the new one and a commit never sent twice. A runner whose service is running keeps its working connection for the lease renewals; one whose service is not running here closes it after each reconcile and holds no connection between them.

## 2026-10-18 — A runner holds no connection, and the watchdog waits for a store that is away

`deployment` uses `capabilities-contract` 0.5.0. A runner opens a transaction connection for each lease take, renewal, release or read and closes it after, and its gate read connects only while it reads, so a runner holds no connection between reconciles; once it knows it holds no lease, a runner whose service is not placed here does not ask the store about the lease at all. The watchdog does not restart a service whose doctor fails because the store does not answer (`store_unreachable`): it reports `waiting for the store` and asks that doctor again after a pause that starts at its interval and doubles while the store stays away, up to 30 minutes, opening nothing meanwhile; any other failure is counted and restarted as before.

## 2026-10-16 — A moved agent's image builds without a database and bakes in no record file

`doctor` counts a service of an agent whose records moved into the store as configured when the store holds its settings document. For such an agent `sync` compiles a Dockerfile whose `capabilities install --allow` and `capabilities init` run without a database and whose `capabilities doctor` moves to the entrypoint, at container start, and a .dockerignore that excludes every record and settings file (`capabilities/settings.json`, `*/connections.json`, `*/identifiers.json`, `*/service/settings.json`, `*/service/config.toml`, `tasks/conveyor.toml`, `slack/policy.json`) and the profile and worker folders that moved with them (`askproject/profiles/`, `*/service/profiles/`, `tasks/workers/`, `tasks/profiles/`). Every other project compiles as before.

## 2026-10-16 — `migrate files` reads runtime.json placement for `capabilities migrate`

Its mover names one node per target that declares one, for the master to register, and the policy rows that place on each node the services runtime.json's service_policy and placement run there today; a target that names no node is a question (`deployment.targets.<name>`). The manager writes the rows; runtime.json stays.

## 2026-10-15 — A target declares the node its server runs as

A deployment target takes an optional `node` field: the name its server runs as in the gate. `deployment sync` writes it into the target's bundle as `AGENT_NODE_NAME` in the Compose file's shared environment, as a literal every container receives whatever the server's environment holds, the bundle's `.env.example` names it as the target's instead of asking for it, and `deployment deploy` sends the same value to the application's environment rather than the deploying machine's own. `deployment node status` reports it as `declared_node_name` beside the `node_name` the node answers to, with the error `node_name_mismatch` while they differ. The target is the one home of the name: `sync` and `doctor` refuse a `services.<name>.environment_defaults` setting `AGENT_NODE_NAME` beside it (`node_declared_twice`) and a malformed value (`node_invalid`); a runtime that names its own artifact paths compiles no bundle and reports a declared node as `node_not_compiled`. A target without `node` compiles, deploys and reports exactly as before. To move a server's name onto its target, add `node`, remove `AGENT_NODE_NAME` from any `environment_defaults`, run `deployment sync` and redeploy.

## 2026-10-14 — A checkout body whose ContextKit keeps no memory layer syncs without one

On the `agent-box-checkout` profile, `deployment sync`, `sync --check` and `doctor` asked ContextKit for its memory layer to write the union-merge rule in `.gitattributes`, and stopped with `node_command_failed` when the project's ContextKit has no such layer - a project whose memory lives in the memory capability's store rather than in the body. Such a project now compiles with no memory rule, since nothing in the body needs a union merge; any other ContextKit failure still stops the command as before, and a project with a memory layer compiles exactly as it did.

## 2026-10-13 — In a store-mode project the gate on each node starts and stops a service, and a lease keeps it on one machine

Every supervised capability service - a Supervisor program in the agent container, a Compose service of its own, a launchd agent on a Mac - now runs through the new `deployment runner <name> --every <seconds> --restart <policy> -- <command>`. Once per reconcile (`service_policy.reconcile_seconds`, default 60) the runner reads the gate for this project on this node (`AGENT_NODE_NAME`, else the host name), takes or renews the service's lease in the new `deployment_service_leases` table of the project's store (migrated under the ledger owner `deployment`; `deployment migrate [status]` answers for it), and starts the command in a process group of its own, restarting it per the descriptor's policy; when the gate no longer places it, it stops the group and releases the lease. A runner on another node whose gate places the same service refuses to start it while the lease is live, naming the holder and the expiry on its stderr, and takes over once the lease expires or is released; with no database resolvable for the project no lease is taken and the service runs as the gate says. A service that exits 4, the contract's policy refusal, is not restarted: its runner releases the lease and holds it idle, reporting the refusal (the service's error code and message when it printed one), until the gate answer for that node changes or the runner restarts. The new `deployment services` reports, per compiled service on this node, what the gate answers and from which row, whether its runner runs it, any refusal it is held for, and who holds its lease, and `deployment node status` folds that into each service. The Compose file now passes `AGENT_NODE_NAME` through, so a container node can keep its name across redeploys. The host watchdog leaves alone a service its runner holds idle.

A project whose gate is in files compiles exactly what it compiled before: the capabilities it enabled itself, chosen and shaped by `service_policy` and the descriptor's `default_policy`, placed by `placement`; its runners run them where the project's own enable stands, and nothing in its runtime is warned about or rewritten.

Breaking for a project whose records are in the store (`"records": "store"` in `project.json`): `deployment sync` compiles every deployable service descriptor of the installed catalogue, less `capabilities.exclude`, and a service runs on a node only where the project's policy row names that node, so such a node runs no service until those rows exist; write them with `capabilities enable <name> --project --node <node>` and set `AGENT_NODE_NAME` on a container node. Turning a service on or off for a node then needs no recompile and no redeploy. Its `service_policy` keeps `shape` (`embedded` or `container`) and per-capability shapes; `auto_include`, `default_mode`, the per-capability `auto`, `enabled` and `disabled`, `service_policy.placement` and `services.<name>.placement` are retired for it: `doctor` and `sync --check` warn about each one, and `sync` rewrites it, keeping the shape it implied and listing what it rewrote under `retired`. Its `setup --with-telegram` and `--with-automations` with any value but `auto` exit 6 `retired_option`, and `deployment deploy` no longer refuses a required key only a capability service declares; left unset locally, the server's value stands. Run `deployment sync` and redeploy once to move to runners.

## 2026-10-13 — A checkout node brings up the other repositories it works on at boot

On the `agent-box-checkout` profile, `compiler.container.checkouts` in `deployment/runtime.json` declares other repositories the box works on beside its body, each `{path, url, branch, register}`: an absolute path outside the project root, the repository URL, the branch (default `main`), and optionally `register: "official"`. Every boot, after initialization and before the doctors, the entrypoint clones each one whose path is absent or holds no files, leaves one that is already a git checkout exactly as it is, and leaves a path holding files but no checkout untouched with a warning. With `register`, it then runs `./bin/capabilities source register-checkout official` from the checkout unless `capabilities source list` already names that checkout as the official one, so a fresh node opens a development session with no manual clone or registration. A failed clone or registration warns and the box still boots. `deployment doctor` names a malformed entry as an error and a declaration on another profile as ignored. A runtime that declares none compiles exactly as before.

## 2026-10-13 — A container node installs the whole catalogue, and the capabilities lock is retired

Breaking. A container image (`agent-box`, `agent-box-checkout`) now installs every capability in the official catalogue at `CAPABILITIES_REF`, read from that ref's `.capability-source/catalog.json`, with `capabilities install <name> --allow`, less the runtime's `capabilities.exclude`; a core capability arrives enabled by the manager's first-install rule, and the build fails when one cannot be installed. Every boot, on every container profile and not only with `persistent_manager`, installs any catalogue capability the registry lacks and leaves installed ones as they are; a catalogue that cannot be read leaves the box running with what it has. Whether a capability is usable is its gate's and its connections' answer, not whether it is installed. `deployment/capabilities.lock` is no longer compiled, copied into the image or read: `init` and `sync` stop writing it, `deployment freeze` is gone, and `sync` drops `capabilities.lockfile` from `deployment/runtime.json`; delete the file from a project. A capability service is embedded or enabled only when the project itself enabled that capability, as help already stated: one enabled only at global scope no longer contributes a service. Run `deployment sync` and redeploy to pick it up.

## 2026-10-13 — A checkout node follows its declared repository on boot

On the `agent-box-checkout` profile, a boot whose body is already populated now points the checkout's `origin` at `AGENT_REPO_URL` when it is set and differs, before the boot sync pass, and logs `origin now <url>`. A node moved to a GitHub body source therefore pulls and pushes GitHub from its first boot after the deploy, rather than the server repository it was first cloned from. The body's content and its own commits are untouched, and a matching or unset `AGENT_REPO_URL` changes nothing.

## 2026-10-13 — A container node can keep the tools it installs and updates

`compiler.container.persistent_manager: true` in `deployment/runtime.json`, on `agent-box` or `agent-box-checkout`, compiles the capabilities manager's whole writable home onto named volumes that every container the image runs mounts: `capabilities_registry` (`~/.capabilities`), `capabilities_bin` (`~/.capabilities-bin`), `capabilities_config` (`~/.config/capabilities`), `capabilities_state` (`~/.local/state/capabilities`), `capabilities_data` (`~/.local/share/capabilities`) and `capabilities_cache` (`~/.cache/capabilities`), one per directory the manager writes, so each rename it makes stays inside one volume. The Dockerfile sets `CAPABILITIES_BIN` to the launcher directory and puts it first on `PATH` in its own `ENV`, so the manager and the lock install there at build while the agent CLIs keep their links in the image, and the entrypoint installs at boot each capability the lock names and the registry lacks, leaving installed ones as they are. A redeploy then no longer upgrades a capability the node already has; the node keeps its tools current through its own updates and releases. Setting the option to `false` or removing it takes back exactly the volumes it added. A runtime that never declares it compiles exactly as before.

## 2026-10-13 — A Coolify checkout node can take its body straight from GitHub

A Coolify target on the `agent-box-checkout` profile can declare `"body_source": {"kind": "github", "repository": "<owner>/<repository>"}` beside its `deploy_key`, the Coolify key authorized read-only on that repository. `deployment deploy` then prepares no server repository, pushes through no `node-<name>` remote and opens no SSH connection for the body: it refuses with `commit_not_on_remote` unless the commit is on the GitHub branch (fetched through the checkout's own remote for the repository, `github_remote_missing` when there is none), creates a new application from the repository with that key or points an existing one at the repository and branch keeping its key, and builds exactly the deployed commit through Coolify's rollback interface. The node's `AGENT_REPO_URL` is the repository's HTTPS URL, so its body sync pulls and pushes GitHub with the node's own credentials, and the deploy empties `GIT_DEPLOY_KEY_B64` and `AGENT_GIT_KNOWN_HOSTS_B64`. `deployment node sync` answers `nothing_to_carry` for such a target and touches no remote, `host-agents` compiles no interval sync job for it, and `deployment node status` reads its Git sync state against the GitHub branch. A malformed declaration is refused as `body_source_invalid`. A target without `body_source` is unchanged.

## 2026-10-11 — A store behind Supabase's transaction pooler is refused at connect

`deployment` now uses `capabilities-contract` 0.4.1. A transaction-mode pooler keeps no session between transactions, so the schema binding, prepared statements and notifications a connection relies on are lost through one, and it is not supported. A database setting that points at Supabase's transaction pooler - a host under `pooler.supabase.com` on port 6543 - is refused before anything is sent to it, as `transaction_pooler`, with a hint naming the session pooler: the same host on port 5432. Every other database, the session pooler included, is reached as before.

## 2026-10-10 — The machine watchdog tells a stopped agent and a copy outside launchd from a restart

`deployment machine watchdog` no longer reads every loaded machine agent with no pid as a restart in progress. A machine agent's `KeepAlive` restarts its process only after a failure, so the pass now asks the service's declared doctor: when it reports a machine process running while launchd holds no pid, the entry is `state: outside_launchd` with `outside_pid` and a detail naming the remedy (`<name> service stop --machine`, then `launchctl kickstart gui/$UID/<label>`); when the agent exited cleanly (last exit code 0) it is `state: stopped`, with the `kickstart` that starts it; otherwise it is `state: restarting` as before. Each such entry carries `last_exit_status`, and none of them is kickstarted. The project-scope `deployment watchdog` is unchanged.

## 2026-10-09 — A node takes its database only from its server's environment

`deployment deploy` no longer sends the deploying machine's store setting: the `AGENT_STORE_*` values are gone from the bulk environment, a service's declared environment never fills an `AGENTKIT_DB_*` key from the Mac, and the entrypoint no longer runs `capabilities store set`, so no setting file is written in the container. The Compose file passes `AGENTKIT_DB_URL` and the other `AGENTKIT_DB_*` keys through from the server's environment, and a deploy leaves the values set there standing. `deployment node status` reports `store` from a probe run in the container through `capabilities-contract`: `configured`, the redacted `setting` with its level and sources, `reachable`, `tls_enforced`, and an `error` when one stops it. ## 2026-10-08 — A node's store setting carries its schema

A setting that names no schema sends none, and the node binds `agentkit` as before. The setting is read from the machine's store setting file, or from the manager's former files while it is absent.

## 2026-10-05 — Supervised services run at standard priority

The launchd agents `deployment sync` (host-agents) and `deployment machine sync` compile for a service now carry `ProcessType Standard` instead of `Background`, so a service and everything it starts - agent turns, builds, test runs - run at standard priority on every core rather than at the lowest priority on the efficiency cores with throttled I/O. The two watchdog agents, short scheduled probes, stay `Background`. `deployment machine status` reports each agent's compiled `process_type`, the `spawn_type` launchd runs it with, and `spawn_type_current`, which stays false until a loaded agent is handed to launchd again; the project doctor's `host_agents` entries carry `spawn_type`. An existing install picks the change up by running the sync and then the steps `deployment machine next` (or `deployment next`) prints.

## 2026-10-05 — Container artifacts compile into one bundle per target, and a deploy creates no Coolify environment

A container runtime that declares no artifact path compiles each target's artifacts into `deployment/targets/<target>/`, beside the target's declaration `target.json`: `docker-compose.yaml`, `Dockerfile`, `Dockerfile.dockerignore`, `.env.example`, `entrypoint.sh`, `supervisord.conf` when Supervisor runs, and `body-sync.sh` on the checkout profile. The project root gains only `.gitattributes` on the checkout profile. The build context stays the project root (`context: ../../..` from the bundle), the ignore file is named for its Dockerfile because Docker reads a plain `.dockerignore` only at the root of the context, and `deployment/runtime.json` and `deployment/capabilities.lock` stay shared. `setup` and `init` write the new layout; a runtime that names `compose_file` or `compiler.artifacts`, as every runtime compiled before this does, keeps its declared paths unchanged, and a declaration at `deployment/targets/<target>.json` is still read. `deployment guide standard` gives the steps that move a project onto bundles, and a bundled runtime's sync names each generated root-layout file it no longer writes.

A new Coolify target declares `production`. The application is named `<project>-<target>` after the name ContextKit's config holds for the project, else its recorded project slug, rather than after the checkout folder, and every deploy sets that name again.
## 2026-10-04 — Agent nodes deploy and sync through Coolify

`deploy`, `rollback`, `logs`, and `node login|status|sync` operate a checkout node through a granted Coolify connection and the server's SSH Git hub. Service placement selects node/local/both per substrate; ContextKit memory uses Git union merges, and host-agents compiles node sync intervals. No existing declaration needs a placement field.

## 2026-10-03 — Machine services are supervised by a machine scope
