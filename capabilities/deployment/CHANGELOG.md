# deployment — change log

## 2026-10-13 — In a store-mode project the gate on each node starts and stops a service, and a lease keeps it on one machine

Every supervised capability service - a Supervisor program in the agent container, a Compose service of its own, a launchd agent on a Mac - now runs through the new `deployment runner <name> --every <seconds> --restart <policy> -- <command>`. Once per reconcile (`service_policy.reconcile_seconds`, default 60) the runner reads the gate for this project on this node (`AGENT_NODE_NAME`, else the host name), takes or renews the service's lease in the new `deployment_service_leases` table of the project's store (migrated under the ledger owner `deployment`; `deployment migrate [status]` answers for it), and starts the command in a process group of its own, restarting it per the descriptor's policy; when the gate no longer places it, it stops the group and releases the lease. A runner on another node whose gate places the same service refuses to start it while the lease is live, naming the holder and the expiry on its stderr, and takes over once the lease expires or is released; with no database resolvable for the project no lease is taken and the service runs as the gate says. A service that exits 4, the contract's policy refusal, is not restarted: its runner releases the lease and holds it idle, reporting the refusal (the service's error code and message when it printed one), until the gate answer for that node changes or the runner restarts. The new `deployment services` reports, per compiled service on this node, what the gate answers and from which row, whether its runner runs it, any refusal it is held for, and who holds its lease, and `deployment node status` folds that into each service. The Compose file now passes `AGENT_NODE_NAME` through, so a container node can keep its name across redeploys. The host watchdog leaves alone a service its runner holds idle.

A project whose gate is in files compiles exactly what it compiled before: the capabilities it enabled itself, chosen and shaped by `service_policy` and the descriptor's `default_policy`, placed by `placement`; its runners run them where the project's own enable stands, and nothing in its runtime is warned about or rewritten.

Breaking for a project whose records are in the store (`"records": "store"` in `project.json`): `deployment sync` compiles every deployable service descriptor of the installed catalogue, less `capabilities.exclude`, and a service runs on a node only where the project's policy row names that node, so such a node runs no service until those rows exist; write them with `capabilities enable <name> --project --node <node>` and set `AGENT_NODE_NAME` on a container node. Turning a service on or off for a node then needs no recompile and no redeploy. Its `service_policy` keeps `shape` (`embedded` or `container`) and per-capability shapes; `auto_include`, `default_mode`, the per-capability `auto`, `enabled` and `disabled`, `service_policy.placement` and `services.<name>.placement` are retired for it: `doctor` and `sync --check` warn about each one, and `sync` rewrites it, keeping the shape it implied and listing what it rewrote under `retired`. Its `setup --with-telegram` and `--with-automations` with any value but `auto` exit 6 `retired_option`, and `deployment deploy` no longer refuses a required key only a capability service declares; left unset locally, the server's value stands. Run `deployment sync` and redeploy once to move to runners.

## 2026-10-13 — A checkout node brings up the other repositories it works on at boot

On the `agent-box-checkout` profile, `compiler.container.checkouts` in `deployment/runtime.json` declares other repositories the box works on beside its body, each `{path, url, branch, register}`: an absolute path outside the project root, the repository URL, the branch (default `main`), and optionally `register: "official"`. Every boot, after initialization and before the doctors, the entrypoint clones each one whose path is absent or holds no files, leaves one that is already a git checkout exactly as it is, and leaves a path holding files but no checkout untouched with a warning. With `register`, it then runs `./bin/capabilities source register-checkout official` from the checkout unless `capabilities source list` already names that checkout as the official one, so a fresh node opens a development session with no manual clone or registration. A failed clone or registration warns and the box still boots. `deployment doctor` names a malformed entry as an error and a declaration on another profile as ignored. A runtime that declares none compiles exactly as before.

## 2026-10-13 — A container node installs the whole catalogue, and the capabilities lock is retired

Breaking. A container image (`agent-box`, `agent-box-checkout`) now installs every capability in the official catalogue at `CAPABILITIES_REF`, read from that ref's `.capability-source/catalog.json`, with `capabilities install <name> --allow`, less the runtime's `capabilities.exclude`; a core capability arrives enabled by the manager's first-install rule, and the build fails when one cannot be installed. Every boot, on every container profile and not only with `persistent_manager`, installs any catalogue capability the registry lacks and leaves installed ones as they are; a catalogue that cannot be read leaves the box running with what it has. Whether a capability is usable is its gate's and its connections' answer, not whether it is installed. `deployment/capabilities.lock` is no longer compiled, copied into the image or read: `init` and `sync` stop writing it, `deployment freeze` is gone, and `sync` drops `capabilities.lockfile` from `deployment/runtime.json`; delete the file from a project. A capability service is embedded or enabled only when the project itself enabled that capability, as help already stated: one enabled only at global scope no longer contributes a service. Run `deployment sync` and redeploy to pick it up.

## 2026-10-13 — A checkout node follows its declared repository on boot

On the `agent-box-checkout` profile, a boot whose body is already populated now points the checkout's `origin` at `AGENT_REPO_URL` when it is set and differs, before the boot sync pass, and logs `origin now <url>`. A node moved to a GitHub body source therefore pulls and pushes GitHub from its first boot after the deploy, rather than the server repository it was first cloned from. The body's content and its own commits are untouched, and a matching or unset `AGENT_REPO_URL` changes nothing.

## 2026-10-13 — A container node can keep the tools it installs and updates

`compiler.container.persistent_manager: true` in `deployment/runtime.json`, on `agent-box` or `agent-box-checkout`, compiles the capabilities manager's whole writable home onto named volumes that every container the image runs mounts: `capabilities_registry` (`~/.capabilities`), `capabilities_bin` (`~/.capabilities-bin`), `capabilities_config` (`~/.config/capabilities`), `capabilities_state` (`~/.local/state/capabilities`), `capabilities_data` (`~/.local/share/capabilities`) and `capabilities_cache` (`~/.cache/capabilities`), one per directory the manager writes, so each rename it makes stays inside one volume. The Dockerfile sets `CAPABILITIES_BIN` to the launcher directory and puts it first on `PATH` in its own `ENV`, so the manager and the lock install there at build while the agent CLIs keep their links in the image, and the entrypoint installs at boot each capability the lock names and the registry lacks, leaving installed ones as they are. A redeploy then no longer upgrades a capability the node already has; the node keeps its tools current through its own updates and releases. Setting the option to `false` or removing it takes back exactly the volumes it added. A runtime that never declares it compiles exactly as before.

## 2026-10-13 — A Coolify checkout node can take its body straight from GitHub

A Coolify target on the `agent-box-checkout` profile can declare `"body_source": {"kind": "github", "repository": "<owner>/<repository>"}` beside its `deploy_key`, the Coolify key authorized read-only on that repository. `deployment deploy` then prepares no server repository, pushes through no `node-<name>` remote and opens no SSH connection for the body: it refuses with `commit_not_on_remote` unless the commit is on the GitHub branch (fetched through the checkout's own remote for the repository, `github_remote_missing` when there is none), creates a new application from the repository with that key or points an existing one at the repository and branch keeping its key, and builds exactly the deployed commit through Coolify's rollback interface. The node's `AGENT_REPO_URL` is the repository's HTTPS URL, so its body sync pulls and pushes GitHub with the node's own credentials, and the deploy empties `GIT_DEPLOY_KEY_B64` and `AGENT_GIT_KNOWN_HOSTS_B64`. `deployment node sync` answers `nothing_to_carry` for such a target and touches no remote, `host-agents` compiles no interval sync job for it, and `deployment node status` reads its Git sync state against the GitHub branch. A malformed declaration is refused as `body_source_invalid`. A target without `body_source` is unchanged.

## 2026-10-11 — A store behind Supabase's transaction pooler is refused at connect

`deployment` now uses `capabilities-contract` 0.4.1. A transaction-mode pooler keeps no session between transactions, so the schema binding, prepared statements and notifications a connection relies on are lost through one, and it is not supported. A database setting that points at Supabase's transaction pooler - a host under `pooler.supabase.com` on port 6543 - is refused before anything is sent to it, as `transaction_pooler`, with a hint naming the session pooler: the same host on port 5432. Every other database, the session pooler included, is reached as before.

## 2026-10-10 — The machine watchdog tells a stopped agent and a copy outside launchd from a restart

`deployment machine watchdog` no longer reads every loaded machine agent with no pid as a restart in progress. A machine agent's `KeepAlive` restarts its process only after a failure, so the pass now asks the service's declared doctor: when it reports a machine process running while launchd holds no pid, the entry is `state: outside_launchd` with `outside_pid` and a detail naming the remedy (`<name> service stop --machine`, then `launchctl kickstart gui/$UID/<label>`); when the agent exited cleanly (last exit code 0) it is `state: stopped`, with the `kickstart` that starts it; otherwise it is `state: restarting` as before. Each such entry carries `last_exit_status`, and none of them is kickstarted. The project-scope `deployment watchdog` is unchanged.

## 2026-10-09 — A node takes its database only from its server's environment

`deployment deploy` no longer sends the deploying machine's store setting: the `AGENT_STORE_*` values are gone from the bulk environment, a service's declared environment never fills an `AGENTKIT_DB_*` key from the Mac, and the entrypoint no longer runs `capabilities store set`, so no setting file is written in the container. The Compose file passes `AGENTKIT_DB_URL` and the other `AGENTKIT_DB_*` keys through from the server's environment, and a deploy leaves the values set there standing. `deployment node status` reports `store` from a probe run in the container through `capabilities-contract`: `configured`, the redacted `setting` with its level and sources, `reachable`, `tls_enforced`, and an `error` when one stops it. Set the variables on each existing node's server before its next deploy: a deploy no longer carries them there.

## 2026-10-08 — A node's store setting carries its schema

`deployment deploy` sends the schema the machine's store setting names as `AGENT_STORE_DB_SCHEMA` beside the other `AGENT_STORE_*` values, and the node's entrypoint passes it to `capabilities store set --schema`, so the node's store setting file binds the same schema as this machine's. A setting that names no schema sends none, and the node binds `agentkit` as before. The setting is read from the machine's store setting file, or from the manager's former files while it is absent.

## 2026-10-05 — Supervised services run at standard priority

The launchd agents `deployment sync` (host-agents) and `deployment machine sync` compile for a service now carry `ProcessType Standard` instead of `Background`, so a service and everything it starts - agent turns, builds, test runs - run at standard priority on every core rather than at the lowest priority on the efficiency cores with throttled I/O. The two watchdog agents, short scheduled probes, stay `Background`. `deployment machine status` reports each agent's compiled `process_type`, the `spawn_type` launchd runs it with, and `spawn_type_current`, which stays false until a loaded agent is handed to launchd again; the project doctor's `host_agents` entries carry `spawn_type`. An existing install picks the change up by running the sync and then the steps `deployment machine next` (or `deployment next`) prints.

## 2026-10-05 — Container artifacts compile into one bundle per target, and a deploy creates no Coolify environment

A container runtime that declares no artifact path compiles each target's artifacts into `deployment/targets/<target>/`, beside the target's declaration `target.json`: `docker-compose.yaml`, `Dockerfile`, `Dockerfile.dockerignore`, `.env.example`, `entrypoint.sh`, `supervisord.conf` when Supervisor runs, and `body-sync.sh` on the checkout profile. The project root gains only `.gitattributes` on the checkout profile. The build context stays the project root (`context: ../../..` from the bundle), the ignore file is named for its Dockerfile because Docker reads a plain `.dockerignore` only at the root of the context, and `deployment/runtime.json` and `deployment/capabilities.lock` stay shared. `setup` and `init` write the new layout; a runtime that names `compose_file` or `compiler.artifacts`, as every runtime compiled before this does, keeps its declared paths unchanged, and a declaration at `deployment/targets/<target>.json` is still read. `deployment guide standard` gives the steps that move a project onto bundles, and a bundled runtime's sync names each generated root-layout file it no longer writes.

`deployment deploy` sets the Coolify application's base directory to the Compose file's folder and its Compose location to the file's name, at creation and on every deploy, so Compose resolves the build context the same on the server as locally; an application created before follows on its next deploy. It places a new application in the project's existing environment (`target.environment`, `production` when absent) and creates none: the request it made to Coolify's environment endpoint is gone, and a named environment the project lacks stops the deploy with `environment_missing` before anything is created. A new Coolify target declares `production`. The application is named `<project>-<target>` after the name ContextKit's config holds for the project, else its recorded project slug, rather than after the checkout folder, and every deploy sets that name again.
## 2026-10-04 — Agent nodes deploy and sync through Coolify

`deploy`, `rollback`, `logs`, and `node login|status|sync` operate a checkout node through a granted Coolify connection and the server's SSH Git hub. Environment and node keys travel on stdin, subscription logins remain interactive, failed deployments request the previous release, and body conflicts abort without discarding either writer. Service placement selects node/local/both per substrate; ContextKit memory uses Git union merges, and host-agents compiles node sync intervals. No existing declaration needs a placement field.

Live-provider compatibility accepts plain identifier UUIDs, keeps connection selection in each CLI parser’s required position, disables automatic deploys through application update, discovers OpenSSH identities when the pairing omits one, resolves the instance address for Coolify’s local server, and finds Compose containers when the API omits its internal numeric id. First deployment does not require rollback support until a previous application exists.

## 2026-10-03 — Machine services are supervised by a machine scope

`deployment machine sync` compiles a launchd agent `capabilities.machine.<name>` for every installed capability that declares `service.machine` and is allowed on this machine, running its machine command with `AbandonProcessGroup`, plus a `capabilities.machine.watchdog` agent whose pass (`deployment machine watchdog`) runs each one's machine doctor and kickstarts it after repeated failures. Settings live in `$XDG_CONFIG_HOME/deployment/machine.json` (watchdog settings and a per-service `disabled`) and the agents in `$XDG_STATE_HOME/deployment/machine/launchd/`, whatever directory it runs from. `deployment machine next` prints the `launchctl` hand-over and `deployment machine status` reports each agent; installing one stays a person's act. Nothing the project scope does has changed.

## 2026-10-03 — Container images install their capabilities allowed

The generated Dockerfile installs each capability in `deployment/capabilities.lock` with `capabilities install <name> --allow`, because a capability new to a machine otherwise arrives quarantined and an image is one agent's whole environment. Rebuild an image with `deployment sync` to pick it up.
