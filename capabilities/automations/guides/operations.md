# Operating automations

Run `automations doctor` after configuration changes. It validates the config, script paths, the store the run ledger lives in, environment selection, and bundled runtime.

The daemon reads configuration at startup, so a change to schedules, limits, environment selectors, or script declarations is declared and not yet in force. `automations service reload` closes that gap: the configuration is validated before it replaces anything, a daemon that rejects it keeps the one it is running, and jobs already dispatched finish under the declaration that started them. Reaching for a restart instead ends that work for no reason. Changing the state root or the records backend is what a reload genuinely cannot do, and still needs one.

It records what it read, and the environment it read it under. `automations doctor` compares the declaration against the configuration declared now and fails with `config_stale` while a running daemon is scheduling a superseded one, so the gap is a health answer rather than something an operator has to remember. The environment is published for a neighbouring reason: a supervisor starts the daemon with its own `AUTOMATIONS_ENVIRONMENT` and a terminal opened later carries none, so `doctor` and `service status` report the daemon's own answer as `daemon_environment` beside this invocation's `environment` rather than letting one stand for both, and `doctor` fails with `environment_idle` when none of the declared automations is declared for the environment the daemon loaded. Such a daemon is alive, answering, and scheduling nothing, which is the state a count of the declarations used to report as healthy. A daemon started before that record existed publishes no environment and keeps running across the upgrade, so `doctor` reports `environment_unknown` for it and stays `ok`: an absent record is not a mismatch, and the answer says what it cannot speak to rather than failing a deployment that is working. The same answer is what a caller waits on: a reload returns when the daemon publishes the fingerprint of the declaration it has taken up, so nothing reports itself current while running something else. A job cannot restart its own scheduler - stopping the program stops the process group it is running in - but it can reload it, which is the other reason the verb exists.

Use `automations service run` as the foreground process under Docker Compose or another process supervisor. `automations service start` and `stop` are local conveniences. Inspect work through `automations runs`, `automations show`, and `automations logs`; cancellation and retry are explicit CLI operations.

On a machine that carries several projects, one scheduler can serve them all instead of one daemon each. Initialise the machine settings once with `automations service init --machine`, run `automations service join` in each project that is to be served - it must enable automations for itself - and supervise `automations service run --machine` the way a project daemon is supervised (`deployment help` covers keeping it running). The machine process owns only what is the machine's: one store connection for each distinct store its projects resolve, the optional cap on jobs running at once across every project, and the turn in which projects are dealt starts under it. Each project keeps its own declaration, limits, state root, pause and environment, and every job starts in its project with the project's `.env` and `.env.local` beneath it, so a script cannot tell which mode started it. One process serves a project at a time: a joined project refuses its own `service start`, and the machine process waits while a project daemon still holds the project. `automations service status --machine` names every joined project as `served`, `paused`, `refused` or `error` with the reason, and a project's own trouble never stops the others. Taking a project back is `automations service leave` there, then `automations service start`. `automations help` states the whole contract under Machine mode.

The scheduler records due work and immediately returns to ticking. Jobs execute in separate process groups with captured output, bounded concurrency, timeouts, graceful cancellation, and retry policy. On startup, active records become `interrupted` and surviving process groups are terminated; `engine.recovery` chooses whether interrupted work remains failed for inspection or is queued as a new attempt. The ledger and queue are the table `automations_runs` in the PostgreSQL the project resolves - the `AGENTKIT_DB_*` keys in its `.env.local` / `.env`, then the process environment, then the machine's store setting file - shared by every machine that resolves it, each run carrying the host it was recorded on. `service run` and `service start` refuse with `store_not_configured` while the project resolves no store, `doctor` fails the same way, and `service status` names the level in force; `capabilities store show` names every level and `capabilities store doctor` proves the one in force.

Project runtime files live under `$XDG_STATE_HOME/capabilities/projects/<project-slug>/automations` by default. `AUTOMATIONS_STATE_DIR` remains an explicit override, and it is read from the project's `.env` or `.env.local` as well as from the process environment, so a project that pins its state root declares it once rather than leaving every shell to export it. A supervisor's environment is invisible to a terminal opened later, so a starting daemon also records the root it is actually using in `capabilities/automations/state/state-root.json`, inside the project state home that the manager's guard keeps out of commits, and an invocation that would otherwise resolve the default answers about that daemon for as long as it is alive. A record at `capabilities/automations/state-root.json`, beside the state home, answers the same way for the daemon that wrote it, and it is removed when `service start` or `service run` next starts a daemon, or by `service stop`, so a project that commits its body stops carrying it. `service status` names the root it read and every root it weighed, and `service stop` removes the record along with the pid file. An envelope that refuses the file - a read-only mount, foreign ownership - never stops the daemon: it starts, and the failure to record it is reported as `state_record_error` by `service start` and `service stop`, on `service run`'s stderr, and by `service status` for as long as the record is missing and cannot be written. On the first service start after upgrading from the envelope layout, durable files are copied from `capabilities/automations/state`, historical run-log paths are repointed in the run ledger, generated scripts and daemon files are rebuilt, and the source is preserved for operator-verified cleanup. The state root record shares that directory and belongs to the running service, so it is neither copied nor part of that cleanup.
