# automations — change log

## 2026-10-08 — The scheduler also runs once per machine

`automations service run --machine` (or `start --machine`) is one scheduler process serving every project that joined it with `automations service join`; `service leave` takes a project off, and `leave --machine --project <id-or-slug>` does so from anywhere. The machine process holds one store connection for all of them and an optional cap on jobs running at once across them, `max_parallel` in `$XDG_CONFIG_HOME/automations/service/config.toml` (`service init --machine` writes it), dealing starts round the projects in turn under it. Each project keeps its own declaration, limits, state root and environment: a job starts through `service launch`, which puts the project's `.env` and `.env.local` under it in its own process with the project as its working directory, so it runs as the project's own daemon runs it, and every run lands in `automations_runs` under its project's id and host. The machine process loads no project's environment and checks before every tick that a project is still on the list and enables automations for itself. One process serves a project at a time, by the project's own lock: a joined project's `service start` and `run` exit 4 `joined_to_machine_service`, as does its `service stop` while the machine process serves it, and the machine process reports a project whose own daemon still runs as refused until that daemon stops. `service status --machine` and `doctor --machine` answer for the process and for every joined project as `served`, `paused`, `refused` or `error` with the reason, and a project whose declaration does not load, or that is paused or refused, leaves the others served. `service pause` and `service resume` are new in both modes: a paused project registers and starts nothing while its running jobs finish. Every service log line now reads `<moment> automations service [<project-slug>]: …`, in both modes. A project that does not join runs its own daemon exactly as before. `service stop` no longer removes a pid file that has come to name another process while it waited.

## 2026-10-08 — The run ledger lives in the machine's store

Runs and their queue now live in the table `automations_runs` of the PostgreSQL the machine's store setting names, or the one `CAPABILITIES_STORE_URL` names, reached through the shared `capabilities-contract` library under its own migration ledger. The table starts empty: nothing is read from or written to `store.db`, which stays as it was, and runs pending there are not carried over; the next schedule creates new ones. Each run carries the project's id and the host it was recorded on, and a scheduled firing is deduplicated within its project. `service run` and `service start` refuse with `store_not_configured` and a hint naming `capabilities store set` while the machine has no store, `doctor` and `service doctor` fail the same way, and `service status` reports `store` as `setting` or `CAPABILITIES_STORE_URL`, or null with `store_error`. A daemon whose store connection drops reconnects on its next tick instead of exiting. `doctor --repair` is still accepted and has nothing to repair. The deployment descriptor passes `CAPABILITIES_STORE_URL` and `CAPABILITIES_STORE_PASSWORD` through.

## 2026-10-06 — The run ledger works on a PostgreSQL store

With `CAPABILITIES_STORE_URL` naming a `postgresql://` store and its driver present, the scheduler now enqueues, claims, runs, cancels and retries runs there, and `run`, `runs`, `show`, `logs`, `cancel`, `retry`, `service status` and `doctor` read and write them; before, every one of them failed on the first run query. A scheduled firing is still claimed once however many daemons share the store: its dedupe key decides it on either backend, and on PostgreSQL a dispatcher holds the pending rows it is choosing from until it has taken one. `doctor` reads the `runs` columns from the database's own catalogue on PostgreSQL. On the SQLite default nothing changes, and existing run history reads as it did.
