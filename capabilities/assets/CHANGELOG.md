# assets — change log

## 2026-10-31 — `assets help` names the agent's vault in the credential cascade

Bare `assets help` no longer lists where a secret resolves by hand, a list that stopped at the process environment and left out the agent's vault; it now points to the contract-rendered `Where a secret resolves` section at the end of the help, which names the vault as the cascade's last tier. It also says `connection add` stores the two keys it takes on stdin as that section says, where it used to say they are written to the project's `.env.local`. Nothing else changes.

## 2026-10-27 — Every write to a kept file is logged

Every write to a file's records is logged in the same transaction as the write: a row of the new append-only table `assets_file_operations` names the record written or retired, the outcome the verb answered - `created` or `replaced` by `files add` and `import`, `linked` or `unlinked` by `files link`, `removed` by `files rm` - who did it and when. `files log [<name>] [--limit N]` reads it newest first, at most N records (default 100), each with the file's name, size, sha256 and document, and with a name it lists that file's records, a removed file's included, so a deleted file leaves a trace of who deleted it and when. It reads the store only. An `unchanged` answer logs nothing. The store refuses an edit or a delete of a log record. The assets tables move to schema 1.2 by the one new step `0006-file-operations`, applied on an existing store by the first command that opens it; the log starts there, and writes made before it are not backfilled. Only an `assets` at this change or later writes the log: an older `assets` still writes to a store at 1.2 - it reads the store as current - and its writes, a `files rm` included, are not in the log. A `TRUNCATE assets_files` without `CASCADE` is now refused by the log's reference to it before the guard trigger is reached; it is refused either way.

## 2026-10-27 — A kept file can be deleted

`files rm <name>` deletes a file the project kept: the object of every record the name has had - the current one and every one it replaced - is deleted from the bucket, then the current record is retired, so the name leaves `files list`, `export` and its document's `files`, and is free for a new file. Records are still never deleted; a retired record of a removed file names bytes the bucket no longer holds. It asks on the terminal before deleting and is refused without one (exit 6 `confirmation_required`) unless `--yes`; a name with no unretired file is refused with exit 3 `not_found`. It answers `removed` with the record it `retired` and the storage keys it `deleted`. It is a write, under the write gate and the read-only switch.

## 2026-10-21 — A connection whose network flow died fails in seconds

`assets` uses `capabilities-contract` 0.7.2. Its store connections give a network flow up once data sent on it has gone unacknowledged for 20 seconds (`tcp_user_timeout`), which keepalives cannot notice since none is sent while data waits, and send keepalives after 15 seconds idle, every 5 seconds, 3 probes: a connection whose flow stopped carrying packets without a FIN or a reset fails in about 20 seconds as a lost connection instead of waiting until the store ends the session, and a plain read that loses it that way runs once more on a new connection. A connection lost where `assets` catches nothing ends the command as `store_unreachable`, exit 5, as before.

## 2026-10-21 — A kept file is linked to its document after the fact

`files link <name> --document NAME` sets the document a kept file belongs to, and `files link <name> --none` clears it, so a file imported with no document - its folder beside the write-up rather than under it - can be attached to it afterwards. The file's record stays immutable: the bytes are copied in the bucket to a new key, checked against their size and sha256 on the way, and a new record is written that retires the current one, as any change to a file is recorded. It answers `linked`, `unlinked` or `unchanged` with the record it `replaced`; an unchanged link reads and writes nothing. It is a write, under the write gate and the read-only switch. `show` lists under `files` the names of the unretired files that belong to the document.

## 2026-10-21 — doctor proves the bucket as a file verb uses it, and import leaves OS litter behind

`doctor` proves each file store connection by a put, head and delete of one throwaway object under the project's prefix, the round trips a file verb makes, and reports them under `proof`; a connection that may not be written, a run under the read-only switch, and a project without an id keep the authenticated listing (`proof: ["list"]`). A connection this project can see but may not use - added but not granted, or switched off - is named under `connections` as `connection_not_granted` with the grant it needs, where doctor answered `{}`; it fails nothing, since a machine's connection is withheld in every project that never asked for it. `import` skips `.DS_Store` and `.gitkeep`, listing each under `skipped`, rather than keeping them in the bucket as project files. `connection add` says whether this project may use the connection it wrote (`granted`) and names the grant a store-mode project still needs.

## 2026-10-20 — Every other file is kept in an S3-compatible bucket

`assets` keeps every file that is not a markdown document in a bucket of any S3-compatible store - Cloudflare R2, AWS S3, Backblaze B2, MinIO and the like - reached through its own file store connection: `endpoint`, `region` and `bucket` sit in the connection entry, the access key id and secret access key resolve through the credential cascade under the env keys the entry names (`access_key_id_env`, `secret_access_key_env`; `connection add` writes them as `ASSETS_<ID>_ACCESS_KEY_ID` and `ASSETS_<ID>_SECRET_ACCESS_KEY`), and every request is addressed path-style and signed with AWS Signature Version 4 over the payload's sha256. A file's bytes are the object `<project id>/<file id>/<name>` and its record is a row of the new table `assets_files` - name, media type, size, sha256, storage key and the document it belongs to - which the store keeps immutable: a replaced file is a new row and the old one is retired, never overwritten or deleted. `files add`, `files get` and `files list` reach them; `import` keeps every file that is not markdown as `files add` does and reports each `created`, `replaced` or `unchanged`; `export` writes each file back byte for byte beside the documents under the rules it applies to documents; every read checks the size and sha256 against the record and refuses a mismatch with exit 8 (`sha256_mismatch`, `object_missing`); and `doctor` proves each connection's bucket with an authenticated listing. Writing to the bucket is a write, under the write gate and the read-only switch. Without a connection every documents verb and `doctor` work as before, and `import` lists every file that is not markdown as skipped with the reason that no file store connection is configured. As for every connection-bearing capability, `assets connections` without a connection registry now refuses with exit 6 `connections_required` where it reported no connections.

## 2026-10-20 — A read is a transaction of its own in one round trip

`assets` uses `capabilities-contract` 0.6.0. On its working connection a plain read that would open a transaction, and any statement in autocommit, reaches the store in one round trip - the transaction's start, the schema binding and the commit go with it - and leaves the connection idle, never `idle in transaction`, so a transaction-mode pooler hands its server session on as soon as the store answers; a write still opens a transaction that its commit closes, and a write whose commit may have reached the store is never sent twice. A connect that fails is tried again after jittered, doubling pauses, and once a store did not answer, a further connect to it is refused at once as `store_unreachable` for a doubling pause of at most 30 seconds rather than dialled again on every statement.

## 2026-10-20 — A project's text assets as versioned documents in its store

`assets` keeps an agent's markdown assets - plans, research, sessions, meetings, journal, digests, reports and notes - as documents in the PostgreSQL the project resolves, in the tables `assets_documents` and `assets_versions` under its own migration ledger. A document is named by its path under `assets/` without `.md`, and its top folder gives its kind. Every save adds a version and leaves one active; versions are never edited or deleted, and the store refuses both. `save` takes an optional base and is refused with exit 7 `stale_base` when another save came first; `retire` hides a document without deleting anything. `list`, `show`, `history`, `diff` and full-text `search` read them, `import` reads an assets folder into the store, listing every file that is not markdown as skipped, and `export` writes the active versions back byte for byte.
